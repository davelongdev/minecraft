# Java Edition mods (Fabric / NeoForge) vs. data packs: capabilities, client/server split, distribution, cost

Research date: 2026-10-12. Current Minecraft Java release: 26.3 (data pack format 121, `java_version: 25`, built 2026-09-15 — read from `version.json` inside the local `minecraft-26.3-client.jar`). Fabric's developer docs currently default to "26.2"; NeoForge's docs default to "26.1". Both toolchains have builds for 26.3 (see Q5). Anything version-specific is marked.

## Q1. What can a mod do that a vanilla data pack cannot?

### Takeaway
A data pack is server-side JSON + mcfunction: it can define content in the registries Mojang made data-driven (functions, loot, recipes, worldgen, dialogs, …) but cannot run code, touch the client, add new block/item/entity *classes*, draw UI, read keys, or alter vanilla logic. A mod is Java running inside the game process (on the client, the server, or both) with full access to the game's classes, plus loader APIs for keybinds, HUD/screens, networking, registries, and Mixin bytecode patching.

### Cited Findings
- Data packs (Java-only) can define/alter: advancements, dimensions/dimension types, enchantments + enchantment providers, loot tables, item modifiers, predicates, recipes, structures, biomes, worldgen incl. terrain, functions, tags, banner patterns, painting variants, armor trims, jukebox songs, trades, mob variants, chat types, damage types, dialogs, timelines, trial spawner configs, goat horn instruments. `/reload` only reloads tags, loot tables, recipes, advancements, item modifiers, predicates, functions, and structure templates; other changes need a world reopen/server reboot. Latest listed format is 121.0 for 26.3. — [Minecraft Wiki: Data pack](https://minecraft.wiki/w/Data_pack)
- Fabric's developer guide (26.2) covers what mods add that packs can't: Items (first item, food, fuel, potions, spawn eggs, tools, armor, shields, custom item interactions, custom enchantment effects, custom data components), Blocks (block entities, block entity renderers, containers, container menus, workstations), Fluids, Entities (first entity, projectiles, attributes, mob effects, damage types), Sounds (incl. dynamic sounds), Commands (creating commands, arguments, suggestions), Rendering (GUI drawing, HUD, in-world rendering, custom screens, custom widgets, particles), Serialization (codecs, data attachments, saved data), Mixins, Class Tweakers (access widening, interface injection, enum extension), Key Mappings, Networking, Game Rules, Statistics. — [Fabric Developer Guides index](https://docs.fabricmc.net/develop/)
- **Keybinds (Fabric, 26.2):** "Key mappings only exist on the client side." Register in the client initializer with `KeyMappingHelper.registerKeyMapping(new KeyMapping("key.example-mod.send_to_chat", InputConstants.Type.KEYSYM, InputConstants.KEY_J, CATEGORY))`; categories via `KeyMapping.Category.register(ExampleMod.id("custom_category"))`; react with `ClientTickEvents.END_CLIENT_TICK.register(client -> { while (this.sendToChatKey.consumeClick()) { … } })`; in GUIs use `ScreenEvents.BEFORE_INIT` + `ScreenKeyboardEvents.beforeKeyPress(screen)` and `keyMapping.matches(keyEvent)`. Translations: `key.category.<namespace>.<path>`, `key.<modid>.<name>`. — [Fabric Docs: Key Mappings 26.2](https://docs.fabricmc.net/develop/key-mappings)
- The older Fabric wiki page uses the previous name `KeyBindingHelper.registerKeyBinding(...)`, requires a `ClientModInitializer` entrypoint registered in `fabric.mod.json`, `"fabric-key-binding-api-v1": "*"` in `depends`, and notes "Versions 1.21.9 and later use a `KeyMapping.Category` object … Older versions use a translation key string"; a server response "requires a custom packet handled on the server". — [Fabric Wiki: Keybinds tutorial](https://wiki.fabricmc.net/tutorial:keybinds)
- Vanilla 26.3 `net.minecraft.client.KeyMapping` public API (from `javap` on the local client jar): constructors `KeyMapping(String, int, KeyMapping$Category)`, `KeyMapping(String, InputConstants$Type, int, KeyMapping$Category)`, `KeyMapping(String, InputConstants$Type, int, KeyMapping$Category, int)`; methods `boolean consumeClick()`, `boolean isDown()`, `getCategory()`. — local file `~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/libraries/com/mojang/minecraft/26.3/minecraft-26.3-client.jar` (primary, inspected 2026-10-12)
- **Keybinds (NeoForge, docs v26.1):** wrap the `KeyMapping` in a `Lazy`, register it in a physical-client-only handler for `RegisterKeyMappingsEvent` (`event.register(...)`, optionally `event.registerCategory(...)` first); constructor takes translation key, `InputConstants.Type` (`KEYSYM`/`SCANCODE`/`MOUSE`), GLFW code, category, plus NeoForge-only optional `IKeyConflictContext` (`UNIVERSAL`/`GUI`/`IN_GAME`) and `KeyModifier` (`NONE`/`CONTROL`/`SHIFT`/`ALT`). Poll in `ClientTickEvent.Post` with `while (mapping.consumeClick())`; the docs warn against using `InputEvent`s for this. In screens use `isActiveAndMatches(...)`, or `ScreenEvent.KeyPressed`/`MouseButtonPressed` `Pre`/`Post` for screens you don't own. — [NeoForge Docs: Key Mappings](https://docs.neoforged.net/docs/misc/keymappings)
- **HUD (Fabric 26.2):** `HudElementRegistry.attachElementBefore(VanillaHudElements.CHAT, ExampleMod.id("before_chat"), HudRenderingEntrypoint::extract)`; elements receive a `GuiGraphicsExtractor` and `DeltaTracker`; example draws `graphics.fill(0, 0, 10, 10, color)`. The older `HudRenderCallback` was removed in 26.1 in favour of `HudElementRegistry`. — [Fabric Docs: Rendering in the HUD](https://docs.fabricmc.net/develop/rendering/hud); [Fabric blog: 26.1](https://fabricmc.net/2026/03/14/261.html)
- **Commands (Fabric 26.2):** mods register server commands via `CommandRegistrationCallback.EVENT.register((dispatcher, buildContext, environment) -> dispatcher.register(Commands.literal("name").executes(...)))`; permission gating is now `.requires(source -> source.permissions().hasPermission(Permissions.COMMANDS_MODERATOR))` (not the old `hasPermission(2)`); `environment.includeDedicated` restricts to dedicated servers. Client-only commands: `ClientCommandRegistrationCallback.EVENT.register(...)` with `ClientCommands.literal(...)` from `net.fabricmc.fabric.api.client.command.v2`. — [Fabric Docs: Creating Commands 26.2](https://docs.fabricmc.net/develop/commands/basics)
- **Mixins:** transform a target class's bytecode at runtime before it loads; used for "injecting custom logic, removing mechanics, or modifying values". Annotations: `@Mixin` (target + priority; must be listed in a mixin config JSON), injectors `@Inject`, `@ModifyVariable`, `@ModifyArg`; redirectors `@Redirect`, `@ModifyConstant`; `@Overwrite`; MixinExtras `@WrapOperation`, `@ModifyExpressionValue`. Only Java mixins are directly supported (Kotlin needs a compat layer); "Overwriting is inherently incompatible … it should never be done"; injectors are preferred because they chain. — [Fabric Wiki: Mixin Introduction](https://wiki.fabricmc.net/tutorial:mixin_introduction)
- **Networking (Fabric 26.2):** a payload is a Java record implementing `CustomPacketPayload` with an `Identifier`, a static `CustomPacketPayload.Type`, a `StreamCodec` (`StreamCodec.composite`) and `type()`. Register on both sides in the common initializer: `PayloadTypeRegistry.clientboundPlay().register(TYPE, CODEC)` / `PayloadTypeRegistry.serverboundPlay().register(TYPE, CODEC)`. Client→server: `ClientPlayNetworking.send(payload)`; receive with `ServerPlayNetworking.registerGlobalReceiver(TYPE, (payload, context) -> … context.player() …)`. Server→client: `ServerPlayNetworking.send(player, payload)`, `ClientPlayNetworking.registerGlobalReceiver(...)`. "There is always a server running, even in singleplayer and LAN." "It is important that you validate the content of the packet on the server side." — [Fabric Docs: Networking 26.2](https://docs.fabricmc.net/develop/networking)
- **Networking (NeoForge, docs 26.1):** `RegisterPayloadHandlersEvent` → `event.registrar("1")` (network version) → `registrar.playToServer / playToClient / playBidirectional(TYPE, STREAM_CODEC, handler)`; also `configuration*` and `common*` phases; client handlers via `RegisterClientPayloadHandlersEvent`. Payload = `record MyData(...) implements CustomPacketPayload` with `CustomPacketPayload.Type<>(Identifier.fromNamespaceAndPath("mymod","my_data"))` and a `StreamCodec.composite(...)`. Handler signature `(MyData data, IPayloadContext context)`, runs on main thread by default; `context.enqueueWork(...)` from the network thread. Sending: `ClientPacketDistributor.sendToServer(payload)`, `PacketDistributor.sendToPlayer(serverPlayer, payload)`, `PacketDistributor.sendToAllPlayers(payload)`. Size limits: ≤1 MiB clientbound, <32 KiB serverbound. — [NeoForge Docs: Registering Payloads](https://docs.neoforged.net/docs/networking/payload)
- **World gen / data hooks:** NeoForge auto-applies every mod's `data/` as a data pack to each new world (cannot be disabled; overridable by higher-priority packs) and generates `pack.mcmeta` at runtime; data generation (`GatherDataEvent`) writes JSON to `src/generated/resources`. — [NeoForge Docs: Resources](https://docs.neoforged.net/docs/resources/) (details in Q6)

### Inferences
- Everything in the "client" column (keys, HUD, screens, rendering, particles, sounds-at-will) is categorically out of reach for a data pack because data packs run only on the logical server and the vanilla client exposes no scriptable hooks. For this project's actual pain point (detecting an arbitrary key press like N), a mod is the *only* route; the current workaround (counting jumps via the `minecraft.custom:minecraft.jump` stat) is exactly the kind of indirection a 30-line client mod removes.
- The NeoForge key-mapping API and the Fabric one are near-identical wrappers over the same vanilla `KeyMapping` class (confirmed in the 26.3 jar), so the client half of a keybind mod ports between loaders with mostly import changes.

### Gaps
- I did not fetch a page that itemises what data packs *cannot* do in Mojang's own words; the Data pack wiki page lists capabilities, not limits. The "cannot" list above is inferred from the absence of those registries in the wiki list and from Fabric's "key mappings only exist on the client side".
- The Fabric docs networking page says nothing about executing commands server-side from a received payload; the pattern (`context.player().level().getServer().getCommands().performPrefixedCommand(...)`) is from general knowledge and not cited here.

## Q2. The specific scenario: a key (N) that makes a server function react — minimal Fabric and NeoForge implementations

### Takeaway
A **client-only** mod is enough: on key press, call vanilla's `ClientPacketListener.sendCommand(String)` (26.3 signature confirmed in the jar) via `Minecraft.getInstance().player.connection`, which is exactly what pressing Enter on `/trigger …` in chat does; the server then runs it with the player's own permissions, so use a level-0 command such as `/trigger` to feed a scoreboard the data pack already watches. A custom packet (needs the mod on the server too) is only required if you want to bypass permission limits or send structured data. Several published Fabric mods already do the "key → chat command" thing with no server component.

### Cited Findings
- 26.3 vanilla client API (from `javap` on the local jar): `net.minecraft.client.multiplayer.ClientPacketListener` has `public void sendChat(String)`, `public void sendCommand(String)`, `public void sendUnattendedCommand(String, Screen)`; `net.minecraft.client.player.LocalPlayer` has `public final ClientPacketListener connection` and `ChatAbilities chatAbilities()`. Server-side permission atoms in `net.minecraft.server.permissions.Permissions`: `COMMANDS_MODERATOR`, `COMMANDS_GAMEMASTER`, `COMMANDS_ADMIN`, `COMMANDS_OWNER`, `COMMANDS_ENTITY_SELECTORS`, `CHAT_SEND_MESSAGES`, `CHAT_SEND_COMMANDS`, `CHAT_RECEIVE_PLAYER_MESSAGES`, `CHAT_RECEIVE_SYSTEM_MESSAGES`. — local `minecraft-26.3-client.jar` (inspected 2026-10-12)
- Fabric key handling (client initializer): `KeyMappingHelper.registerKeyMapping(new KeyMapping("key.example-mod.send_to_chat", InputConstants.Type.KEYSYM, InputConstants.KEY_J, CATEGORY))` + `ClientTickEvents.END_CLIENT_TICK.register(client -> { while (key.consumeClick()) { if (client.player == null) return; … } })`. — [Fabric Docs: Key Mappings 26.2](https://docs.fabricmc.net/develop/key-mappings)
- NeoForge key handling: `RegisterKeyMappingsEvent` (mod bus, client only) + `ClientTickEvent.Post` with `while (mapping.consumeClick())`. — [NeoForge Docs: Key Mappings](https://docs.neoforged.net/docs/misc/keymappings)
- Fabric client→server packet alternative: `PayloadTypeRegistry.serverboundPlay().register(TYPE, CODEC)` in the common initializer on both sides; `ClientPlayNetworking.send(payload)`; `ServerPlayNetworking.registerGlobalReceiver(TYPE, (payload, context) -> …)`; "validate the content of the packet on the server side". — [Fabric Docs: Networking 26.2](https://docs.fabricmc.net/develop/networking)
- NeoForge client→server packet alternative: `registrar.playToServer(TYPE, STREAM_CODEC, ServerPayloadHandler::handle)` and `ClientPacketDistributor.sendToServer(new MyData(...))`. — [NeoForge Docs: Registering Payloads](https://docs.neoforged.net/docs/networking/payload)
- **Published precedents (all Fabric, all "client-side" per their pages):**
  - *BindCommands* (Modrinth, 613.2K downloads, MIT, source github.com/devs-immortal/bind-cmd): versions listed through 26.3; requires Mod Menu (its own README adds Fabric Language Kotlin for older builds). Current source: `gradle.properties` `minecraft_version=26.3`, `loader_version=0.19.5`, `fabric_api_version=0.161.0+26.3`; `fabric.mod.json` `"environment": "*"`, `depends` `fabric-api >=0.160.5`, `fabricloader >=0.19.0`, `minecraft >=26.3-`, `modmenu *`; has a `client` entrypoint and an optional `server` entrypoint (`DedicatedServerModInitializer`) that only pushes server-defined bindings to clients via a `ConfigPayload` on `clientboundPlay`/`clientboundConfiguration` — the key→command path itself is client-side: `@Mixin(KeyMapping.class) … @Inject(method = "click", at = @At("HEAD"))` reads bound commands from config, applies a 200 ms cooldown, and imports `ClientPacketListener` to send; `Command.java` classifies text starting with `/` as `CmdType.COMMAND` and strips the slash. — [Modrinth: BindCommands](https://modrinth.com/mod/bindcommands); [GitHub: devs-immortal/bind-cmd](https://github.com/devs-immortal/bind-cmd)
  - *d1ezz9's Chat Keybinds*: Minecraft 26.1.2, Fabric Loader ≥0.19.3 + Fabric API, "fully client-side", MIT, 90 downloads; entries beginning with `/` are "sent as server commands, such as `/home`". — [Modrinth](https://modrinth.com/mod/d1ezz9s-chat-keybinds)
  - *ChatMacro* (client-side Fabric, 1.21.11; entries starting with a slash go to the server as a command), *AnyBind* (CurseForge; adds binds into the vanilla Controls menu, "sending chat or game commands"), *Saved Commands*, *Auto Command / AutoCommandX* (four slots bound in Options → Controls → Key Binds, 1.21.9/1.21.10), *KeyBinder* (1.20.1–1.21.8), *Easy Keybinds* (states it works on multiplayer servers incl. Hypixel). — [ChatMacro](https://modrinth.com/mod/chatmakro); [AnyBind](https://www.curseforge.com/minecraft/mc-mods/anybind); [Saved Commands](https://modrinth.com/mod/savedcommands); [KeyBinder](https://modrinth.com/mod/keybinder)
- **Permissions:** Java operator levels 0–4; level 2 ("Gamemaster") unlocks "more commands, command blocks … target selectors"; a singleplayer world with cheats enabled gives level 4; a LAN world with cheats gives every player level 4; otherwise players are level 0. Servers set per-player levels in `ops.json`; `function-permission-level` (since 1.14.4 pre-4) sets the level functions run at. `/trigger` is listed as Java-only; the page does not give it a level. — [Minecraft Wiki: Permission level](https://minecraft.wiki/w/Permission_level)
- Fabric commands can be hidden from unprivileged players: commands failing `.requires(...)` "are not registered and don't appear in tab completion for those users". — [Fabric Docs: Creating Commands](https://docs.fabricmc.net/develop/commands/basics)

### Inferences
- **Minimal Fabric implementation (client-only, ~1 class + fabric.mod.json):** `ClientModInitializer` → register `KeyMapping` for `InputConstants.KEY_N` with `KeyMappingHelper` → in `ClientTickEvents.END_CLIENT_TICK`, `while (key.consumeClick()) client.player.connection.sendCommand("trigger tut_key_n");` (no leading slash, mirroring how `/trigger` typed in chat is sent). The data pack side is unchanged vanilla: `scoreboard objectives add tut_key_n trigger`, `scoreboard players enable @a tut_key_n` each tick, and a tick function that reacts to `tut_key_n` ≥ 1 and resets it. Vanilla servers accept this because it is indistinguishable from the player typing the command. `fabric.mod.json` can set `"environment": "client"` so the jar is ignored on dedicated servers.
- **Minimal NeoForge implementation:** same shape — `@Mod(value = "...", dist = Dist.CLIENT)` class with a `Lazy<KeyMapping>`, `RegisterKeyMappingsEvent` registration, `ClientTickEvent.Post` → `Minecraft.getInstance().player.connection.sendCommand("trigger tut_key_n")`. For client-only acceptance on vanilla/other servers Forge-era docs use `displayTest = "IGNORE_ALL_VERSION"` in `neoforge.mods.toml`, but see Gaps: I could not find that key in the current NeoForge docs.
- **Permission reality:** `sendCommand` runs as the player, so it can only do what the kid could type. In the Command Forge singleplayer worlds, cheats are on (level 4), so even `function tut:...` would work; on a LAN/dedicated server you'd want `/trigger` (designed for level-0 players) so no op is needed. A custom packet with a server-side receiver sidesteps permissions entirely (the receiver can call the server's `Commands` dispatcher as the server) but then the mod must be installed on the server too — trivial in singleplayer (same JVM, same `mods/` folder), a real constraint on a shared server.
- Since 26.3 exposes `CHAT_SEND_COMMANDS` as a permission atom, a server could in principle strip a player's ability to send commands; the default for ordinary players is unaffected.

### Gaps
- I read only the head of `KeyMappingMixin.java` in BindCommands; the file imports `ClientPacketListener` and I did not see the exact `sendCommand`/`sendChat` call line. Treat "sends via `ClientPacketListener`" as highly likely but not line-verified.
- No primary source confirms a per-level table of vanilla command permission levels in 26.x (the wiki page defers to "more commands"); the claim that `/trigger` is level 0 is from general knowledge, not cited.
- Current NeoForge docs (`docs/gettingstarted/modfiles.md`, `docs/concepts/sides.md`, grepped at `main`) contain no `displayTest` or `clientSideOnly` entry; whether the Forge-era `displayTest = "IGNORE_ALL_VERSION"` still applies in NeoForge 26.x is unverified. Only Forge documentation and forum posts describe it. — [Forge community wiki: Mods.toml](https://forge.gemwire.uk/wiki/Mods.toml_file)

## Q3. Client-only vs server-only vs both-sides mods

### Takeaway
Rendering, input, HUD/screens, sounds-as-heard, and resource packs live on the logical client (always a physical client); game logic, data packs, world state, and commands live on the logical server (a dedicated server or the integrated server inside singleplayer). A mod needs to be on *both* machines only when it adds registry content (blocks/items/entities/recipe types) or custom packets whose receiver is on the other side; a client-only keybind-to-command mod and a server-only command/rule mod each run on one side.

### Cited Findings
- Physical sides = the two distributions (client via launcher; dedicated server JAR). Logical client = rendering, sends player input, handles resource packs, partially simulates the world; logical server = "core logic, data packs, and holds the authoritative world state". A logical server can be hosted by a physical server *or* a physical client (integrated server). Client-only code carries `@Environment(EnvType.CLIENT)`; check `world.isClient` for the logical side. Logical sides exchange data only via packets (in-memory on the integrated server). — [Fabric Wiki: Side](https://wiki.fabricmc.net/tutorial:side)
- `fabric.mod.json` `environment`: `"*"` (default, all), `"client"` (game client), `"server"` ("the dedicated server. Integrated servers are not included"). Entrypoints `main` (`ModInitializer`, run first), `client` (`ClientModInitializer`), `server` (`DedicatedServerModInitializer`). — [Fabric Wiki: fabric.mod.json spec](https://wiki.fabricmc.net/documentation:fabric_mod_json_spec)
- Fabric template project splits code into `src/main/java` (both environments) and `src/client/java` (client-only), with `src/client/resources`. — [Fabric Docs: Project Structure 26.2](https://docs.fabricmc.net/develop/getting-started/project-structure)
- NeoForge: physical side = `Dist` enum (`Dist.CLIENT` / `Dist.DEDICATED_SERVER`, via `FMLEnvironment.getDist()`), logical side = `LogicalSide`; `Level#isClientSide()` is the default check; "In singleplayer, the physical client starts a logical server and connects to it as the logical client"; restrict a mod class to one physical side with `@Mod(..., dist = Dist.CLIENT)`; "modern server JARs no longer contain classes the client lacks"; `NoClassDefFoundError`/`ClassNotFoundException` are the most common side-separation bugs; "always test with dedicated servers". Dependency entries in `neoforge.mods.toml` take `side = "CLIENT" | "SERVER" | "BOTH"` (default BOTH). — [NeoForge Docs: Sides](https://docs.neoforged.net/docs/concepts/sides); [NeoForge Docs: Mod Files](https://docs.neoforged.net/docs/gettingstarted/modfiles)
- Fabric payload registration must happen "on both physical sides"; client receivers go in the client initializer, server receivers in the common initializer; "A dedicated server has no client code". — [Fabric Docs: Networking](https://docs.fabricmc.net/develop/networking)
- NeoForge auto-loads mod `data/` as data packs on the server and mod `assets/` as a "Mod resources" pack on the client. — [NeoForge Docs: Resources](https://docs.neoforged.net/docs/resources/)
- Fabric's registry sync kicks vanilla/mismatched clients when a Fabric server has modded registry entries (blocks/items, even recipe serializers from a server-side mod); community workarounds exist (RegSyncFix / ModernRegSyncFix for 26.1+, "Bypass Fabric Check" server-side). — [fabricmc/fabric issue #3766](https://github.com/fabricmc/fabric/issues/3766); [ModernRegSyncFix](https://modrinth.com/project/U2w9BZus); [Bypass Fabric Check](https://www.modpackindex.com/mod/149482/bypass-fabric-check)
- Modrinth's `.mrpack` `env` field marks each file `client`/`server` as `required` / `optional` / `unsupported`; "`server` refers to the dedicated server. Files marked server-only should not be installed on clients." — [Modrinth: mrpack format](https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack)

### Inferences
- Feature → where the mod must be installed:
  - Keybind → chat command; HUD overlay; custom screens; client commands; client-side sounds/particles: **client only** (every kid's computer; nothing on the server). Works against a vanilla server.
  - Server commands, gamerules, event hooks on server logic, bundled data pack, server-side receiver for a custom packet: **server only** (in singleplayer that *is* the kid's computer, so "server only" still means installing on each client machine).
  - New blocks/items/entities, custom packets in both directions, block entity renderers for new blocks: **both** (and Fabric's registry sync will refuse clients that lack it).
- For this project (singleplayer worlds per kid, run via Prism), the client/server distinction mostly collapses: one jar in the instance's `mods/` folder covers both halves. The distinction matters only if the class ever moves to a shared server.

### Gaps
- No primary source found stating whether a Fabric server with a client-only (`environment: client`) mod jar in its `mods/` simply skips it; the spec says `environment` "controls which side a mod loads on", which implies yes.
- NeoForge's current mechanism for a client-only mod to connect to servers lacking it (the Forge-era `displayTest`) is undocumented in the pages fetched (see Q2 gaps).

## Q4. Distribution and installation: Modrinth/CurseForge, .mrpack, Prism Launcher (incl. Flatpak), shipping a ready instance to kids

### Takeaway
A mod is a single `.jar` dropped into an instance's `minecraft/mods/` folder (plus Fabric API for Fabric mods). Prism Launcher can install mods from Modrinth/CurseForge in-app, add a local jar ("Add File"), export an instance as a `.zip`, `.mrpack`, or CurseForge pack, and import any of those from a file or URL — so a teacher can hand kids one exported file. Publishing on Modrinth is optional and slow (review queue of days to weeks). The Prism Flatpak sandbox only sees `~/Downloads` (read-only) plus its own `~/.var/app/org.prismlauncher.PrismLauncher` data dir, so on this machine the reliable path is to `cp` the jar straight into `…/instances/<name>/minecraft/mods/` from the host.

### Cited Findings
- **Prism instance mods tab** (UI strings from source `launcher/ui/pages/instance/ExternalResourcesPage.ui`): actions `Add File` ("Add a locally downloaded file."), `Remove`, `Enable`, `Disable`, `View Folder` ("Open the folder in the system file manager."), `Download` ("Download resources from online mod platforms."), `Check for Updates`, `Change Version`, `Lock Updates`, `Export List`. — [PrismLauncher/PrismLauncher source](https://github.com/PrismLauncher/PrismLauncher/blob/develop/launcher/ui/pages/instance/ExternalResourcesPage.ui)
- Prism wiki "Downloading Mods": Edit → Version tab → pick loader (Fabric for 1.14+, NeoForge for >1.20.1) → Mods tab → Download Mods → Modrinth or CurseForge → select → OK; "Fabric mods mostly need the Fabric API for your game version", installable the same way. — [Prism Wiki: Downloading Mods](https://prismlauncher.org/wiki/getting-started/download-mods/)
- **Export:** `MainWindow.ui` defines `actionExportInstance` ("Export the selected instance to supported formats.") with sub-actions `actionExportInstanceZip`, `actionExportInstanceMrPack`, `actionExportInstanceFlamePack` (CurseForge). — [PrismLauncher MainWindow.ui](https://github.com/PrismLauncher/PrismLauncher/blob/develop/launcher/ui/MainWindow.ui). Release 7.0 added "support for exporting instances as Modrinth modpacks (.mrpack)"; 7.1 fixed a Windows bug where exports bundled every mod jar instead of only metadata; 8.0 added CurseForge export and a progress bar. — [Prism news: 7.0](https://prismlauncher.org/news/release-7.0/); [7.1](https://prismlauncher.org/news/release-7.1/); [8.0](https://prismlauncher.org/news/release-8.0/)
- **Import:** Add Instance → "Import" accepts a `.zip` or `.mrpack` "from a website (via a URL) or from your filesystem"; other sources: ATLauncher, CurseForge, FTB App Import, Modrinth, Technic. — [Prism Wiki: Import](https://prismlauncher.org/wiki/help-pages/zip-import/); [Prism Wiki: Downloading Modpacks](https://prismlauncher.org/wiki/getting-started/download-modpacks/)
- **Instance Copy** (right-click → Copy): options to copy saves, game options, resource packs, screenshots, shader packs, servers, mods; advanced: symlinks, hard links, CoW clone (APFS/BTRFS/XFS/ZFS…). — [Prism Wiki: Instance Copy](https://prismlauncher.org/wiki/help-pages/instance-copy/)
- **.mrpack format:** a ZIP with `modrinth.index.json` (`formatVersion: 1`, `game: "minecraft"`, `versionId`, `name`, `files[]` with `path`, `hashes.sha1`+`sha512`, optional `env.client/server`, `downloads[]` HTTPS URLs, `fileSize`; `dependencies` keyed `minecraft`, `fabric-loader`, `neoforge`, `forge`, `quilt-loader`) plus `overrides/`, `client-overrides/`, `server-overrides/` copied into the instance root. Modrinth-hosted packs may only reference `cdn.modrinth.com`, `github.com`, `raw.githubusercontent.com`, `gitlab.com`. Since 2026-06-23 modpacks must submit proof of permission for all external content. — [Modrinth Support: Project Review Times](https://support.modrinth.com/en/articles/8793355); [Modrinth news: modpack permissions](https://modrinth.com/news/article/modpack-permissions)

### Inferences
- **Dropping a jar from the host (this machine):** `cp mymod.jar "$HOME/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/instances/Command Forge/minecraft/mods/"` — the sandbox already has read-write access to its own `~/.var/app` tree, so no `flatpak override` is needed; Prism picks the file up on the Mods tab (restart the instance). Alternative without touching `~/.var/app`: copy the jar to `~/Downloads` (read-only to the sandbox) and use Mods → Add File. The same `~/Downloads` trick is what the repo already uses for pack zips. "View Folder" / "Open Pack Folder" will keep failing from inside the sandbox for the same reason noted in CLAUDE.md.
- **Shipping a ready instance to kids:** (a) set up one instance (26.3 + Fabric Loader + Fabric API + the mod + the datapack world), (b) right-click → Export Instance → `.zip` (MultiMC/Prism format, self-contained: includes the mod jar and worlds; works offline once the Minecraft/Fabric libraries are cached or downloaded on first launch), or `.mrpack` (metadata only; recipient needs internet to pull jars from Modrinth/GitHub, and only Modrinth-hosted or GitHub-hosted jars are allowed if you later upload to Modrinth; a private unpublished jar must go in `overrides/mods/`), (c) kids: Add Instance → Import → pick the file (or a URL you host). The `.zip` route avoids publishing anything and avoids Modrinth's weeks-long review.

## Q5. Cost and maintenance: breakage across 26.1 → 26.2 → 26.3, Java knowledge, first-mod effort

### Takeaway
26.1 was a one-time cliff (Minecraft became unobfuscated, Fabric dropped Yarn, every mod needed recompiling, Java 25 became the floor); 26.2 and 26.3 have been ordinary minor ports where a tiny client mod mostly needs a version bump and rebuild, but each Minecraft release still requires a new jar because of hard `minecraft` version dependencies and small API renames (e.g. `Minecraft.screen` → `gui.screen()` in 26.2). Both loaders require JDK 25 and a Gradle project; the loaders themselves say "familiarity with Java" is a prerequisite. Nothing cited gives hour estimates — see inferences.

### Cited Findings
- Fabric for 26.1 (2026-03-14): "26.1 is the first version of Minecraft to not be obfuscated"; Yarn no longer officially supported, use Mojang mappings; "no mods from 1.21.11 or before will work without, at a minimum, recompilation"; toolchain Loom 1.15, Gradle 9.4.0, Java 25 minimum for the Gradle JVM, IntelliJ 2025.3+ for mixins, Fabric Loader 0.18.4; `fabric-loom` no longer remaps (`modImplementation` → `implementation`, `remapJar` → `jar`); Fabric API renamed to match official names (e.g. `ItemGroupEvents` → `CreativeModeTabEvents`), not backward compatible; removed `fabric` mod id (depend on `fabric-api`), `fabric-convention-tags-v1`, `fabric-loot-api-v2`, `HudRenderCallback` (→ `HudElementRegistry`); `ItemStack` can't be created before a world loads (`ItemStackTemplate`); raw OpenGL users must move to Blaze3D; 26.1 "expected to be the last version supporting only OpenGL". — [Fabric blog: Fabric for Minecraft 26.1](https://fabricmc.net/2026/03/14/261.html)
- Fabric migration tooling: Loom `migrateMappings` (semi-automated, no Kotlin) or the Ravel IntelliJ plugin; Fabric API renames "are not handled by the mapping migration tools" and need manual fixes. — [Fabric Docs: Migrating Mappings](https://docs.fabricmc.net/develop/porting/mappings/index); [Fabric Docs: Porting Fabric API](https://docs.fabricmc.net/de_de/develop/porting/fabric-api)
- Fabric 26.3 support exists today: `meta.fabricmc.net/v2/versions/game` lists `26.3` (stable: true) with 26.4 snapshots above it; `versions/loader/26.3` returns Fabric Loader 0.19.5 (stable) with intermediary pinned to `0.0.0` (i.e. no remapping); Modrinth lists Fabric API `0.162.0+26.3`, `0.161.0+26.3`, `0.160.7+26.3`. — [Fabric Meta API](https://meta.fabricmc.net/v2/versions/game); [Modrinth API: fabric-api versions](https://api.modrinth.com/v2/project/fabric-api/version?game_versions=%5B%2226.3%22%5D) (queried 2026-10-12)
- NeoForge 26.3 support exists: NeoForge Maven lists `26.3.0.72-beta` … `26.3.0.75-beta` and a non-beta `26.3.0.76`. — [NeoForge Maven versions API](https://maven.neoforged.net/api/maven/versions/releases/net/neoforged/neoforge) (queried 2026-10-12). Mid-2026 mod changelogs said NeoForge had "no stable (non-beta) build for 26.2 yet" at that time. — [Balm migration notes 26.2](https://balm.twelveiterations.com/migration/26.2)
- 26.2 breakage reported by mod authors: Java 25 required and 26.2 builds "aren't compatible with 26.1.x or 1.21.x"; `Minecraft.screen` field / `Minecraft.setScreen(Screen)` removed or relocated (replacements `Minecraft.gui.screen()` and `setScreenAndShow(Screen)`); `Gui` renamed `Hud`; `CriteriaTriggers` moved packages; `net.minecraft.util.Tuple` removed; Mojang sealed `Holder`; Architectury moved NeoForge-specific packages. — [Shulker Stuff changelog](https://www.curseforge.com/minecraft/mc-mods/shulker-stuff/files/8524622); [Tough As Nails 21.11.0.8](https://modrinth.com/mod/tough-as-nails/version/21.11.0.8); [Balm 26.2 migration](https://balm.twelveiterations.com/migration/26.2); [Architectury port 26.1→26.2](https://docs.architectury.dev/api/port-26.1-26.2)
- Version pinning in practice: BindCommands' `fabric.mod.json` depends on `"minecraft": ">=26.3-"` and its Modrinth page lists separate files per Minecraft version from 1.16.5 through 26.3 — i.e. one build per game version. — [GitHub: bind-cmd fabric.mod.json](https://github.com/devs-immortal/bind-cmd/blob/HEAD/src/main/resources/fabric.mod.json); [Modrinth: BindCommands](https://modrinth.com/mod/bindcommands)
- **Fabric getting started (26.2):** use the Fabric Template Mod Generator (mod name, package, Minecraft version; optional Kotlin / data generators) → zip → open in IDE; or clone `FabricMC/fabric-example-mod`. JDK 25 required ("To develop mods for Minecraft 26.1, you will need JDK 25"), IntelliJ IDEA recommended, VS Code listed as alternative. — [Fabric Docs: Creating a Project](https://docs.fabricmc.net/develop/getting-started/creating-a-project); [Fabric Docs: Setting Up](https://docs.fabricmc.net/develop/getting-started/setting-up)
- **NeoForge getting started (docs 26.1):** prerequisites "Familiarity with Java, including its object-oriented, generic, and functional features"; JDK 25, 64-bit; IntelliJ IDEA or Eclipse officially supported; Mod Generator on neoforged.net (choose ModDevGradle or NeoGradle); first Gradle import "downloads NeoForge dependencies, including Minecraft, and decompiles them. This can take up to an hour"; build with `gradlew build` → `build/libs/<archivesBaseName>-<version>.jar`; test with `gradlew runClient` / `runServer`; "always test in a dedicated server environment, including client-only mods". — [NeoForge Docs: Getting Started](https://docs.neoforged.net/docs/gettingstarted/)
- Mixins need bytecode awareness: "Mixin applies to bytecode rather than source code, so some Java bytecode knowledge helps"; Kotlin mixins unsupported without compat layers. — [Fabric Wiki: Mixin Introduction](https://wiki.fabricmc.net/tutorial:mixin_introduction)

### Inferences
- **Per-version maintenance for a 30-line client keybind mod:** each new Minecraft release (26.2 → 26.3 → 26.4) means bump `minecraft_version`, `loader_version`, `fabric_api_version` in `gradle.properties`, rebuild, fix any renamed symbol (the 26.2 `Minecraft.screen` → `gui.screen()` kind of thing), re-test, re-copy the jar to every instance. Expect 10–30 minutes per version when nothing in your tiny API surface moved, an hour or two when something did. Fabric's version pinning means the 26.2 jar will not load in 26.3 even if the code would compile — unlike this repo's data packs, which load in both via `min_format`/`max_format`.
- **Java knowledge for someone fluent in Python/C:** the minimal mod touches only classes, lambdas, static fields, and one annotation; the harder part is the toolchain (JDK 25, Gradle, IntelliJ or VS Code with the Java extension, the first Gradle sync downloading/decompiling Minecraft). Mixins can be avoided entirely for this scenario. A realistic first-mod budget is an afternoon to a day including toolchain setup, versus minutes for the rebuild afterwards.
- NeoForge lagged Fabric in reaching a stable 26.2 (beta-only for months per mod changelogs) and now has a single non-beta 26.3 build; for a project that wants same-day support for each release, Fabric is the lower-friction loader. Fabric also has far more precedent client-side keybind→command mods to copy from.
- Arch's `pacman` provides `java-27-openjdk` on this machine (`/usr/lib/jvm/java-27-openjdk/bin/javap` exists); Gradle/Loom want a JDK ≥25 for the Gradle JVM, so the system JDK suffices, and Prism's bundled `java-runtime-epsilon` (25) runs the game.

### Gaps
- No source gives quantitative "hours to first mod" figures; the estimates above are inferences.
- No Fabric or NeoForge blog post for 26.2 or 26.3 was found (searches returned Hyperledger Fabric noise and mod changelogs only); the 26.2 breakage list is assembled from third-party mod changelogs, not loader release notes.
- Whether Fabric Loader 0.19.5 is also the recommended loader for 26.2 instances (vs. 0.18.x) was not checked.

## Q6. Mod + data pack hybrid patterns

### Takeaway
Mods can ship a data pack inside the jar (the loader mounts `data/<namespace>/…` automatically, no `pack.mcmeta` needed on NeoForge), can register extra commands, predicates, and loot conditions for functions to call, and can act as "bridge" mods whose only job is to turn client input into vanilla commands/scoreboard changes. Existing keybind→command mods are configurable bridges; a purpose-built one that hard-codes `/trigger` would be a few dozen lines.

### Cited Findings
- NeoForge: "applies all mod data packs to each new world when it's created. These also cannot be disabled. Most data files can be overridden by higher-priority data packs"; mod assets are gathered into a built-in "Mod resources" pack at the bottom of the Selected Packs list; "For mods, NeoForge generates [`pack.mcmeta`] at runtime, so you usually don't need to write one"; data generation via `GatherDataEvent` writing to `src/generated/resources` (`PackMetadataGenerator` produces `pack.mcmeta`). — [NeoForge Docs: Resources](https://docs.neoforged.net/docs/resources/)
- Fabric: `src/main/resources` mirrors resource-pack layout (`assets/example-mod/textures/block/block.png`); Fabric's docs have a full Data Generation section (translations, models, advancements, enchantments, loot tables, recipes, tags, features) and "Resource Conditions". — [Fabric Docs: Project Structure](https://docs.fabricmc.net/develop/getting-started/project-structure); [Fabric Developer Guides index](https://docs.fabricmc.net/develop/)
- Mods exposing new commands: Fabric `CommandRegistrationCallback` with Brigadier `Commands.literal(...).then(...).executes(...)`, `.redirect(...)`, permission `requires(...)`. — [Fabric Docs: Creating Commands](https://docs.fabricmc.net/develop/commands/basics)
- Community data-pack-loader mods: *Global Packs* (drop packs in a generated `/datapacks/` folder, auto-loaded into every new world), *Datapack Installer* (Fabric; copies packs from its own folder into the world's datapacks folder at server start; on clients they appear in the world-creation and pause-menu selectors; cannot handle feature-flag packs), *Embedded Assets* (Fabric; loads resource packs embedded inside data packs, `/embedded_assets` command for priority). — [Global Packs](https://www.mado-hosting.com/en/minecraft-mods/globalpacks); [Datapack Installer](https://www.mado-hosting.com/minecraft-mods/dp-installer); [Embedded Assets (GitHub)](https://github.com/Minenash/Embedded-Assets)
- Bridge mods making key presses visible to the server (all configurable key→chat/command; see Q2 for details): BindCommands (through 26.3; 613K downloads; optional server component only syncs server-defined bindings to clients via a custom payload — a real-world example of a client-side feature with an *optional* server half), d1ezz9's Chat Keybinds (26.1.2), ChatMacro (1.21.11), AnyBind, Saved Commands, KeyBinder, Auto Command, Easy Keybinds. — [Modrinth: BindCommands](https://modrinth.com/mod/bindcommands); [GitHub: bind-cmd](https://github.com/devs-immortal/bind-cmd); [d1ezz9's Chat Keybinds](https://modrinth.com/mod/d1ezz9s-chat-keybinds); [ChatMacro](https://modrinth.com/mod/chatmakro); [AnyBind](https://www.curseforge.com/minecraft/mc-mods/anybind)
- Fabric Resource Conditions let JSON data (recipes, loot, etc.) load only when conditions (e.g. a mod is present) hold — listed under Miscellaneous in the developer guide. — [Fabric Developer Guides index](https://docs.fabricmc.net/develop/)

### Inferences
- **Lowest-effort hybrid for Command Forge:** keep the entire tutorial as the existing 26.3 data pack; add one client-only Fabric jar that maps N (and any other keys) to `trigger <objective>` commands. Functions see the press as a scoreboard change next tick. No server component, no mixins, works on vanilla servers, and the data pack still loads without the mod (the key just does nothing).
- **Off-the-shelf alternative with zero Java:** install BindCommands (26.3 build) + Mod Menu + Fabric API in the Command Forge instance and configure N → `/trigger tut_key_n`; the mod even supports server-pushed bindings if the class ever runs on a shared server. Cost: three third-party jars, a config GUI kids could change, and you depend on someone else's update cadence (their description still said "up to 26.2" while files for 26.3 existed).
- **Bundling the data pack inside the mod** is possible on both loaders (auto-mounted `data/` folder) and would let one jar carry tutorial + keybinds, but it changes the install story (`mods/` instead of `saves/<world>/datapacks/`), requires Fabric/NeoForge on every machine, and loses the "one zip works in 26.2 and 26.3" property — not worth it for this project unless mods are adopted anyway.

### Gaps
- Fabric's docs page explicitly stating that a mod jar's `data/` folder is auto-loaded as a data pack was not located (Project Structure covers only `assets/`); the NeoForge statement is primary, the Fabric equivalent is inferred from the template's resource-pack-mirroring layout and the community mods listed.
- No Modrinth mod was found that is *purpose-built* to write a scoreboard/`/trigger` for data packs (all found mods are generic key→chat/command macros). Searching Modrinth with terms like "trigger", "scoreboard keybind", "datapack input" was not done within the call budget.
- Mod-provided custom predicate/loot-condition types callable from data pack JSON were not researched beyond the command API.
