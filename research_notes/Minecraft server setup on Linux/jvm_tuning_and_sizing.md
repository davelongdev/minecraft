# JVM tuning, resource sizing, and server.properties for small Minecraft Java 26.3 Fabric servers

Scope: 3–6 small instances (10–20 players total) on one i5-13400 / 62 GB Linux box, October 2026, Minecraft Java 26.3 on Java 25. Where a source is written for large Paper survival servers, that is flagged. One finding below is a direct experiment run on this machine (2026-10-18), marked "local test".

## 1. Java 25 and Minecraft 26.x: required version, newer JDKs, 26.x JVM notes

### Takeaway
Mojang's own version metadata requires Java 25 for 26.1, 26.2, and 26.3 (1.21.11 was the last Java 21 release). The 26.3 server jar does start on JDK 27 (local test: `--initSettings` ran cleanly apart from `sun.misc.Unsafe` deprecation warnings), but no source documents Java 27 as supported, and Fabric Loader/Mixin compatibility with 27 is unverified, so run Java 25 (the version Mojang bundles) for anything that has to work on class night. The relevant JDK-level changes since the Java 21 era: ZGC is generational-only from JDK 24, and compact object headers became a supported product flag in JDK 25.

### Cited Findings
- Mojang's version manifest (`piston-meta.mojang.com`, read directly 2026-10-18): `26.3` → `javaVersion: {component: java-runtime-epsilon, majorVersion: 25}`; `26.1` → majorVersion 25; `1.21.11` → `java-runtime-delta`, majorVersion 21. 26.3 released 2026-09-15, 26.2 on 2026-06-16, 26.1 on 2026-03-24; latest snapshot is `26.4-snapshot-4`. — [Mojang version manifest](https://piston-meta.mojang.com/mc/game/version_manifest_v2.json) and [26.3 version JSON](https://piston-meta.mojang.com/v1/packages/11f1aefe473eefba0af62e3286c33b692807b2eb/26.3.json)
- The minecraft.wiki 26.3 article's infobox lists "Minimum Java version: Java SE 25"; release date September 15, 2026; protocol 777, data version 5023. — [Java Edition 26.3](https://minecraft.wiki/w/Java_Edition_26.3)
- 26.1 "is the first version to require Java 25. If your server currently runs Java 21 or Java 17, you must upgrade the JRE before installing 26.1." and "Older Minecraft versions generally run fine on a newer Java than they were built for... The reverse is fatal" (hosting-provider guides; consistent with the manifest). — [GameServerKings](https://www.gameserverkings.com/knowledge-base/minecraft/updating-your-server-version/), [Wepwawet Java version table](https://docs.wepwawet.net/games/minecraft/setup/java-version)
- **Local test (2026-10-18, this machine):** `openjdk version "27" 2026-09-15`; `java -jar server.jar --initSettings --nogui` on the official 26.3 `server.jar` (62,294,556 bytes, sha `33680f5f…`) exited 0 and wrote `server.properties` + `eula.txt`. JDK 27 printed `WARNING: A terminally deprecated method in sun.misc.Unsafe has been called … by org.joml.MemUtil$MemUtilUnsafe (joml-1.10.9.jar) … sun.misc.Unsafe::objectFieldOffset will be removed in a future release` and `WARNING: Restricted methods will be blocked in a future release unless native access is enabled`. This proves the bundler and server main class load on 27; it does not prove a full tick loop or Fabric Loader works on 27. — local run, server jar from [piston-data](https://piston-data.mojang.com/v1/objects/33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c/server.jar)
- Every 26.3 server guide found names Java 25 only; none mentions Java 27. Fabric Loader 0.19.5 was the recommended loader at 26.3 release; Paper 26.3 and NeoForge 26.3 were still beta/experimental as of late September–early October 2026. — [TroubleChute 26.3 Fabric server guide](https://hub.tcno.co/games/minecraft/26.3/server/fabric/), [Space-Node 26.3 update guide](https://space-node.net/blog/minecraft-26-3-server-update-guide-2026)
- JEP 490 (JDK 24, delivered): non-generational ZGC removed; `-XX:+UseZGC` alone gives generational ZGC; `-XX:+ZGenerational` or `-XX:-ZGenerational` both still run generational ZGC and print an obsolete-option warning; the option will later be removed entirely, at which point "the HotSpot JVM … will refuse to start". — [JEP 490](https://openjdk.org/jeps/490)
- JEP 519 (JDK 25): compact object headers promoted from experimental to product feature; flag is now plain `-XX:+UseCompactObjectHeaders` (no `UnlockExperimentalVMOptions`); opt-in, not default ("not a goal to make compact object headers be the default"); cited results: SPECjbb2015 ~22% less heap and 8% less CPU in one setting, ~15% fewer GCs with G1/Parallel in another, ~10% less run time on a parallel JSON benchmark. Oracle's JDK 25 release notes list JEP 519 the same way. — [JEP 519](https://openjdk.org/jeps/519), [Oracle JDK 25 release notes](https://www.oracle.com/java/technologies/javase/25-relnote-issues.html)
- 1.21.2's infobox lists minimum Java SE 21 and its changelog says "Improved server performance when the render distance is high" and reduced impact of chunk loading/generation. — [Java Edition 1.21.2](https://minecraft.wiki/w/Java_Edition_1.21.2)

### Inferences
- Because Mojang's `javaVersion` for 26.3 is 25 and that is what the launcher bundles (`java-runtime-epsilon`), Java 25 is the only configuration Mojang tests. JDK 27's `Unsafe` warnings against JOML suggest a future JDK will break the unmodified 26.3 jar; running 25 avoids that cliff.
- `-XX:+ZGenerational` strings copied from 2024–2025 guides are harmless on Java 25 (warning only) but should be dropped now so they don't become a hard start failure later.
- `-XX:+UseCompactObjectHeaders` is a low-risk opt-in on Java 25 that should cut heap for Minecraft's object-heavy workload (block states, NBT, chunk sections); no Minecraft-specific measurement was found, so verify with `/spark gc` before and after.

### Gaps
- No source documents Fabric Loader 0.19.x or Mixin on Java 27; the 2019 Fabric changelog is the only Java-version-detection note found. Test on a throwaway instance if 27 is ever wanted.
- No Mojang statement on virtual threads or any other 26.x-specific JVM use was found; the 26.3 changelog's performance items (faster structure location and chunk generation) are game-level, not JVM-level.

## 2. Flags: Aikar's vs ZGC vs default G1 on Java 25 for 2–4 GB heaps; Xms=Xmx; AlwaysPreTouch; GraalVM

### Takeaway
For 2–4 GB heaps on Java 25, the sourced consensus is still G1: Aikar's flags (Paper's canonical string) or even stock G1 are "near optimal" at small heaps, while ZGC's advocates themselves only recommend it from 16 GB (one source) or 32 GB and >10 cores (MeowIce). Keep `-Xms` = `-Xmx` with `-XX:+AlwaysPreTouch` only if you accept that each instance commits its full heap at boot (fine on 62 GB). GraalVM gains are real but modest in the one controlled test (~17.4 → ~20 TPS on a modpack) and come from a single-author benchmark otherwise; not worth the extra moving parts for a classroom.

### Cited Findings
- Paper's current canonical Aikar string: `java -Xms10G -Xmx10G -XX:+UseG1GC -XX:+ParallelRefProcEnabled -XX:MaxGCPauseMillis=200 -XX:+UnlockExperimentalVMOptions -XX:+DisableExplicitGC -XX:+AlwaysPreTouch -XX:G1NewSizePercent=30 -XX:G1MaxNewSizePercent=40 -XX:G1HeapRegionSize=8M -XX:G1ReservePercent=20 -XX:G1HeapWastePercent=5 -XX:G1MixedGCCountTarget=4 -XX:InitiatingHeapOccupancyPercent=15 -XX:G1MixedGCLiveThresholdPercent=90 -XX:G1RSetUpdatingPauseTimePercent=5 -XX:SurvivorRatio=32 -XX:+PerfDisableSharedMem -XX:MaxTenuringThreshold=1 -Dusing.aikars.flags=https://mcflags.emc.gs -Daikars.new.flags=true -jar paper.jar --nogui`. Explanations on the page: matching Xms/Xmx "avoids unused reserved memory, since G1 uses the heap it's given"; a larger young gen because Minecraft allocates mostly short-lived objects; `MaxGCPauseMillis=200` is a target, not a cap; `DisableExplicitGC` blocks plugin-triggered full GCs; `AlwaysPreTouch` "reserves and touches memory at startup" and is needed for transparent huge pages; THP is "controversial", only with AlwaysPreTouch, "effects haven't been measured". GC logging (Java 11+): `-Xlog:gc*:logs/gc.log:time,uptime:filecount=5,filesize=1M`, "does not hurt your performance and can be left on at all times". — [PaperMC: Aikar's flags](https://docs.papermc.io/paper/aikars-flags)
- Same page, memory guidance (aimed at Paper survival servers, flagged): "We recommend using at least 6-10GB, no matter how few players!"; reduce Xms/Xmx by ~1000–1500 MB below the host's figure (8 GB host → 6500M); "Do not allocate all of your available memory on a shared host!"; more memory stops helping past a point. The older 1.18 page: "if your host says you have 8000M memory, DO NOT USE 8000M! Minecraft (and Java) needs additional memory on top of that Xmx parameter." — [PaperMC Aikar's flags (1.18 archive)](https://docs.papermc.io/paper/1.18/aikars-flags)
- Paper docs mention neither ZGC nor GraalVM. — [PaperMC: Aikar's flags](https://docs.papermc.io/paper/aikars-flags)
- A 2026 GC comparison blog (single-author, cites r/admincraft and a GitHub comparison it does not link): ZGC "stable since JDK 21"; recommends ZGC mainly at 16 GB+, "modest" gain at 8 GB, "G1 is near optimal at 4–12 GB"; ZGC uses ~10–20% more memory than G1 and wants ≥4 free cores; ZGC flattens p99 latency, G1 keeps a slight average-throughput edge on small heaps; it claims generational became default on Java 25 (wrong release: JEP 490 says JDK 24). — [mineguard.pro ZGC vs G1GC](https://mineguard.pro/en/blog/zgc-vs-g1gc-minecraft-java-21-benchmark); a competing hosting blog claims generational ZGC default "in Java 21+", also inconsistent with JEP 490 — [Space-Node ZGC vs G1 guide](https://space-node.net/blog/minecraft-zgc-vs-g1gc-garbage-collector-guide-2026)
- MeowIce's flags (README): tested "Java 25+, GraalVM JVM, Linux, Minecraft 1.21+, x86_64"; two sets, G1GC "for heaps under 32GB" opening `--add-modules=jdk.incubator.vector -XX:+UseG1GC -XX:MaxGCPauseMillis=200 …`, and ZGC "for 32GB+ heaps with many cores" opening `--add-modules=jdk.incubator.vector -XX:+UseZGC -XX:-ZProactive -XX:SoftMaxHeapSize=$((Memory - 2048))M …`, ZGC warned against below 8–10 cores; both end in GraalVM-only `-Djdk.graal.CompilerConfiguration=enterprise` etc.; ARM64 must drop the `-XX:+UseXmm*`/`-XX:UseAVX=2` flags. Benchmark: one Leaf 1.21.8 server, 6 GB (`-Xms6G -Xmx6G`), 10700K, ~20 MSPT better than Aikar's, at 1,000 simulated players ~30–35 MSPT vs Aikar's ~90–95 MSPT; the author runs an optimization service, the benchmark used a GraalJDK 24 image and a flag set differing from the README, and calls Aikar's flags "almost a placebo effect" (opinion). — [MeowIce/meowice-flags](https://github.com/MeowIce/meowice-flags)
- The only controlled GraalVM test found: ATM6 modpack world, entity spawning off, 144 chunks loaded: ~17.4 TPS on OpenJDK vs ~20.0 on GraalVM, memory ~2.7 GB vs ~2.4 GB; author notes the map was too light to push GraalVM below 20 TPS. A German guide's "5–15% better" figure cites no benchmark. — [tallua/minecraft-graalvm-benchmark](https://github.com/tallua/minecraft-graalvm-benchmark/blob/main/README.md), [mineguard flags guide](https://mineguard.pro/blog/minecraft-server-java-flags-optimization)
- The docker-minecraft-server docs: their Aikar option "adjusts flags automatically at 12G or more" and MeowIce's are "an updated set based on Aikar's flags with optimizations for Java 17 and above". — [itzg docker-minecraft-server JVM options](https://mintlify.com/itzg/docker-minecraft-server/configuration/jvm-options)
- A 2026 flag-generator page says its Aikar-style G1 line was "last verified for Minecraft 26.2"; a Spanish guide calls stock G1GC "la config mínima segura — funciona en todo (Mojang, Forge, NeoForge, Fabric)". — [Craftdex server flags](https://craftdex.net/es/tools/server-flags), [mineguard flags (es)](https://mineguard.pro/es/blog/minecraft-server-java-flags-optimization)
- The 12 GB+ variant of Aikar's flags (`G1NewSizePercent=40 G1MaxNewSizePercent=50 G1HeapRegionSize=16M G1ReservePercent=15 InitiatingHeapOccupancyPercent=20`) is referenced by the docker image's "12G or more" behaviour; the current Paper page itself no longer shows the two-tier table. — [itzg JVM options](https://mintlify.com/itzg/docker-minecraft-server/configuration/jvm-options)

### Inferences
- Copy-paste candidates for a 3 GB Fabric instance on Java 25 (constructed from the sources above; the first is Aikar's string unchanged apart from heap and jar name, the second is a minimal modern alternative using JDK 25 features; the third is only for experimentation):
  - Aikar (safe default): `java -Xms3G -Xmx3G -XX:+UseG1GC -XX:+ParallelRefProcEnabled -XX:MaxGCPauseMillis=200 -XX:+UnlockExperimentalVMOptions -XX:+DisableExplicitGC -XX:+AlwaysPreTouch -XX:G1NewSizePercent=30 -XX:G1MaxNewSizePercent=40 -XX:G1HeapRegionSize=8M -XX:G1ReservePercent=20 -XX:G1HeapWastePercent=5 -XX:G1MixedGCCountTarget=4 -XX:InitiatingHeapOccupancyPercent=15 -XX:G1MixedGCLiveThresholdPercent=90 -XX:G1RSetUpdatingPauseTimePercent=5 -XX:SurvivorRatio=32 -XX:+PerfDisableSharedMem -XX:MaxTenuringThreshold=1 -Dusing.aikars.flags=https://mcflags.emc.gs -Daikars.new.flags=true -jar fabric-server-launch.jar --nogui`
  - Minimal G1 + JDK 25 extras: `java -Xms3G -Xmx3G -XX:+UseG1GC -XX:MaxGCPauseMillis=100 -XX:+UseCompactObjectHeaders -XX:+DisableExplicitGC -XX:+AlwaysPreTouch -Xlog:gc*:logs/gc.log:time,uptime:filecount=5,filesize=1M -jar fabric-server-launch.jar --nogui`
  - Generational ZGC (experiment only at this heap size, per every ZGC source): `java -Xms3G -Xmx3G -XX:+UseZGC -XX:+UseCompactObjectHeaders -XX:+AlwaysPreTouch -jar fabric-server-launch.jar --nogui` (no `-XX:+ZGenerational` on 24+).
- Whether `-XX:+UseCompactObjectHeaders` combines with Aikar's `G1HeapRegionSize=8M` etc. is untested in any source; it is a layout flag independent of GC tuning, so it should compose, but check `latest.log` for JVM warnings on first start.
- `-Xms`=`-Xmx` + `AlwaysPreTouch` costs nothing on this box: 6 × 3 GB = 18 GB committed out of 62 GB. On a shared or small host the same flags would be the first thing to drop, since pre-touching makes every idle instance hold its full heap. `pause-when-empty-seconds` (section 5) does not release heap, so idle instances still hold what they pre-touched.
- With 10 cores shared by up to 6 JVMs, ZGC's concurrent threads would compete with other instances' main threads; this is the practical reason (beyond heap size) to stay on G1 here.

### Gaps
- No independent, reproducible 2026 benchmark comparing Aikar/stock G1/ZGC/MeowIce on a 2–4 GB heap and Java 25; all comparisons found are single-author or vendor material.
- No measurement of `-XX:+UseCompactObjectHeaders` on Minecraft specifically.
- Fabric publishes no official JVM-flag recommendation (searches returned only hosting guides).

## 3. Memory per instance and how many fit in 62 GB

### Takeaway
Mojang-community sizing says a vanilla-like server needs ~1 GB baseline plus ~50–100 MB per player, with 2 GB "recommended" for 5–10 players and 4 GB "best" for 10+ (view distance ≤ 10, fresh world); hosting guides treat 2 GB as the floor and 4 GB as comfortable for a Fabric server with a few mods. Six instances at 3 GB heap (~4 GB RSS each with off-heap) use ~24 GB of 62 GB, so memory is not the constraint; CPU single-thread time per instance and save-time disk I/O are. Beyond what the world needs, more heap doesn't make a server faster, it only lengthens the interval between (and the size of) old-gen collections.

### Cited Findings
- minecraft.wiki Server/Requirements (LAN party table; "assume a draw distance no higher than 10 and a new world"): Minimum 1–4 players 1 GB; Recommended 5–10 players 2 GB; Best 10+ players 4 GB, i5-4690/Ryzen 5 1600; baseline `-Xmn 128M -Xmx 1G`; "a player object takes roughly 50 to 100 MB, but the server often allocates more per player"; "Single-core performance matters most, and the server typically uses up to three cores"; large worlds, advanced redstone and mob grinders "can significantly increase RAM and CPU needs". — [Server/Requirements](https://minecraft.wiki/w/Server/Requirements)
- minecraft.wiki Server/Requirements/Dedicated, Unix console tiers (same draw-distance-10 / new-world assumptions, "can easily more than double" for big worlds, OS memory extra): 1–5 players 512 MB, 5–10 players 1 GB, 10–15 players 3 GB, 15–20 players 5 GB, 20+ players 6 GB; "1 player ~ 50-100 MB of RAM". (These tables are old: CPUs listed are Pentium 4 through Ryzen 3/5.) — [Server/Requirements/Dedicated](https://minecraft.wiki/w/Server/Requirements/Dedicated)
- Hosting guides: 2 GB "Up to ~10 players, not recommended for modded"; 4 GB for ~10–15 players on Paper/Spigot; one host lists Fabric "Min. RAM 2 GB, Empf. RAM 4 GB" and 5–10 players at 4 GB, adding that with performance mods "you can host even more players on less RAM than on Vanilla"; another suggests 4–6 GB for Fabric with mods at 5–15 players and 100–300 MB per player for modded servers. — [Shockbyte RAM guide](https://shockbyte.com/help/knowledgebase/articles/how-much-ram-do-i-need-for-a-minecraft-server), [mine-hoster Fabric](https://mine-hoster.de/en/rent-minecraft/fabric), [mineguard RAM guide](https://mineguard.pro/en/blog/how-much-ram-minecraft-server)
- A hosting doc estimates ~200 MB of RAM per player at view distance 10, and two sources say view distance mainly costs RAM and bandwidth rather than TPS/MSPT. — [Foliumhosting view distance](https://docs.foliumhosting.net/games/minecraft/configuration/view-distance), [Nodecraft view distance](https://nodecraft.com/support/games/minecraft/configuring-view-distance-on-a-minecraft-server)
- Paper: "more memory stops improving performance past a certain point" and leave 1000–1500 MB below the host figure for JVM overhead and the OS (large-server context). — [PaperMC Aikar's flags](https://docs.papermc.io/paper/aikars-flags)
- FerriteCore's "10–12%" memory saving comes from a single informal 15-player test; "up to 45%" is a vendor claim. — [minecraft.how FerriteCore](https://minecraft.how/es/blog/articulo/ferritecore-minecraft-server-optimization), [WiseHosting optimization mods](https://wisehosting.com/blog/10-best-minecraft-server-optimization-mods)
- Server-side Fabric performance mods that recur across curated lists: Lithium (game logic), FerriteCore (memory), Krypton (networking), ServerCore (mob/breeding caps, async login, entity limits), ModernFix, C2ME, Very Many Players, Noisium, ScalableLux; vendor percentages ("40% less CPU", "30–50%") are unsourced. No list was 26.3-specific; check each Modrinth page for a 26.3 build. — [xgamingserver Fabric performance guide](https://xgamingserver.com/docs/minecraft/fabric-optimize), [Modrinth server-optimization collection](https://modrinth.com/collection/Jz9ziBbs)

### Inferences
- Sizing for this project (void/superflat worlds, datapacks, 3–6 players per instance): 2 GB heap is in the "recommended" wiki tier and would work; 3 GB gives GC headroom for mini-game packs that spawn many entities/items and for `/reload`s that rebuild registries; 4 GB only if a world grows (terrain exploration) or a content mod is added. Expect RSS ≈ heap + 0.5–1 GB (metaspace, code cache, Netty direct buffers, chunk cache), so plan ~4 GB per instance.
- 62 GB therefore fits 6 instances × 4 GB = 24 GB with ~35 GB left for the OS page cache (helps region-file reads/writes) and Prism/desktop use. Even 10 instances would fit on memory; the binding limits are CPU (one busy main thread per instance, section 4) and disk writes during autosave (`sync-chunk-writes=true` default, section 5).
- Oversizing heaps on G1 makes individual old-gen pauses longer when they finally happen; the Paper guidance to stop at "what the world needs" applies with more force to six co-located JVMs that also compete for L2/L3 cache.

### Gaps
- No published measurement of heap used by a 26.x Fabric server with a handful of server-side mods and datapacks at 5–10 players; the only route is `/spark health` or `-Xlog:gc*` on the real instances during a session.
- No source quantifies disk I/O during autosave for small worlds; it is negligible for void worlds (a few region files) but unmeasured.

## 4. CPU: main thread vs async workers, how many instances an i5-13400 carries, P-core pinning, hybrid scheduling, governor

### Takeaway
Each Minecraft server is one latency-critical main thread plus helper threads (Netty, chunk workers, GC), and the wiki says a server "typically uses up to three cores" with single-core speed mattering most; community experience is that busy servers use close to two cores. The i5-13400 has 6 P-cores (4.6 GHz turbo, hyperthreaded, 12 threads) + 4 E-cores (3.3 GHz), so six instances is the natural ceiling with one P-core per main thread. Linux has had documented trouble placing single-threaded work on P-cores on Alder/Raptor Lake (kernel bug 218195; a cluster-scheduling fix only targets Linux 7.3, this box runs 7.2.9), so pinning the instances' main threads to P-cores via systemd `CPUAffinity` is justified, and E-core-only placement would cost roughly a quarter of single-thread speed.

### Cited Findings
- i5-13400: 10 cores / 16 threads, 6 P-cores (2.5 GHz base, 4.6 GHz max turbo) + 4 E-cores (1.8 GHz base, 3.3 GHz max turbo), 20 MB L3, 9.5 MB L2, 65 W base / 148 W max turbo (one datasheet says 154 W), UHD 730. — [mini-itx.com i5-13400](https://www.mini-itx.com/~i5-13400), [Advantech 96MPI-13400 datasheet](https://advdownload.advantech.com/productfile/PIS/96MPI-13400-10E/file/96MPI-13400-10E_datasheet20231003104319.pdf)
- "Single-core performance matters most, and the server typically uses up to three cores." — [Server/Requirements](https://minecraft.wiki/w/Server/Requirements)
- A Slackware how-to reports a Java Minecraft server can use close to two full cores on a busy world and that pinning with `taskset` is common; Feed-the-Beast forum users ran several modded servers on one multi-core box without pinning, noting the game thread is single-threaded while GC and other JVM work use other cores. — [Slackware processor affinity](https://docs.slackware.com/howtos:hardware:processor_affinity), [FTB forum thread](https://forum.feed-the-beast.com/threads/have-minecraft-server-using-a-specific-cpu-core.106678/)
- systemd services accept a `CPUAffinity=` directive (drop-in file, `daemon-reload`, restart); verify with `taskset -cp <pid>`; pinning improves cache locality and keeps other processes off reserved cores. — [OneUptime taskset guide](https://oneuptime.com/blog/post/2026-03-02-how-to-set-cpu-affinity-for-processes-with-taskset-on-ubuntu/markdown)
- Kernel Bugzilla 218195 (late 2023, Alder Lake i7-1260P): from Linux 6.6 the scheduler placed single-threaded work on E-cores; reporter could force a P-core with `taskset` but called manual scheduling impractical. — [kernel.org bug 218195](https://bugzilla.kernel.org/show_bug.cgi?id=218195), [LKML thread](https://lkml.iu.edu/hypermail/linux/kernel/2312.2/01953.html)
- Intel's cluster-aware scheduling fix for hybrid CPUs targets the Linux 7.3 merge window (August 2026 coverage); the cover letter: "on partially busy systems, the remaining tasks are supposed to be evenly spread among the small-CPU clusters, but this does not happen"; tested on Alder Lake, Lunar Lake, Panther Lake (Raptor Lake not named, but the i5-13400 shares Alder Lake's Golden Cove/Gracemont design in most SKUs). — [Phoronix: Linux 7.3 hybrid cluster scheduling](https://phoronix.com/news/Linux-7.3-Better-Intel-Hybrid), [Phoronix: Linux 7.3 scheduler](https://www.phoronix.com/news/Linux-7.3-Scheduler)
- Earlier Intel hybrid-placement work: Linux 6.5 load-balancing improvements, mid-2024 asymmetric-capacity patches. — [Phoronix Linux 6.5](https://www.phoronix.com/news/Linux-6.5-Intel-Hybrid-Sched), [Phoronix mid-2024](https://www.phoronix.com/news/Intel-Linux-Mid-2024-Hybrid)
- A Panther Lake test measured an E-core at 80.3% of a P-core's SHA-256 throughput and concluded wrong-class placement cuts single-thread performance by roughly a quarter; a NUC 13 Pro (Raptor Lake) article uses `taskset -c 0-7` for its P-cores and notes numbering varies by CPU. — [LinuxLinks Panther Lake scheduling](https://www.linuxlinks.com/minisforum-m2-does-linux-schedule-panther-lake-correctly/9/), [LinuxLinks NUC 13 Pro](https://linuxlinks.com/intel-nuc-13-pro-mini-pc-running-linux-p-cores-e-cores/4)

### Inferences
- Capacity: 3–4 instances with 3–6 kids each is comfortable; 6 instances is the ceiling where every main thread can own a P-core while Netty/chunk/GC threads share the P-core siblings and the E-cores. Beyond that, instances start contending for P-cores and tick times rise together under load.
- A workable layout (verify CPU numbering first with `lscpu -e` or `cat /sys/devices/system/cpu/cpu*/topology/core_cpus_list`; on most 13400 boards CPUs 0–11 are the six hyperthreaded P-cores and 12–15 the E-cores): per instance `CPUAffinity=0 1` … `CPUAffinity=10 11` (one P-core + sibling each) or, simpler and still an improvement, `CPUAffinity=0-11` for all instances to keep them off E-cores and let the scheduler balance within the P-cores. systemd unit sketch:
  ```
  [Service]
  WorkingDirectory=/srv/mc/one-block
  CPUAffinity=0-11
  Nice=-5
  ExecStart=/usr/lib/jvm/java-25-openjdk/bin/java -Xms3G -Xmx3G ... -jar fabric-server-launch.jar --nogui
  ```
  (Java 25 path per Arch's `jdk25-openjdk` package as installed on this box; confirm with `archlinux-java status`.)
- Governor: the Arch wiki page could not be fetched (bot protection), so from general knowledge only: Arch on Intel uses `intel_pstate` in active/HWP mode with `powersave` as default governor; `cpupower frequency-set -g performance` (persist via `cpupower.service`) or `energy_performance_preference=performance` raises ramp-up for the bursty 50 ms tick pattern. Unsourced here; treat as a thing to verify, not a finding.
- The 7.2.9 kernel on this box predates the 7.3 cluster-scheduling fix, so the pinning advice applies as of today; re-evaluate when 7.3 lands (Arch rolling will pick it up within weeks of release).

### Gaps
- No Minecraft-specific benchmark of E-core vs P-core placement or of pinning several instances; the ~25% figure is a generic single-thread comparison on a different (Panther Lake) generation.
- Raptor Lake is not named in the 2026 scheduler-fix coverage; whether the i5-13400 is affected by the exact cluster bug is unconfirmed.
- The Arch wiki `CPU_frequency_scaling` page was blocked by Anubis; governor defaults above are unsourced.

## 5. server.properties for a class

### Takeaway
26.3's real defaults (captured on this machine with `--initSettings`): `white-list=true`, `enforce-whitelist=false`, `online-mode=true`, `enforce-secure-profile=true`, `view-distance=10`, `simulation-distance=10`, `max-players=20`, `spawn-protection=16`, `function-permission-level=2`, `op-permission-level=4`, `max-tick-time=60000`, `network-compression-threshold=256`, `sync-chunk-writes=true`, `entity-broadcast-range-percentage=100`, `rate-limit=0`, `player-idle-timeout=0`, `pause-when-empty-seconds=60`, plus the management-server keys (off). `enable-command-block` no longer exists (it is the `enableCommandBlocks` gamerule since 25w35a). For a kids' LAN/WAN class: whitelist on with `enforce-whitelist=true`, `online-mode=true` (keep secure profile unless offline accounts force otherwise), `spawn-protection=0` (it blocks non-ops from building at spawn), `simulation-distance` 6–8 and `view-distance` 8–10, `max-players` at the actual class size, `player-idle-timeout` 0, `pause-when-empty-seconds` left at 60 for idle instances (set 0 if a datapack must keep ticking with nobody online).

  enforce-whitelist=true

## 6. Bandwidth per player and uplink sizing

### Takeaway
No measured per-player figure exists in any source found (the one 2026 article titled "bandwidth per player" contains none). The only numeric guidance is the minecraft.wiki dedicated table's totals at draw distance ≤ 10: 8 Mbit/s up for 10–15 players, 14 Mbit/s up for 15–20, 30 Mbit/s for 20+, i.e. roughly 0.7–1 Mbit/s upstream per player, dominated by chunk sends. For 10–20 kids on a studio uplink, budget 15–30 Mbit/s upstream with view-distance 8–10 and far less once players stop moving.

### Cited Findings
- Dedicated-server table (Unix console): 1–5 players 3 Mbit/s up / 2 down; 5–10 players 6 up / 3 down; 10–15 players 8 up / 4 down; 15–20 players 14 up / 7 down; 20+ players 30 up / 15 down; assumes draw distance ≤ 10 and a new world; "The server _will_ miss ticks" at the minimum tier. — [Server/Requirements/Dedicated](https://minecraft.wiki/w/Server/Requirements/Dedicated)
- The LAN-party page gives no bandwidth numbers, only "a low-ping connection such as DSL or cable is recommended". — [Server/Requirements](https://minecraft.wiki/w/Server/Requirements)
- Space-Node's "bandwidth per player 2026" article contains no per-player kbps/Mbps figures and no measurement method (only its own VPS plan limits). — [Space-Node bandwidth article](https://space-node.net/blog/minecraft-server-bandwidth-per-player-2026)
- View distance is "a cap on how much chunk data the server sends each player"; chunk count grows with the square of the radius (≈441 chunks at 10 vs ≈289 at 8). — [Nodecraft view distance](https://nodecraft.com/support/games/minecraft/configuring-view-distance-on-a-minecraft-server), [xgamingserver render distance](https://xgamingserver.com/docs/minecraft/render-distance)
- `network-compression-threshold` default 256 bytes; −1 disables compression. — [Server.properties](https://minecraft.wiki/w/Server.properties)

### Inferences
- The wiki totals imply ~0.7–1.0 Mbit/s upstream per player at vd ≤ 10 during exploration; void/superflat mini-game worlds send far smaller chunk packets (mostly air), so real usage for these packs will be well under the table. A 20 Mbit/s upstream budget covers 20 kids with margin; a typical 10–35 Mbit/s residential/cable uplink is enough, and on the studio LAN bandwidth is a non-issue.
- Dropping view-distance from 10 to 8 cuts chunk traffic ~35% (441 → 289 chunks per player on first load); it is the cheapest bandwidth lever and has no gameplay cost on 12×12 islands or a 31-block course.
- Measure rather than guess: `/spark health --network` reports per-interface throughput on the running server, and `vnstat`/`iftop` on the host give the total across instances.

### Gaps
- No 2024–2026 measured per-player bandwidth data at specific view distances was found in docs, admincraft, or vendor posts; the wiki totals are undated and based on old hardware tiers.

## 7. Datapack-heavy servers: per-tick function cost and profiling

### Takeaway
The vanilla tools are `/debug start`/`/debug stop` (permission 3; `stop` returns average TPS, and the old `profile-results-*.txt` dump is documented as removed) and `/debug function <name>`, which runs a function while writing a `debug-trace-*.txt` with every command, message, return value and nested function size, so you can count exactly what a per-tick loop executes. For sustained lag hunting on Fabric, spark (`spark-*-fabric.jar` in `mods/`, needs Fabric API) with `/spark profiler start --only-ticks-over <ms>` or `--timeout 120` and `/spark tickmonitor` is the standard; look under `MinecraftServer.tickChildren` for function/command-execution frames.

### Cited Findings
- `/debug start` "Starts a new debug time profiler session", fails if already running; `/debug stop` returns average TPS as its result value; the `profile-results-yyyy-MM-dd_HH.mm.ss.txt` in `.minecraft/debug` is listed as removed content; `/debug function <name|#tag>` behaves like `/function` but writes `debug-trace-yyyy-MM-dd_HH.mm.ss.txt` with `[C]` executed command, `[M]` message, `[E]` failure, `[R = n]` return value, `[C] <command> -> <num>`, `[F] <function> size=<num>`; result value = total number of commands in the functions; it cannot be called via `/return run` or nested `/debug function`; requires permission level 3. — [Commands/debug](https://minecraft.wiki/w/Commands/debug)
- spark commands: `/spark profiler start|stop|open|cancel|info`, `--timeout <s>`, `--thread *|<name> [--regex]`, `--only-ticks-over <ms>`, `--alloc`, `--interval <ms>` (default 4), `stop --save-to-file`; `/spark health [--memory|--network]` (dashboard every 10 s), `/spark tps` (TPS + CPU), `/spark tickmonitor --threshold <pct>|--threshold-tick <ms> [--without-gc]`, `/spark gc`, `/spark gcmonitor`, `/spark heapsummary`, `/spark heapdump --compress gzip|xz|lzma`; permissions `spark`, `spark.profiler`, `spark.health`, `spark.tps`, `spark.tickmonitor`. — [spark docs: Command usage](https://spark.lucko.me/docs/Command-Usage)
- Fabric install: `spark-X.X.X-fabric.jar` in `mods/`, depends on Fabric API; workflow `/spark tps` → `/spark profiler start` during lag for 2–5 minutes (or the 120 s default timeout) → `/spark profiler stop` → read the flame graph from `MinecraftServer.tickChildren`; ops only by default. — [xgamingserver spark guide](https://xgamingserver.com/docs/minecraft/setup-spark), [mineguard spark guide](https://mineguard.pro/en/blog/spark-profiler-find-minecraft-lag-source)
- `max-tick-time=60000` watchdog default (local test + wiki): a single tick longer than 60 s crashes the server with exit code 1; `max-chained-neighbor-updates=1000000` caps cascading block updates. — [Server.properties](https://minecraft.wiki/w/Server.properties)
- Fabric server performance mods relevant to command-heavy worlds: Lithium (game logic), Krypton (networking), FerriteCore (memory); vendor percentages unsourced. — [xgamingserver Fabric performance guide](https://xgamingserver.com/docs/minecraft/fabric-optimize)

### Inferences
- For this repo's packs (tutorial `player_tick` per player per tick, `one-block_2` speedrun/lives tick, tile/npc tick loops): run `/debug function tut:internal/tick` once to get the command count per tick from the trace's `size=` lines and `[C]` entries, then multiply by players; a few hundred commands per tick is trivial on a 4.6 GHz P-core, but `execute as @a at @s run …` selector chains and `fill`/`clone` on every tick are the usual offenders. spark's `--only-ticks-over 50` isolates the ticks that actually missed the 20 TPS budget.
- `--profile` was asked about: no 26.x server flag of that name was found on the wiki or in the jar's `--help` output during the local run (the `--help` was not captured; only `--initSettings`), so treat it as nonexistent for the dedicated server; the equivalents are `/debug` and spark.
- Because `pause-when-empty-seconds` stops ticking with nobody online, a per-tick datapack loop costs nothing between sessions; the per-instance CPU budget only matters during class.

### Gaps
- No source quantifies the cost of a given number of datapack commands per tick in 26.x (ms per 1,000 commands); only measurement on the real packs will give that.
- The `max_command_chain_length` / `command_modification_block_limit` gamerule values and 26.3 spellings were not fetched; check in-game.
- Whether `/debug start`/`stop` in 26.3 still writes any profiler file (the wiki marks the old dump as removed) is unclear; spark is the dependable path.
