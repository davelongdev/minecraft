# Day-to-day operations for self-hosted Minecraft Java 26.3 Fabric servers on Arch Linux (backups, upgrades, world/datapack workflow, running state, monitoring, multi-server housekeeping)

Researched 2026-10-18. Scope: 3 to 6 small game servers on one Arch box, worlds and datapacks authored in singleplayer (Prism Launcher flatpak, Minecraft 26.3) on a laptop and pushed to the server. Version facts below were checked against minecraft.wiki, Fabric Meta, Modrinth's API, and the itzg docs on the research date. Where I could not reach an official page (fabricmc.net/use/server is JS-rendered, the Arch wiki was behind an Anubis challenge), the finding is marked as an inference or a gap.

## 1. Backups: consistent world backups while the server runs

### Takeaway
A live world can only be copied safely after `save-off` + `save-all flush` (and only until `save-on`), which is exactly the sequence every serious tool (itzg/mc-backup, Crafty, ad-hoc scripts) automates over RCON; restic (or borg) on top of that gives deduplicated, retention-managed, off-box copies, and the whole server directory (not just `world/`) is what to back up.

### Cited Findings
- `save-all` "saves player data immediately and marks all chunks for saving", which then happens "over time"; `save-all flush` "saves all players and chunks immediately" and "freezes the server for a short time". Both are dedicated-server only, permission level 4. — [minecraft.wiki Commands/save-all](https://minecraft.wiki/w/Commands/save-all)
- `save-off` "stops the server from writing to level files, except player, advancement, and stat files, so they can be copied for backup"; "all level changes are temporarily queued". It fails if saving is already off, and "this option is reset each time the server restarts". `save-on` re-enables writing and fails if saving was not off. — [minecraft.wiki Commands/save-all](https://minecraft.wiki/w/Commands/save-all)
- Why plain `cp` of a live world is unsafe: region files (`r.x.z.mca`, Anvil) are rewritten in place as chunks save; with saving on, the copy can capture a file mid-write. Crafty's docs state it directly: Crafty "copies file system data, so changes made during the copy can cause data loss or corruption", which is why it offers (and recommends) "Shutdown During Backup". — [Crafty 4 Backup Manager](https://docs.craftycontrol.com/pages/user-guide/backup-manager/)
- `sync-chunk-writes=true` (default, since 20w14a/1.16) "enables synchronous chunk writes to prevent data loss or corruption after a crash, at the possible cost of I/O performance"; `region-file-compression` (default `deflate`; `lz4`, `none` also allowed since 1.20.5) "changed chunks are not automatically recompressed". — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- Scripts that forget `save-on` after a crash leave autosave disabled; a German ops guide recommends a shell `trap` so `save-on` always runs. — [mineguard.pro (secondary)](https://mineguard.pro/de/blog/minecraft-server-world-backup-restore); the save-off → save-all → copy → save-on order is also described in a Minecraft backup-tool devlog — [rustybever.be devlog (secondary; site unreachable on re-fetch)](https://rustybever.be/dev/alex/devlog-1/)
- itzg/mc-backup (Docker sidecar for `itzg/minecraft-server`) RCON sequence: wait until the server accepts `save-on`; run `PRE_SAVE_ALL_SCRIPT`; send `save-off` then `save-all`; run `PRE_BACKUP_SCRIPT`; back up; run `PRE_SAVE_ON_SCRIPT`; send `save-on`; run `POST_BACKUP_SCRIPT`. It also runs the filesystem `sync` after `save-all` (`ENABLE_SYNC`, default true, "only disable this if you know why"). — [github.com/itzg/docker-mc-backup](https://github.com/itzg/docker-mc-backup)
- mc-backup methods and knobs: `BACKUP_METHOD` = `tar` (default; `DEST_DIR` default `/backups`, `TAR_COMPRESS_METHOD` default gzip, also zstd/xz/etc., `LINK_LATEST`), `rsync`, `restic` (needs `RESTIC_REPOSITORY` + `RESTIC_PASSWORD`; `PRUNE_RESTIC_RETENTION` default `--keep-within 7d`; warning: pin the container hostname or use a unique `BACKUP_NAME`, otherwise instances sharing a repo prune each other's snapshots; SFTP not supported directly, use rclone), `rclone` (tar locally then move to a remote; config in `/config/rclone/rclone.conf`). Scheduling: `BACKUP_INTERVAL` default `24h` (0 or negative = run once and exit), `INITIAL_DELAY` `2m`, `BACKUP_ON_STARTUP` true, or `CRON_SCHEDULE`; `PAUSE_IF_NO_PLAYERS` (default false) with `PLAYERS_ONLINE_CHECK_INTERVAL` `5m`. Pruning: `PRUNE_BACKUPS_DAYS` default 7, `PRUNE_BACKUPS_COUNT` (tar/rsync only). Defaults `EXCLUDES=*.jar,cache,logs,*.tmp`, `SRC_DIR=/data`, `BACKUP_NAME=world`, `RCON_HOST=localhost`, `RCON_PORT=25575`, `RCON_PASSWORD=minecraft` (or `RCON_PASSWORD_FILE`). On-demand: `docker compose exec backups backup now`. Restore: `restore-backup` (tar) / `restore-rsync-backup` only extract the newest backup into an empty `SRC_DIR`; the README's compose example uses an init container (`entrypoint: restore-tar-backup`, name differs from the text, verify against your image). — [github.com/itzg/docker-mc-backup](https://github.com/itzg/docker-mc-backup)
- itzg/mc-backup does not support Bedrock. — [github.com/itzg/docker-mc-backup](https://github.com/itzg/docker-mc-backup)
- restic retention: `restic forget --keep-last n | --keep-hourly n | --keep-daily n | --keep-weekly n | --keep-monthly n | --keep-yearly n | --keep-within 2y5m7d3h` (plus `--keep-within-daily` etc. and `--keep-tag`); `--prune` runs `prune` afterwards only if something was removed; `--dry-run` previews; run `restic check` after pruning to verify repository structures. Example from the docs: `restic forget --keep-daily 7 --keep-weekly 5 --keep-monthly 12 --keep-yearly 75`. — [restic docs: Removing backup snapshots](https://restic.readthedocs.io/en/stable/060_forget.html)
- Crafty 4 built-in backups: Max Backups count (0 = unlimited, older ones garbage-collected), optional compression (docs warn compressing chunk data "can cause chunk corruption or artifacting", use at own risk), "Shutdown During Backup" option (recommended), pre/post server commands, path exclusions, scheduling via the Server Task Scheduler, a non-deletable "Default backup" that runs before any server update, two restore modes ("restore in place" keeps files not in the backup; "restore and reset server directory" replaces everything, irreversibly). Only Super Users may change the storage path. — [Crafty 4 Backup Manager](https://docs.craftycontrol.com/pages/user-guide/backup-manager/)
- Pelican Panel: a backup storage method must be configured before backups can be created; the default is local storage on the Wings node, S3 is the alternative (`BACKUP_PRESIGNED_URL_LIFESPAN`, `AWS_BACKUPS_STORAGE_CLASS`, default STANDARD); after switching drivers, existing backups remain downloadable/deletable from the old driver. A third-party "Backup Templates" plugin adds reusable ignored-path presets. — [pelican.dev optional config](https://pelican.dev/docs/panel/optional-config); [hub.pelican.dev Backup Templates](https://hub.pelican.dev/plugins/backup-templates)
- What lives where in a 26.x world (so you know what a `world/` backup contains): `level.dat` (+ `level.dat_old` written on load, `level.dat_new` written then renamed), `session.lock`, `datapacks/`, `resourcepacks/`, `players/` (since 26.1 Snapshot 6: `playerdata` → `players/data`, `stats` → `players/stats`, `advancements` → `players/advancements`), `data/minecraft/` (`game_rules.dat`, `scoreboard.dat`, `weather.dat`, `world_gen_settings.dat`, `random_sequences.dat`, `scheduled_events.dat`, `custom_boss_events.dat`, `world_clocks.dat`, ...), `dimensions/minecraft/overworld/{region,entities,poi,data}/`, `dimensions/minecraft/the_nether/`, `dimensions/minecraft/the_end/` (dragon fight under `the_end/data/minecraft/`), custom dimensions under `dimensions/<namespace>/<path>/`. Scoreboards and storage (`data/minecraft/` and per-namespace `data/<ns>/`) are world-level, not dimension-level. — [minecraft.wiki Java Edition level format](https://minecraft.wiki/w/Java_Edition_level_format)
- Server-level files outside `world/` that a backup must include: `whitelist.json` (Java; `whitelist reload` re-reads it "when whitelist.json was modified outside of Minecraft"), and the whitelist is on by default since 26.3 Snapshot 2. — [minecraft.wiki Commands/whitelist](https://minecraft.wiki/w/Commands/whitelist); [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- itzg's Docker image health/stop knobs that matter for backups on shutdown: `STOP_DURATION` (default 60 s) is how long the wrapper waits after sending `stop`; `STOP_SERVER_ANNOUNCE_DELAY` adds a pre-stop announcement; the Docker stop grace period must exceed it, and "exit code 137 indicates a longer grace period is needed"; `docker stop --signal SIGUSR1 mc` skips the announce delay. — [itzg docs misc options](https://docker-minecraft-server.readthedocs.io/en/latest/configuration/misc-options/)

### Inferences
- Minimal correct manual sequence (dedicated server, RCON enabled): `save-off` → `save-all flush` → wait a second or two → copy `world/` (and the other server files) → `save-on`, with the `save-on` in a shell `trap` so a failed copy cannot leave autosave off. Because `save-off` resets on restart, a crash during the copy self-heals on the next start. Player, advancement, and stat files are still written during `save-off`, so a backup taken mid-session can hold a player file newer than the world; the wiki notes this exclusion, so treat player data as "latest wins" rather than part of the frozen snapshot.
- Stopped-server backups (Crafty's "shutdown during backup" model) are strictly simpler and are fine for a class server that is idle between sessions; they also capture `session.lock`-free, fully flushed worlds, which is the state you want to copy to the laptop or to a restore test.
- Back up the entire server directory, excluding only `logs/`, `cache/`, `libraries/`, `versions/`, `.fabric/`, and jars (itzg's default excludes are `*.jar,cache,logs,*.tmp`); that covers `world/` (which already contains `datapacks/`), `mods/`, `config/`, `server.properties`, `whitelist.json`, `ops.json`, `banned-*.json`, `usercache.json`, and `eula.txt`. Fabric libraries and the vanilla server jar are re-downloadable.
- restic fits this setup well: deduplication across six similar small worlds and across daily runs keeps the repo tiny, retention is a single `forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune` line, and the same repository can live on the laptop (over SSH via `sftp:` or `rest-server`) or in an S3/B2 bucket. Borg is equivalent for a single-host-to-single-destination setup; the published comparisons I found are 2017 to 2019 and not decision-grade.
- A class-appropriate retention policy (unsourced, derived from the tools above): hourly snapshots while a session is running (mc-backup `BACKUP_INTERVAL: 1h` with `PAUSE_IF_NO_PLAYERS: true`), keep 7 daily + 4 weekly + a tagged "end of term" snapshot, plus a manual tagged snapshot before every version upgrade and before each class session so a griefing incident can be rolled back to "start of class".
- Restoring one region or one player: stop the server, restore the single file from the snapshot (`restic restore <id> --target /tmp/r --include /srv/mc/<server>/world/dimensions/minecraft/overworld/region/r.0.0.mca`, same for `world/players/data/<uuid>.dat`), copy it into place, start. The `--include` syntax is from restic's restore docs, which I did not fetch this session; verify with `restic restore --help`. Region files are independent 32×32-chunk units, so replacing a single `.mca` is safe as long as `entities/` and `poi/` for the same region are restored together (inference from the format layout).
- Testing restores: unpack the newest backup into a scratch directory and start a throwaway Fabric server on a different port (e.g. `server-port=25599`, `level-name=world`) against it; if it reaches "Done" and `/tick query` reports a normal rate, the backup is good. Do this at least once per term and after any change to the backup script.
- Pulling backups to the laptop: `rsync -a --delete server:/srv/mc-backups/ ~/mc-backups/` on a timer, or make the laptop the restic repository host; the itzg `rclone` mode is the Docker-native way to push tarballs to any rclone remote (B2, S3, Google Drive, SFTP).

### Gaps
- I did not find an authoritative write-up of the exact corruption mechanism for copying live `.mca` files (sector table vs chunk payload); the claim rests on the wiki's description of queued writes and Crafty's warning.
- restic's `restore --include` flags and the healthchecks/cron examples were not fetched; the restore page returned only the `forget` material.
- No current (2026) r/admincraft thread surfaced for backup practice; search results were tool READMEs and dated comparisons.

## 2. Upgrades: Fabric jar/loader, 26.3 → 26.4 with datapacks, Java on Arch, rollback

### Takeaway
Upgrading is "swap the Fabric launcher jar (or re-run the installer), update Fabric API/spark, bump every pack's `max_format`, test on a copy, keep the pre-upgrade backup because world upgrades are one-way"; on Arch the practical Java rule is to install `jdk25-openjdk` (or `jre25-openjdk-headless`) and point the server at `/usr/lib/jvm/java-25-openjdk/bin/java` explicitly rather than depending on the system default, which Docker images avoid by bundling Java per tag.

### Cited Findings
- Java requirement: 1.20.5 (24w14a) through 1.21.11 need Java 21; 26.1 (from 26.1 Snapshot 1) and later need Java 25 or newer. — [minecraft.wiki Tutorials/Update Java](https://minecraft.wiki/w/Tutorials/Update_Java); 26.4 Snapshot 1 still lists Java SE 25 as minimum. — [minecraft.wiki Java Edition 26.4 Snapshot 1](https://minecraft.wiki/w/Java_Edition_26.4-snapshot-1)
- Running a 26.x jar on Java 21 "fails immediately with an unsupported class file version" rather than warning (third-party hosting guide). — [space-node.net 26.3 server update guide (secondary)](https://space-node.net/blog/minecraft-26-3-server-update-guide-2026)
- Fabric Meta for game version 26.3 lists loader 0.20.0 (stable: false), 0.19.5 (stable: true), 0.19.4 as the newest three; each entry carries `launcherMeta.min_java_version`, server/common library lists, and `mainClass.server`. Installer versions: 1.1.2 (stable), 1.1.1, 1.1.0, from `https://maven.fabricmc.net/net/fabricmc/fabric-installer/<v>/fabric-installer-<v>.jar`. — [meta.fabricmc.net loader/26.3](https://meta.fabricmc.net/v2/versions/loader/26.3); [meta.fabricmc.net installer](https://meta.fabricmc.net/v2/versions/installer)
- Fabric Meta documents `/v2/versions/game`, `/v2/versions/loader/:game_version` (compatible loaders, newest first, 5-minute refresh), `/v2/versions/loader/:game_version/:loader_version` (launcherMeta with server libraries and main class), and `/v2/versions/loader/:game_version/:loader_version/server/json`; the `/server/jar` endpoint is not described in the README. — [FabricMC/fabric-meta README](https://raw.githubusercontent.com/FabricMC/fabric-meta/master/README.md)
- The Fabric wiki's Linux server tutorial: make a directory, pick Minecraft and loader versions on the Fabric server download page, download the server JAR either by pasting the page's generated `curl` command or by file transfer, and launch with the command shown on the page. (Its Java table stops at "1.20.5 or newer: Java 21"; it predates 26.x.) — [wiki.fabricmc.net install_server](https://wiki.fabricmc.net/player:tutorials:install_server)
- Fabric API builds for 26.3 on Modrinth (6 total): 0.163.0+26.3 (2026-10-14), 0.162.0+26.3 (2026-10-06), 0.161.0+26.3 (2026-09-18); each is single-game-version (26.3 only), so 26.4 will need a `+26.4` build. — [Modrinth API fabric-api versions for 26.3](https://api.modrinth.com/v2/project/fabric-api/version?game_versions=%5B%2226.3%22%5D&loaders=%5B%22fabric%22%5D)
- spark for Fabric: one 26.3-compatible build, `spark-1.10.187-fabric.jar` (2026-09-19), declared for 26.1, 26.1.1, 26.1.2, 26.2, 26.3, with no Fabric API dependency listed. — [Modrinth API spark versions for 26.3](https://api.modrinth.com/v2/project/spark/version?game_versions=%5B%2226.3%22%5D&loaders=%5B%22fabric%22%5D)
- Pack formats: 26.1–26.1.2 = 101.1; 26.2 = 107.1; 26.3 = 121.0 (26.3 snapshots ran 108.0–120.0, 114 skipped); since 25w31a `pack.mcmeta` uses `min_format`/`max_format` instead of `pack_format`; a pack with a format higher than the game supports "appears as incompatible", and a mismatch "displays a warning in the pack list". — [minecraft.wiki Pack format](https://minecraft.wiki/w/Pack_format)
- 26.4 Snapshot 1 (2026-09-22): data pack format 122.0, resource pack format 98.0, data version 5119; worldgen-side changes (`cuboid` placement sizes now exact, `fixed_placement` needs ≥1 position, `straight_trunk_placer.trunk_width`, noise settings `default_block` removed, placed features validated to a 3×3 chunk region, `/fillbiome` block-accurate, NBT float→int rounds down); new server.properties `allowed-connection-ids`, `status-contact-details`, `enable-legacy-status` (default true). No removed or renamed commands listed. — [minecraft.wiki Java Edition 26.4 Snapshot 1](https://minecraft.wiki/w/Java_Edition_26.4-snapshot-1)
- Data pack `min_format`/`max_format` example in the wiki uses array form `[88, 0]` for 1.21.9; broken packs "trigger an error on world open" and Safe Mode "disables all data packs except the vanilla one". — [minecraft.wiki Data pack](https://minecraft.wiki/w/Data_pack)
- Paper's update guide (applies to any server jar): back up world folders, server config, and plugin/mod jars and configs, keep multiple points in time ("the most important step, and yet the most frequently skipped"); stop the server before replacing the jar ("don't replace the JAR while the server is running"); rename the new jar to match your start command; watch the startup log; avoid automatic updates. — [docs.papermc.io Updating](https://docs.papermc.io/paper/updating/)
- itzg Docker image: `TYPE=FABRIC` auto-downloads the Fabric launcher and loader for `VERSION` from Fabric Meta; pin with `FABRIC_LOADER_VERSION` / `FABRIC_LAUNCHER_VERSION`; `FABRIC_LAUNCHER` (custom jar under `/data`) or `FABRIC_LAUNCHER_URL`; `FABRIC_FORCE_REINSTALL=true` to redo a corrupted launcher; `MODRINTH_PROJECTS=fabric-api` installs Fabric API automatically. — [itzg docs Fabric](https://docker-minecraft-server.readthedocs.io/en/latest/types-and-platforms/server-types/fabric/)
- itzg image tags carry Java: `latest`/`stable`/`java25` = Java 25 Ubuntu Hotspot (also `java25-alpine`, `java25-jdk`, `java25-graalvm`), `java21*`, `java17*`, `java8`; "latest moves to the Java version Mojang requires for the latest Minecraft release"; pin with `<release>-<java tag>` such as `2024.4.0-java17`. — [itzg docs Java versions](https://docker-minecraft-server.readthedocs.io/en/latest/versions/java/)
- Arch, checked locally on this machine (2026-10-18): `archlinux-java status` lists `java-21-openjdk` and `java-27-openjdk (default)`; `/usr/lib/jvm/` holds `default`, `default-runtime`, and one directory per JDK. `pacman -Si jdk25-openjdk` → 25.0.4.1.u1-1, provides `java-environment=25`, `java-runtime=25`, `java-runtime-headless=25`, conflicts with `jre25-openjdk`/`jre25-openjdk-headless`; `jre25-openjdk-headless` 25.0.4.1.u1-1 provides only `java-runtime-headless=25`; `jdk-openjdk` is 27.u35-1 (provides `java-environment=27`). `/etc/pacman.conf` has `IgnorePkg` support (`IgnorePkg = rpi-imager` already present) and `HoldPkg = pacman glibc`. — local `pacman -Si`, `archlinux-java status`, `/etc/pacman.conf` (no URL; primary system state)

### Inferences
- Procedure for the non-Docker Fabric server (the exact installer CLI could not be fetched from an official page this session; this matches the installer's long-standing interface and should be verified with `java -jar fabric-installer-1.1.2.jar help`): `java -jar fabric-installer-1.1.2.jar server -dir /srv/mc/<name> -mcversion 26.3 -loader 0.19.5 -downloadMinecraft` writes `fabric-server-launch.jar`, `fabric-server-launcher.properties` (`serverJar=server.jar`), `server.jar` (vanilla), and `.fabric/`; start with `java -Xms2G -Xmx2G -jar fabric-server-launch.jar nogui`. The one-file "executable server jar" from the download page (`fabric-server-mc.26.3-loader.0.19.5-launcher.1.1.2.jar`) bundles the launcher and fetches `server.jar` + libraries on first start; upgrading is "download the new one-file jar for 26.4 (or re-run the installer with `-mcversion 26.4`), keep the same directory". Pin the loader to a `stable: true` entry (0.19.5 today, not 0.20.0) for the class servers.
- 26.3 → 26.4 checklist for datapack worlds: (1) take a tagged backup; (2) clone the server directory to a scratch port and run 26.4 there first, because the world is rewritten on first load and Paper's "don't replace the jar while running / back up first" advice doubles as the rollback plan: there is no documented downgrade, so rollback = restore the pre-upgrade copy; (3) bump `max_format` from 121 to 122 in every pack (your packs already use `min_format: 107, max_format: 121`; keeping `min_format` low lets one zip serve 26.2–26.4); (4) read the 26.4 datapack changes (above) against your packs: none of the listed 26.4 Snapshot 1 changes touch commands your packs use (`/fillbiome`, placement modifiers, noise settings are worldgen), but check later 26.4 snapshots; (5) swap `fabric-api-*+26.4.jar` and a spark build listing 26.4; (6) run `/reload`, grep `latest.log` for "Failed to load function" and "Registry loading errors"; (7) only then upgrade the real servers one at a time.
- Java on Arch, decision: because `jdk-openjdk` already tracks 27 and `archlinux-java set` changes the system-wide default for every Java app (Prism's instances are unaffected: Prism uses its own Mojang-provided runtime), start each server with an explicit JVM path, e.g. `/usr/lib/jvm/java-25-openjdk/bin/java`, in the systemd unit. Install `jre25-openjdk-headless` on a headless server (smaller, no GUI deps) or `jdk25-openjdk` if you also build mods there. Arch keeps versioned JDK packages (`jdk21-openjdk`, `jdk25-openjdk`) side by side with the unversioned `jdk-openjdk`, so pinning is implicit: the 25 package stays at 25.x across `pacman -Syu`; `IgnorePkg` is only needed if you want to freeze a specific 25.0.x build. Re-check with `archlinux-java status` after any `-Syu` that pulls in a new `jdk-openjdk`, since `archlinux-java fix` can reset the default.
- Docker sidesteps the Java question entirely: `itzg/minecraft-server:java25` + `TYPE=FABRIC` + `VERSION=26.3` bundles the JVM Mojang requires; moving to 26.4 is changing `VERSION`, and pinning the image to `<release>-java25` avoids surprise base-image changes. The cost is that the Fabric launcher, mods, and datapacks are managed by env vars instead of files, and a flatpak Prism laptop can't run the compose stack to test locally.

### Gaps
- Official fabricmc.net server page and the fabric-installer README could not be fetched (JS-rendered landing page / README not in the GitHub capture), so the installer CLI flags and generated file names are stated from prior knowledge, not a fetched source.
- The Arch wiki Java page was behind an Anubis challenge; `archlinux-java` semantics (`set`, `fix`, `status`) are from local inspection and the package metadata, not the wiki text.
- No source states whether a server loads a datapack whose `max_format` is below the running version with a warning vs refusing; the wiki only describes the singleplayer pack-list warning. Test on the scratch server.
- 26.4 release date and final pack format are not known; the snapshot value 122.0 may change before release.

## 3. World and datapack workflow from the Prism laptop to the server

### Takeaway
A 26.3 singleplayer save is a drop-in server world: copy the save folder to `<server>/<level-name>/`, drop `session.lock` and `level.dat_old` (harmless but useless), put pack zips in `<level-name>/datapacks/`, and `/reload` over RCON for function/tag/loot/advancement changes; anything touching dimensions, worldgen, or `level.dat`-level settings needs a restart.

### Cited Findings
- `level-name` (default `world`): "if a valid world exists at this path, the server loads it; otherwise it generates a new world there, creating parent directories as needed"; it may be absolute or relative to the working directory or `--universe`. — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- `session.lock` holds the single character ☃ (U+2603); the game writes it and then takes an OS file lock, and "if the lock fails, the program aborts and gives up its claim on the level"; before 1.16 it held a timestamp that other instances watched. The wiki notes Minecraft "can sometimes keep holding a lock after you switch levels" and recommends closing the game first. — [minecraft.wiki Java Edition level format](https://minecraft.wiki/w/Java_Edition_level_format)
- `level.dat_old` is the previous `level.dat`, backed up on load; `level.dat_new` is written first and renamed. — [minecraft.wiki Java Edition level format](https://minecraft.wiki/w/Java_Edition_level_format)
- 26.1 Snapshot 6 introduced `dimensions/` and `players/`; `DIM-1`/`DIM1` became `dimensions/minecraft/the_nether` / `the_end`; overworld data moved under `dimensions/minecraft/overworld/`; many `level.dat` fields moved into `data/minecraft/*.dat`; 26.3 Snapshot 7 added a `version_history` list to `level.dat`. — [minecraft.wiki Java Edition level format](https://minecraft.wiki/w/Java_Edition_level_format)
- Data packs live in the world's `datapacks/` folder ("`.minecraft/saves/<world>/datapacks`" for singleplayer); the wiki does not name the server path separately. — [minecraft.wiki Data pack](https://minecraft.wiki/w/Data_pack)
- The itzg image installs `DATAPACKS` (comma list of zip URLs, zip files, or directories) into `/data/$LEVEL/datapacks`, i.e. `<level-name>/datapacks/` is the server location; `REMOVE_OLD_DATAPACKS=true` deletes zips matching `*.zip` first. `WORLD` accepts a URL to a ZIP/TAR or a path; the archive is searched for `level.dat` and that subdirectory becomes `$LEVEL`; the copy happens only when no world exists unless `FORCE_WORLD_COPY=TRUE`. — [itzg docs world data](https://docker-minecraft-server.readthedocs.io/en/latest/misc/world-data/)
- `/reload` reloads "registry tags, loot tables, recipes, advancements, item modifiers, predicates, functions, and structure templates"; "other features require the world or server to be rebooted". `dimension`, `dimension_type`, and `worldgen` folders are experimental/dynamic-registry content that `/reload` cannot apply: "the world must be exited and reopened in singleplayer, or the server rebooted in multiplayer". If a pack has invalid data, "changes are not applied and the game continues using the previous data". `/datapack enable|disable` also triggers a reload. When a file exists in multiple packs, "only the file in the last data pack is used"; tag files without `"replace": true` merge. — [minecraft.wiki Data pack](https://minecraft.wiki/w/Data_pack); [minecraft.wiki Commands/reload](https://minecraft.wiki/w/Commands/reload)
- RCON: `enable-rcon` default false; `rcon.port` 25575; `rcon.password` blank means RCON will not start; the wiki warns RCON is unencrypted and "should ideally be used only from localhost". — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- `whitelist reload` re-reads `whitelist.json` after outside edits; operators can always connect even when not whitelisted. — [minecraft.wiki Commands/whitelist](https://minecraft.wiki/w/Commands/whitelist)

### Inferences
- Copy procedure from the laptop (flatpak path `~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/instances/<inst>/minecraft/saves/<world>/`): stop the singleplayer world (so the lock is released and `level.dat` is flushed), `rsync -a --delete --exclude session.lock --exclude level.dat_old --exclude 'players/' <save>/ server:/srv/mc/<name>/world/` with the server stopped, set `level-name=world` (or the folder name you chose), start. Excluding `players/` drops your laptop player file (position/inventory) so kids start at world spawn; keep it if you want your own op state. `session.lock` is an OS-level lock since 1.16, so a stale file does not block the server; deleting it is tidiness, not a requirement (inference from the format page). Keep the `datapacks/` subfolder in the copy: it already holds the installed zips, so the world arrives with its packs.
- Scripted deploy for a pack-only change (no world change): `scp ~/minecraft/zips/<pack>.zip server:/srv/mc/<name>/world/datapacks/ && mcrcon -H 127.0.0.1 -P <port> -p <pw> reload` run on the server (or over an SSH tunnel so RCON stays loopback-only). Then `grep -A3 "Failed to load function" logs/latest.log`. For `commands-tutorial`, which carries per-player scoreboards and storage, a world re-copy would wipe progress; the pack zip is the thing to redeploy, the world only on first install or a deliberate reset.
- Keep `~/minecraft/zips/` as the source of truth: a `deploy.sh <server> <pack>` wrapper that zips from the pack directory (your existing `zip -r ../zips/<pack>.zip pack.mcmeta data`), scp's, reloads, and tails the log is enough; commit the server's `server.properties`, `whitelist.json`, `ops.json`, the systemd unit, and the deploy script to a `server-config/` git repo (secrets like `rcon.password` in an untracked `.env` the unit reads via `EnvironmentFile=`).
- Treat `/reload` as sufficient for everything your packs change today (functions, predicates, tags, loot tables, dialogs, structure templates); schedule a restart when a pack adds or changes a dimension/worldgen file, when `pack.mcmeta` formats are bumped, or when mods change.

### Gaps
- No official statement of the dedicated-server datapack path beyond the itzg docs and the general "inside the world folder" rule; it is the universally used `<level-name>/datapacks/`.
- Whether the 26.x server tolerates an extra `players/data/<uuid>.dat` from the laptop's offline/online UUID mismatch is untested here.

## 4. Running state: restarts, pause-when-empty, watchdog, "Can't keep up!", logs, crashes, disk, time

### Takeaway
Small 26.3 servers do not need scheduled restarts; let the built-in `pause-when-empty-seconds` idle them, keep `max-tick-time` at a sane value (or -1 if you ever use process pausing), route console output through journald with size caps, and know where crash reports and `hs_err_pid` files land.

### Cited Findings
- `pause-when-empty-seconds` default 60, added 1.21.2 (24w33a): seconds after the last player leaves before the server pauses. — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- itzg's autopause page advises against its own container-level autopause since 1.21.2 because the server "natively auto-pauses when the server is empty" (`PAUSE_WHEN_EMPTY_SECONDS`); for process-level pausing, "pausing makes a single tick look as long as the process was stopped, so the watchdog may force a restart after resume", hence set `max-tick-time` very large or -1 (`MAX_TICK_TIME`); Paper needs `JVM_DD_OPTS=disable.watchdog:true`. — [itzg docs autopause](https://docker-minecraft-server.readthedocs.io/en/latest/misc/autopause-autostop/autopause/)
- `max-tick-time` default 60000 ms: "if a single tick exceeds this limit, the server watchdog stops the server and exits with code 1"; -1 disables. — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- `player-idle-timeout` default 0 (never kick); `max-chained-neighbor-updates` default 1000000; 26.2 added `chat-spam-threshold-seconds` and `command-spam-threshold-seconds` (default 10, 0 disables kicks). — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- `/tick query` (1.20.3+, permission level 3) reports the target tick rate, average time per tick, and percentiles, and since 1.20.3-pre3 shows a message when the game is lagging behind the target; `/tick rate 1.0–10000.0`, `/tick freeze`, `/tick sprint <ticks>` also exist. — [minecraft.wiki Commands/tick](https://minecraft.wiki/w/Commands/tick)
- Crash reports go to the `crash-reports` folder; JVM-level crashes do not create a crash report but write `hs_err_pid<PID>.log` in the game/server directory and are "nearly always" out-of-RAM or very large operations (mass TNT, huge block moves). — [minecraft.wiki Crash](https://minecraft.wiki/w/Crash)
- HotSpot fatal error log: `hs_err_pid<pid>.log` in the process working directory, falling back to the OS temp dir (`/tmp` on Linux) if it cannot be written there; `-XX:ErrorFile=/var/log/java/java_error%p.log` relocates it (`%p` = PID). — [Oracle JDK 21 Troubleshooting Guide](https://docs.oracle.com/en/java/javase/21/troubleshoot/fatal-error-log.html)
- Log files: the live log is `logs/latest.log` in the server root; rotated sessions are gzip files named by date and sequence (`YYYY-MM-DD-N.log.gz`); `crash-reports/` only appears after the first crash. — [xgamingserver docs (secondary)](https://xgamingserver.com/docs/minecraft/find-share-server-logs); [kinetichosting (secondary)](https://www.kinetichosting.com/articles/minecraft/basics/how-to-find-a-minecraft-latest-log-file)
- Docker `json-file` driver: `max-size` (default unlimited) and `max-file` (default 1, only effective with `max-size`); set globally in `/etc/docker/daemon.json` (`"log-opts": {"max-size": "10m", "max-file": "3"}`, values must be strings) and restart Docker; existing containers keep their old config. — [Docker docs json-file driver](https://docs.docker.com/engine/logging/drivers/json-file/)
- The wiki's systemd template (`/etc/systemd/system/minecraft@.service`, `WorkingDirectory=/opt/minecraft/%i`, `User=minecraft`, screen session `mc-%i`, `Restart=on-failure`, `RestartSec=60s`, `ProtectSystem=full`, `ProtectHome=true`) stops gracefully by warning players, waiting `SHUTDOWN_DELAY`, `save-all`, `stop`, then `POST_SHUTDOWN_DELAY`; `ExecReload` sends `reload`; its sample `ExecStart` contains a `{}` placeholder and an inline comment that need fixing. — [minecraft.wiki Tutorials/Server startup script](https://minecraft.wiki/w/Tutorials/Server_startup_script)

### Inferences
- Scheduled restarts: with 3–6 players per server, vanilla pause-when-empty, and no plugin memory leaks, there is no evidence a daily restart is needed; the one restart worth scheduling is a weekly one at a dead hour so JVM heap fragmentation, log rotation, and any pending mod/pack reload all happen predictably. Pair it with the backup timer (backup first, then restart).
- "Can't keep up! Is the server overloaded? Running Xms behind, skipping N tick(s)" is the server's own log line for MSPT above 50 ms over a stretch; on these tiny servers it almost always means a datapack `tick` function doing heavy `fill`/`clone` work, a `schedule`-free recursive function, or chunk generation on first visit. `/tick query` (vanilla) or `/spark tickmonitor --threshold-tick 100` confirms it; `/spark profiler start --only-ticks-over 100` finds the function. No wiki page for the message was found this session, so the wording is from memory.
- Watchdog: 60 s is generous; leave it unless you pause the JVM externally. A watchdog exit (code 1) under systemd `Restart=on-failure` brings the server back in `RestartSec` and leaves a crash report, which is the behaviour you want for an unattended class server.
- Logging under systemd: run Java in the foreground (no screen) with `StandardOutput=journal`, and cap journald in `/etc/systemd/journald.conf` (`SystemMaxUse=500M`); Minecraft still writes its own `logs/*.log.gz`, so add a `find logs/ -name '*.log.gz' -mtime +30 -delete` to the backup script or a `tmpfiles.d` age rule. Keep `crash-reports/` and `hs_err_pid*.log` out of the auto-clean so you can read them later.
- Disk hygiene for 6 servers: worlds are small (void worlds + datapacks are megabytes); the growth is `logs/`, `crash-reports/`, and backups. Put backups on a different filesystem or host, monitor with `df` in the same healthcheck ping (fail the ping if `/srv` > 85 %), and keep `region-file-compression=deflate` (default).
- Time sync matters for the backup timers, `healthchecks.io` late detection, and TLS to Mojang's session servers: `systemd-timesyncd` (`timedatectl set-ntp true`) or chrony; nothing Minecraft-specific.

### Gaps
- No primary source for the exact "Can't keep up!" text and threshold in 26.3; treat the above as recollection.
- The minecraft.wiki logs page (naming of rotated files) was not in search results; only hosting guides describe the `YYYY-MM-DD-N.log.gz` pattern.

## 5. Monitoring: TPS/MSPT, exporters, external uptime checks, failure notifications

### Takeaway
Inside the server use `/tick query` (no mod) or spark (`/spark tps`, `/spark health`, `/spark profiler`); for dashboards use FabricExporter or itzg's mc-monitor Prometheus endpoint; for "is it up" use Uptime Kuma's GameDig monitor or a healthchecks.io dead-man ping from a cron/timer, and wire systemd `OnFailure=` to a Discord webhook.

### Cited Findings
- spark commands (server-side Fabric mod; the 26.3 build has no Fabric API dependency): `/spark tps` (TPS and CPU), `/spark health` (live dashboard every 10 s; `show --memory --network` prints to console), `/spark profiler start [--timeout s] [--thread *] [--only-ticks-over ms] [--alloc]`, `/spark profiler stop [--save-to-file]`, `/spark tickmonitor [--threshold %|--threshold-tick ms] [--without-gc]`, `/spark heapsummary`, `/spark gc`, `/spark gcmonitor`; permissions `spark` or `spark.<sub>`. — [spark docs Command Usage](https://spark.lucko.me/docs/Command-Usage); [Modrinth API spark 26.3](https://api.modrinth.com/v2/project/spark/version?game_versions=%5B%2226.3%22%5D&loaders=%5B%22fabric%22%5D)
- `/tick query` is vanilla since 1.20.3 and reports average and percentile tick times plus a lag warning. — [minecraft.wiki Commands/tick](https://minecraft.wiki/w/Commands/tick)
- Prometheus exporters: cpburnz's "Prometheus Exporter" (`minecraft-prometheus-exporter` on GitHub) is server-side only and its newest Fabric file found is for 1.21.8, so it is not available for 26.x; "FabricExporter" (hit-mc) is a separate Fabric-only mod with builds listed for 1.21.11 and 26.1 that recommends installing spark to get TPS/MSPT metrics. — [github.com/cpburnz/minecraft-prometheus-exporter](https://github.com/cpburnz/minecraft-prometheus-exporter); [CurseForge Prometheus Exporter files](https://www.curseforge.com/minecraft/mc-mods/prometheus-exporter/files/6830957); [Modrinth FabricExporter](https://modrinth.com/mod/fabricexporter); [github.com/hit-mc/fabric-exporter](https://github.com/hit-mc/fabric-exporter)
- itzg/mc-monitor: `mc-monitor status -host H -port 25565 [-timeout 15s] [-retry-limit N -retry-interval 10s]` exits 0 on success, 1 on failure (Docker healthcheck use); `export-for-prometheus` serves `/metrics` on port 8080 (`EXPORT_PORT`) with `minecraft_status_healthy`, `minecraft_status_response_time_seconds`, `minecraft_status_players_online_count`, `minecraft_status_players_max_count`, labels `server_host`, `server_port`, `server_edition`, `server_version`; also `gather-for-telegraf` and `collect-otel`; install via `go install github.com/itzg/mc-monitor@latest`, GitHub releases, or `docker run --rm itzg/mc-monitor status --host <host>`. — [github.com/itzg/mc-monitor](https://github.com/itzg/mc-monitor)
- The itzg server image's health status (healthy/unhealthy/starting) is visible in `docker ps` / `docker container inspect`, backed by mc-monitor. — [itzg docs healthcheck (mirror)](https://mintlify.com/itzg/docker-minecraft-server/operations/healthcheck)
- Uptime Kuma ships a `gamedig.js` monitor type (GameDig covers Minecraft) alongside `tcp.js`, `dns.js`, `steam.js`, `mqtt.js`, `system-service.js`, etc. — [louislam/uptime-kuma server/monitor-types](https://github.com/louislam/uptime-kuma/tree/master/server/monitor-types)
- healthchecks.io: each check has a ping URL (`https://hc-ping.com/<uuid>` or `/<ping-key>/<slug>`, treat as secrets); simple schedules go Late when the period elapses and Down after period + grace; cron/OnCalendar schedules go Late at the next scheduled time; `/start`, `/fail`, `/<exitcode>` suffixes report run time and failures. — [healthchecks.io docs](https://healthchecks.io/docs/)
- systemd `OnFailure=` notification pattern: a drop-in on the target unit sets `OnFailure=notify@%n.service`; a oneshot template service runs a script with the failed unit's name; blazon (quickvm) provides this for desktop/Slack, Telegram-Notifier for Telegram, and a 2026 Ubuntu headless guide shows the drop-in plus template; webhooks are recommended on headless servers because there is no user D-Bus session. — [github.com/quickvm/blazon](https://github.com/quickvm/blazon); [github.com/Git-User76/Telegram-Notifier](https://github.com/Git-User76/Telegram-Notifier); [oneuptime headless notifications guide](https://oneuptime.com/blog/post/2026-03-02-configure-desktop-notifications-ubuntu-server-headless/markdown)
- Discord incoming webhooks accept a JSON body with a `content` field (shown in Kestra's Discord webhook task docs). — [kestra.io Discord webhook](https://kestra.io/plugins/plugin-notifications/tasks/discord/io.kestra.plugin.notifications.discord.discordincomingwebhook)

### Inferences
- Recommended stack for 6 small servers: spark in every `mods/` (free, no Fabric API needed, gives `/spark tps` and profiler when a quest function lags), one `mc-monitor export-for-prometheus` process (or container) pointed at all six ports if you ever stand up Prometheus/Grafana, Uptime Kuma (self-hosted) with one GameDig monitor per server for an outside-in status page, and a healthchecks.io check pinged at the end of each backup run so a silently broken backup timer pages you.
- Discord notifications: `discord-notify@.service` (oneshot) running `curl -H 'Content-Type: application/json' -d "{\"content\":\"$1 failed on $(hostname)\"}" "$WEBHOOK"` with the URL in an `EnvironmentFile=` root-only file; attach via `OnFailure=discord-notify@%n.service` in `minecraft@.service`, and add `ExecStartPost=`/`ExecStopPost=` curls for start/stop messages. The Discord payload shape is the only unverified-against-Discord-docs piece.
- FabricExporter is the only Prometheus mod with 26.x builds found; confirm a 26.3 file on its Modrinth page before relying on it, otherwise mc-monitor (ping-level metrics only, no TPS) is the no-mod fallback.

### Gaps
- No Uptime Kuma documentation page describing the Minecraft/GameDig monitor options was fetched; presence of `gamedig.js` is from the source tree.
- FabricExporter's exact 26.3 compatibility and metric names were not verified (listing showed 26.1 and 1.21.11).
- Discord webhook payload details are from a third-party integration's docs, not Discord's.

## 6. Multi-server housekeeping: shared whitelist/ops, ports, start/stop-all, layout, docs

### Takeaway
One systemd template unit (`minecraft@<name>`) per server directory with its own game and RCON ports, a `whitelist.json`/`ops.json` synced from a single source (sync + `whitelist reload`, not symlinks across running servers), and a short `mc` script or Makefile wrapping `systemctl`/`mcrcon` covers 3–6 servers.

### Cited Findings
- Template units: the wiki's `minecraft@.service` runs one server per `/opt/minecraft/%i` folder, "the part behind the @ is your instance name e.g. the folder name", enabled per instance with `systemctl enable/start minecraft@<name>`, and "takes care to automatically stop your minecraft server if you reboot". — [minecraft.wiki Tutorials/Server startup script](https://minecraft.wiki/w/Tutorials/Server_startup_script)
- A published `minecraft@.service` uses `mcrcon` in `ExecStop` to send `stop`; each server directory needs its own RCON port; the file is copied into `/etc/systemd/system/`. — [brianwarner/minecraft-server-hosting minecraft@.service](https://github.com/brianwarner/minecraft-server-hosting/blob/main/minecraft@.service)
- Linuxize's single-server unit sends `save-all stop` through `mcrcon` in `ExecStop`. — [linuxize Debian guide](https://linuxize.com/post/how-to-install-minecraft-server-on-debian-9/)
- An on-demand variant stops the server only when RCON reports zero players, via a timer and a stop service. — [dataswamp.org (Solène Rapenne)](https://dataswamp.org/~solene/2022-08-20-on-demand-minecraft-with-systemd.html)
- `whitelist reload` re-reads `whitelist.json` after outside edits; operators bypass the whitelist; whitelist is on by default since 26.3 Snapshot 2; `enforce-whitelist` (default false) kicks already-connected non-listed players when the file is reloaded. — [minecraft.wiki Commands/whitelist](https://minecraft.wiki/w/Commands/whitelist); [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- `rcon.port` default 25575, `server-port` default 25565 (mc-monitor and mc-backup both default to these). — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties); [github.com/itzg/mc-monitor](https://github.com/itzg/mc-monitor)
- itzg's docs note RCON is enabled by default in their image and that `rcon-cli` is available for console access, with the stop sequence handled by the wrapper (`STOP_DURATION`, announce delay). — [itzg docs misc options](https://docker-minecraft-server.readthedocs.io/en/latest/configuration/misc-options/)

### Inferences
- Layout: `/srv/mc/<name>/` per server (`one-block`, `command-forge`, `tile-game`, `npc-game`, ...), each with `server.properties` (`server-port=2556N`, `rcon.port=2557N`, `rcon.password` from a shared `.env`), `world/` (with `datapacks/`), `mods/` (Fabric API + spark), `fabric-server-launch.jar` or the one-file launcher, and a `README.md` saying what the server is for, which pack/zip version it runs, the port, the last upgrade date, and how to reset (`/function tut:___reset_player` etc.). One `/etc/systemd/system/minecraft@.service` with `WorkingDirectory=/srv/mc/%i`, `EnvironmentFile=/srv/mc/%i/.env`, `ExecStart=/usr/lib/jvm/java-25-openjdk/bin/java -Xms1G -Xmx2G -jar fabric-server-launch.jar nogui`, `ExecStop=/usr/bin/mcrcon -H 127.0.0.1 -P ${RCON_PORT} -p ${RCON_PASSWORD} "say Server stopping" "save-all flush" "stop"`, `Restart=on-failure`, `OnFailure=discord-notify@%n.service`, `User=minecraft`. `mcrcon` is in the AUR; `rcon-cli` (itzg) is a Go binary alternative.
- Shared whitelist/ops: keep a single `/srv/mc/_shared/whitelist.json` and `ops.json` in the config git repo, and a `sync-lists.sh` that copies them into each server and runs `whitelist reload` over RCON (ops changes need `/op`/`/deop` or a restart; `ops.json` is read at start). Symlinking the same `whitelist.json` into six running servers works until one server rewrites the file after a `/whitelist add`, which races the others; copy-and-reload is the safe version.
- `mc` wrapper (shell script or Makefile targets): `mc start|stop|restart|status [name|all]` → `systemctl <verb> minecraft@{name}` looping over `ls /srv/mc`, `mc rcon <name> <cmd>`, `mc deploy <name> <pack.zip>` (scp + reload + log grep), `mc backup [name|all]` (the save-off/flush/restic/save-on sequence + healthchecks ping), `mc logs <name>` (`journalctl -fu minecraft@<name>`). `systemctl start 'minecraft@*'` does not expand; a loop or a `minecraft.target` with `Wants=minecraft@a.service minecraft@b.service ...` gives a true start-all/stop-all.
- Docker alternative: one `compose.yaml` with six `itzg/minecraft-server:java25` services plus one `itzg/mc-backup` per server (RCON per container), `docker compose up -d` / `down` as start-all/stop-all, and the json-file `max-size` cap from section 4. This trades Arch Java management and systemd units for env-var configuration; the per-server README habit is the same.

### Gaps
- No single authoritative guide for stopping several template instances at once was found; the `minecraft.target` approach is standard systemd practice, not a Minecraft-specific sourced recipe.
- Whether `ops.json` is hot-reloaded in 26.3 without `/op` was not verified.
