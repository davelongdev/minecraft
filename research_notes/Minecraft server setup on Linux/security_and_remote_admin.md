# Security hardening and remote administration for a self-hosted Arch box running Minecraft Java 26.3 servers for kids (October 2026)

Scope: one admin, one studio machine on a home/studio connection, several Fabric 26.3 servers with vanilla clients, kids deliberately given op (the dialog-form datapacks need it). Sources are the Arch wiki (read via its raw-wikitext endpoint because the rendered site is behind the Anubis bot wall), Docker docs, minecraft.wiki, PaperMC/Velocity docs, Tailscale KB, FTC, and scanner authors' own write-ups. Where a source is a vendor blog or forum post, that is flagged.

## Host and SSH: key-only SSH, no root/password login, port move, sshguard vs fail2ban, Tailscale SSH, Arch "unattended upgrades", LUKS at boot, `%wheel NOPASSWD`

### Takeaway
Force public-key auth and deny root with two drop-in files; OpenSSH ≥ 9.8 already rate-penalises bad sources, so a brute-force banner (sshguard with the nftables backend is the lightweight Arch choice) is optional once passwords are off. Moving the port only cuts log noise. The cleanest option for a one-admin box is to not expose sshd publicly at all and reach it over Tailscale (Tailscale SSH or plain sshd on the tailnet IP). Arch has no unattended-upgrades; the wiki's position is "read the news, then `pacman -Syu`", with `checkupdates`, a news-check pacman hook, and reboot discipline. For remote reboots of a LUKS root, the supported Arch routes are TPM2 auto-unlock via `systemd-cryptenroll` (with a recovery key and the PCR caveats) or an SSH server in the initramfs (`mkinitcpio-systemd-extras` for systemd initramfs; the old `mkinitcpio-dropbear`/`-netconf`/`-tinyssh` packages are now unmaintained). Keep `%wheel` password-protected; use per-command `NOPASSWD` only for the handful of commands automation needs.

### Cited Findings
**SSH configuration**
- Force keys: "One of the most effective ways to protect against this attack is to disable password logins entirely, and force the use of SSH keys" via `/etc/ssh/sshd_config.d/20-force_publickey_auth.conf` containing `PasswordAuthentication no` and `AuthenticationMethods publickey`; the wiki warns to put keys in every account's `authorized_keys` first — [Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Force_public_key_authentication)
- Arch's packaged default is already `KbdInteractiveAuthentication no` (the wiki notes a drop-in ordering quirk: custom snippets should sort after `99-archlinux.conf`) — [Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#PAM_setup)
- Deny root: `/etc/ssh/sshd_config.d/20-deny_root.conf` with `PermitRootLogin no`; the wiki flags the section as out of date because "Root login has been disabled by default upstream in the current version" (upstream default is `prohibit-password`); alternatives `forced-commands-only` / `prohibit-password` — [Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Limit_root_login)
- Restrict accounts with `AllowUsers user1 user2` or `AllowGroups group1 group2` — [Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Configuration)
- Port change: "A port change from default port 22 will reduce the number of log entries caused by automated authentication attempts but will not eliminate them" — [Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Configuration). The wiki's troubleshooting section calls a non-default port "security through obscurity" — [Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Connection_refused_or_timeout_problem)
- Built-in brute-force protection: "Since 9.8 a basic protection similar to fail2ban is implemented: the option `PerSourcePenalties` is set with reasonable default values. Penalties for various conditions are enforced against a client on its source address, resulting in a refused connection for a time period." Other listed options: only allow SSH from trusted locations; fail2ban or sshguard; `pam_shield` — [Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Protecting_against_brute_force_attacks)
- Do not use `sshd.socket`: openssh 8.0p1-3 removed it "due to it being susceptible to denial of service" — [Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Socket_activation)
- Deny root over SSH is "always good practice" as "an additional layer of security before a user can completely compromise your system remotely"; `passwd --lock root` disables root while keeping sudo — [Arch wiki: Security](https://wiki.archlinux.org/title/Security#Restricting_root)
- `pam_faillock` is on by default since pambase 20200721.1-2: lock out for 10 minutes after 3 failed password attempts in 15 minutes; "The lockout only applies to password authentication (e.g. login and sudo), public key authentication over SSH is still accepted"; root is exempt; locks are lost at reboot unless `dir = /var/lib/faillock` — [Arch wiki: Security](https://wiki.archlinux.org/title/Security#Lock_out_user_after_three_failed_login_attempts)

**sshguard vs fail2ban on Arch**
- fail2ban's own wiki page: "It usually does not make sense to use fail2ban with sshd when only public key authentication or similar is enabled." For nftables set `banaction = nftables` and `banaction_allports = nftables[type=allports]` in `/etc/fail2ban/jail.local`; jails are off by default (`[sshd] enabled = true`) — [Arch wiki: fail2ban](https://wiki.archlinux.org/title/Fail2ban)
- sshguard "is written in C, is lighter and simpler to use with fewer features while performing its core function equally well"; package `sshguard`; set `BACKEND="/usr/lib/sshguard/sshg-fw-nft-sets"` in `/etc/sshguard.conf`, enable `sshguard.service`; it then creates tables named `sshguard` in the `ip` and `ip6` families whose chains have priority −10 so they run before the normal filter chain; default ban 120 s growing ×1.5 per repeat, permanent blacklist at danger level 120 (≈12 failures), journald read via `LOGREADER="LANG=C.UTF-8 /usr/bin/journalctl -afb -p info -n1 -t sshd-session -o cat"` — [Arch wiki: sshguard](https://wiki.archlinux.org/title/Sshguard)
- The sshguard page carries a warning that an IP blacklist "relies on an additional daemon and successful logging (the partition containing /var can become full...)", that spoofed-source packets can lock you out, and that "SSH keys provide an elegant solution to brute forcing without these problems" — [Arch wiki: sshguard](https://wiki.archlinux.org/title/Sshguard)
- Pure-nftables alternative: `tcp dport ssh ct state new limit rate 15/minute accept comment "Avoid brute force on SSH"` — [Arch wiki: nftables](https://wiki.archlinux.org/title/Nftables#Limit_rate)

**Tailscale SSH instead of exposing port 22**
- Tailscale SSH "takes over port 22 for traffic arriving via the Tailscale IP"; `sshd_config` and `authorized_keys` are untouched, non-Tailscale SSH still works; enable with `tailscale set --ssh`; authentication is the WireGuard node identity, so "the SSH layer does not require further client proof"; `action: "check"` forces re-auth through the identity provider (MFA), default 12 h, `checkPeriod` 1 min–168 h or `"always"`; rules need both a network grant and an SSH rule (`src`, `dst`, `users`, `checkPeriod`, `acceptEnv`); Linux hosts; Tailscale ≥ 1.24; all plans — [Tailscale KB: Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)
- Caveats: restarting `tailscaled` (upgrades) ends sessions; only port 22; "Any OS user on a client machine can connect, since no local key pair is required" so it is discouraged on multi-user client machines; revoking policy ends sessions but SSH keys must be removed separately; `checkPeriod: "always"` breaks Ansible-style tooling; session recording is available — [Tailscale KB: Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)
- The KB does not say whether to firewall public port 22; it only states the public sshd keeps working — [Tailscale KB: Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)

**Arch has no unattended-upgrades**
- Wiki policy: "Before upgrading, users are expected to visit the Arch Linux home page to check the latest news"; pacman hooks `informant`, `newscheck` (AUR), `arch-manwarn` (AUR) block an update "if there is fresh Arch News that you have not read"; "never run `pacman -Sy`; instead, always use `pacman -Syu`"; `checkupdates` (pacman-contrib) safely checks/downloads pending updates (`-d`) without syncing the DB; deal with `.pacnew` promptly; `checkservices` (archlinux-contrib) merges pacnews and restarts processes using outdated libraries; "The kernel is particularly difficult to patch without a reboot. A reboot is always the most secure ... option"; consider `linux-lts` — [Arch wiki: System maintenance](https://wiki.archlinux.org/title/System_maintenance)
- Community automation: `pacroller` (AUR) runs upgrades on a timer, parses pacman output/log for known error patterns and refuses to run again after a failure until reset — [pacroller on PyPI](https://pypi.org/project/pacroller); `uau` (AUR) schedules upgrades "while respecting the recommended upgrade process" and warns auto-upgrades "can break services... require reboot handling" — [uau AUR listing (mirror)](https://linux-meta.duckdns.org/en/p/uau); Arch forum regulars argue unattended upgrades "cannot consider manual intervention news" and "cannot deal with .pacnew files" — [bbs.archlinux.org thread 283957](https://bbs.archlinux.org/viewtopic.php?id=283957)

**LUKS root and remote reboots**
- TPM2 enrol: `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/sdX` adds a TPM-bound key alongside the passphrase; requires `tpm2-tss`, LUKS2, and the `systemd` + `sd-encrypt` mkinitcpio hooks (hook order matters, wrong order "can make the system unbootable"); also enrol a recovery key: `systemd-cryptenroll /dev/disk --recovery-key` ("computer-generated... guaranteed high entropy... may be scanned off screen via a QR code") — [Arch wiki: systemd-cryptenroll](https://wiki.archlinux.org/title/Systemd-cryptenroll)
- PCR 7 warnings: Secure Boot must be active and in user mode "otherwise, unauthorized boot devices could unlock the encrypted volume"; PCR 7 "can change if firmware certificates change" (fwupd, key rotation) and lock you out; binding only to pre-boot PCRs 0–7 lets a rogue root partition that mimics the real one receive the key; mitigations are binding to an empty PCR 15 with `tpm2-measure-pcr=yes`, PCR policies / signed UKI, or `fixate-volume-key=` pinning — [Arch wiki: systemd-cryptenroll](https://wiki.archlinux.org/title/Systemd-cryptenroll#Trusted_Platform_Module), [Arch wiki: dm-crypt/System configuration](https://wiki.archlinux.org/title/Dm-crypt/System_configuration#Pinning_a_LUKS_volume), [Arch wiki: TPM](https://wiki.archlinux.org/title/Trusted_Platform_Module#PCR_policies)
- Wire it up: kernel parameter `rd.luks.options=<UUID>=tpm2-device=auto` or an initramfs `/etc/crypttab` line `root UUID=<UUID> none x-initrd.attach,tpm2-device=auto` (the password field must be `none` or `-` or the TPM is never tried) — [Arch wiki: dm-crypt/System configuration](https://wiki.archlinux.org/title/Dm-crypt/System_configuration#Trusted_Platform_Module_and_FIDO2_keys)
- Clevis is the other TPM binder: `clevis luks bind -d /dev/sdX tpm2 '{"pcr_ids":"1,7"}'`; PCR changes after UEFI/Secure Boot edits make decryption fail (re-bind needed); Tang gives network-bound unlocking; it has a mkinitcpio hook — [Arch wiki: Clevis](https://wiki.archlinux.org/title/Clevis)
- SSH-in-initramfs, systemd initramfs: AUR `mkinitcpio-systemd-extras` with `HOOKS=(base systemd autodetect microcode modconf kms keyboard sd-vconsole block sd-network sd-tinyssh sd-encrypt filesystems fsck)` and `SD_TINYSSH_COMMAND="systemd-tty-ask-password-agent --query"`; it copies systemd-networkd config and converts existing OpenSSH/TinySSH host keys; `tinyssh` must be installed; **critical warning**: add `rootflags=x-systemd.device-timeout=0` or systemd gives up after 90 s and drops to emergency mode, "You are then effectively locked out!"; predictable interface names are absent in early boot — [Arch wiki: dm-crypt/Specialties](https://wiki.archlinux.org/title/Dm-crypt/Specialties#Remote_unlocking_of_root_(or_other)_partition)
- `mkinitcpio-systemd-tool` is mentioned only historically: "documentation about this approach and how to use the tool itself is very limited" — [Arch wiki: dm-crypt/Specialties](https://wiki.archlinux.org/title/Dm-crypt/Specialties#systemd_based_initramfs_(built_with_mkinitcpio))
- Busybox initramfs: the page "used to recommend the mkinitcpio-netconf, mkinitcpio-dropbear and mkinitcpio-tinyssh packages but no longer does so as they are unmaintained"; use AUR `mkinitcpio-extras` (hooks `netconf`, `dropbear`, `tinyssh`) plus `mkinitcpio-utils` (`encryptssh` hook replacing `encrypt`), optional deps `dropbear`/`mkinitcpio-nfs-utils`; keys go in `/etc/dropbear/root_key` or `/etc/tinyssh/root_key` (tinyssh: Ed25519/ECDSA only, no passphrase); kernel `ip=dhcp` or `ip=192.168.1.1::192.168.1.254:255.255.255.0::eth0:none` (kernel names like `eth0`, not `enp1s0`); NIC module may need adding to `MODULES`; the initramfs sshd listens on **port 222** with its own host keys because the initramfs image may be world-readable — [Arch wiki: dm-crypt/Specialties](https://wiki.archlinux.org/title/Dm-crypt/Specialties#Busybox_based_initramfs_(built_with_mkinitcpio))
- One-time passwordless reboot via a temporary keyfile (`passless-boot`, AUR) exists for occasional remote reboots — [Arch wiki: dm-crypt/Specialties](https://wiki.archlinux.org/title/Dm-crypt/Specialties#One-time_password-less_reboot)

**sudo**
- Standard: `/etc/sudoers.d/10-wheel` → `%wheel ALL=(ALL:ALL) ALL`; disabling the password prompt carries the warning "This will allow any process running with your user name to use sudo without asking for permission"; the wiki's alternative is per-command passwordless, e.g. `archie hostname= NOPASSWD: /usr/bin/halt,/usr/bin/poweroff,/usr/bin/reboot,/usr/bin/pacman -Syu`, placed after the `%wheel` line; `Defaults timestamp_timeout=10` lengthens the 5-minute cache instead — [Arch wiki: Sudo](https://wiki.archlinux.org/title/Sudo#Configuration)
- Do not use root for daily use; create an unprivileged account per person — [Arch wiki: Security](https://wiki.archlinux.org/title/Security#Do_not_use_the_root_account_for_daily_use)

### Inferences
- For this box: `PasswordAuthentication no` + `AuthenticationMethods publickey` + `PermitRootLogin no` + `AllowUsers dave` covers the SSH surface; with keys only, pam_faillock and sshd 9.8's PerSourcePenalties already blunt brute force, so sshguard is a nice-to-have (choose it over fail2ban on Arch for the nftables backend and lower footprint), and its main value becomes log hygiene.
- The lowest-risk remote path is sshd bound to (or firewalled to) the Tailscale interface plus Tailscale SSH with `check` mode for the admin; keep a plain key-based sshd reachable over the tailnet as a fallback for the day `tailscaled` is mid-upgrade.
- Pick ONE of TPM2 auto-unlock (unattended reboots, but the disk decrypts for anyone who boots the real OS with the right Secure Boot state, so keep a recovery key off-box and lock the login screen/console) or initramfs SSH (you type the passphrase remotely; needs wired Ethernet and the `device-timeout=0` flag). For a studio machine that mostly needs reboots after kernel updates while the admin is away, TPM2 + PCR 7 (+PCR 15 trick or a signed-UKI policy) is the usual choice.
- "Unattended" on Arch realistically means: a timer that runs `checkupdates -d` and emails/notifies, with the admin running `pacman -Syu` over Tailscale after reading news; a tool like pacroller is acceptable only if you are willing to recover a broken boot remotely (which is exactly why the LUKS/initramfs question matters).
- Keep `%wheel` with a password. If something needs passwordless sudo (a deploy script, a reboot button), grant that one command only, as the wiki shows.

### Gaps
- No source quantifies how much `PerSourcePenalties` reduces brute force vs sshguard; the wiki merely says it is "similar to fail2ban".
- The Arch wiki does not say how `mkinitcpio-systemd-extras` behaves with Wi-Fi-only hosts (the busybox path has `mkinitcpio-wifi`); assume wired.
- No primary source found for Tailscale's own advice on closing public port 22 once Tailscale SSH is on.

## Firewall: nftables vs ufw vs firewalld on Arch, minimal ruleset (SSH + 25565–2557x only, rate limit, drop RCON/Query), Docker's bypass

### Takeaway
Use nftables directly: the package ships a secure default `/etc/nftables.conf`, ufw only works through the `iptables-nft` compatibility layer, and firewalld is a heavier front-end. A drop-policy `inet` table with loopback, established/related, ICMP, `tcp dport ssh` (ideally restricted to the Tailscale interface or LAN) and `tcp dport 25565-25569` is enough; add a `ct state new limit rate` or a per-source `meter` on the game ports, and do not open 25575 (RCON) or UDP 25565 (Query) at all. If Docker is in the picture, remember its published ports are inserted in the `nat`/`FORWARD` path before host `INPUT` rules; constrain them via `DOCKER-USER` (iptables backend), the `ip` daemon option / `127.0.0.1:` binds, or Docker 29's experimental nftables backend, which drops `DOCKER-USER` and needs your own base chains.

### Cited Findings
**Choice of tool on Arch**
- "nftables comes with a simple and secure firewall configuration stored in the /etc/nftables.conf file. The nftables.service will load rules from that file when started or enabled"; the `iptables` package itself "actually create[s] and act[s] on nftables rules" (iptables-nft), legacy rules are separate objects; "ufw is supported via a compatibility layer iptables-nft"; firewalld supports both back-ends — [Arch wiki: nftables](https://wiki.archlinux.org/title/Nftables)
- The wiki's own "Using iptables-nft" note: "quite a few things still depend on iptables to run (such as Docker's networking)", and `iptables-translate` can convert old rules into nft syntax — [Arch wiki: nftables](https://wiki.archlinux.org/title/Nftables#Using_iptables-nft)

**Ruleset building blocks (verbatim syntax from the wiki's server example)**
- Base chain: `type filter hook input priority filter; policy drop;` then `iif lo accept`, `ct state invalid drop`, `fib daddr . iif type != { local, broadcast, multicast } drop` (strong host model), `ct state { established, related } accept`, `meta l4proto { icmp, ipv6-icmp } accept`, `tcp dport ssh accept`; forward chain `policy drop`, output chain `policy accept` — [Arch wiki: nftables, Server example](https://wiki.archlinux.org/title/Nftables#Server)
- Rate limiting: `tcp dport ssh ct state new limit rate 15/minute accept` and ICMP `limit rate over 10/second burst 4 packets drop` — [Arch wiki: nftables](https://wiki.archlinux.org/title/Nftables#Limit_rate)
- Per-source dynamic blackhole: `ct state new meta l4proto { tcp, udp } th dport 443 meter flood_ipv4 size 128000 { ip saddr timeout 10s limit rate over 10/second } ...` (add to a blackhole set), and `update @set { ip saddr counter }` for per-IP counting — [Arch wiki: nftables](https://wiki.archlinux.org/title/Nftables#Dynamic_blackhole)
- Reload atomically with `nft -f /etc/nftables.conf` (file starts with `flush ruleset`) / `systemctl restart nftables`; save with `nft list ruleset` — [Arch wiki: nftables](https://wiki.archlinux.org/title/Nftables#Atomic_reloading)
- Port semantics to block: `rcon.port` default 25575 TCP, "The protocol is unencrypted, so use only on localhost"; `query.port` default 25565 **UDP**, `enable-query` default false; `enable-rcon` default false — [minecraft.wiki: Server.properties](https://minecraft.wiki/w/Server.properties)

**Docker's firewall bypass**
- "Docker routes container traffic in the nat table, so packets are diverted before they reach the INPUT and OUTPUT chains that ufw uses. Because of this, published ports can bypass ufw rules"; with firewalld Docker creates a `docker` zone with target ACCEPT and a `docker-forwarding` policy; setting `iptables`/`ip6tables` to false "is not appropriate for most users and is likely to break container networking"; "it is not possible to fully prevent Docker from creating firewall rules" — [Docker docs: Packet filtering and firewalls](https://docs.docker.com/engine/network/packet-filtering-firewalls/)
- `DOCKER-USER` is "A placeholder for user-defined rules that will be processed before rules in the DOCKER-FORWARD and DOCKER chains"; restrict external access with `iptables -I DOCKER-USER -i ext_if ! -s 192.0.2.2 -j DROP` (subnet / `-m iprange --src-range` variants; put a `RELATED,ESTABLISHED` accept before the drops); packets there are already DNAT-ed, so match original ports with `-m conntrack --ctorigdst ... --ctorigdstport 80` (performance cost) — [Docker docs: iptables](https://docs.docker.com/engine/network/firewall-iptables/)
- "Publishing container ports is insecure by default"; bind to loopback with `-p 127.0.0.1:8080:80` (older than 28.0.0, same-L2 hosts could still reach loopback-bound ports); change the default with `"ip": "127.0.0.1"` in `daemon.json` (default bridge) or `com.docker.network.bridge.host_binding_ipv4` for user-defined bridges; unpublished ports are blocked, published ports go to all host addresses — [Docker docs: Port publishing](https://docs.docker.com/engine/network/port-publishing/)
- nftables backend: "Docker 29.0.0 introduced the nftables firewall backend. It is experimental"; enable with `"firewall-backend": "nftables"`; it creates `ip docker-bridges` / `ip6 docker-bridges`; "DOCKER-USER ... does not exist under nftables. To replace it, create your own table with base chains" ordered by priority, or use `--bridge-accept-fwmark`; "An nftables accept is not final, so other base chains can still drop the packet"; Docker then does not enable IP forwarding itself; a leftover iptables `FORWARD` DROP policy can still block traffic — [Docker docs: nftables](https://docs.docker.com/engine/network/firewall-nftables/)
- Arch note: "nftables may block docker connections by default. Use `nft list ruleset` to check for blocking rules" (forward chain) — [Arch wiki: Docker](https://wiki.archlinux.org/title/Docker#Troubleshooting)

### Inferences
- A minimal `/etc/nftables.conf` for this box (assembled from the cited syntax; not itself a quoted source):
  ```
  flush ruleset
  table inet filter {
    set mc_abusers { type ipv4_addr; flags dynamic, timeout; timeout 10m; }
    chain input {
      type filter hook input priority filter; policy drop;
      iif lo accept
      ct state invalid drop
      ct state { established, related } accept
      meta l4proto { icmp, ipv6-icmp } accept
      iifname "tailscale0" tcp dport ssh accept          # admin path
      # tcp dport ssh ct state new limit rate 15/minute accept   # only if public SSH is kept
      tcp dport 25565-25569 ct state new add @mc_abusers { ip saddr limit rate over 10/minute } drop
      tcp dport 25565-25569 ct state new limit rate 30/minute burst 20 packets accept
      # nothing for 25575 (RCON) or udp 25565 (Query): policy drop covers them
    }
    chain forward { type filter hook forward priority filter; policy drop; }
    chain output  { type filter hook output  priority filter; policy accept; }
  }
  ```
  Numbers are placeholders to tune against real join rates (a class joining at once is ~20 new connections in a minute). The `meter`/dynamic-set form is the wiki's pattern for per-source limits.
- Because Docker's rules sit in `nat`/`FORWARD`, the input chain above does not protect containerised servers. If servers run in Docker, either publish only to `127.0.0.1` and front them with something that is in the host table, or write the equivalent restrictions in `DOCKER-USER` (iptables backend). Simplest for a one-admin box: run the JVMs as systemd services, not containers, so nftables `input` is the only path.
- Leave `enable-rcon=false`; if a panel needs RCON, bind it via `rcon.port` on a server with `server-ip=127.0.0.1`? No: `server-ip` also moves the game port. Instead rely on the firewall not opening 25575 and on a strong `rcon.password`, and prefer console-over-tmux/`systemd` stdin.

### Gaps
- No Arch-wiki or Docker-doc text gives a Minecraft-specific rate-limit figure; the numbers above are inferences.
- Docker's "direct routing"/`trusted_host_interfaces` behaviour for 29.x was only summarised, not read in full.

## Running Minecraft unprivileged: systemd hardening that works with Java, and the Docker equivalent

### Takeaway
Run each server as its own unprivileged user under a systemd unit with `ProtectSystem=strict` + `ReadWritePaths=<server dir>`, `ProtectHome=true`, `PrivateTmp=true`, `NoNewPrivileges=true`, `ProtectKernelTunables/Modules/ControlGroups`, `RestrictSUIDSGID`, `RestrictRealtime`, `LockPersonality`, `RestrictNamespaces`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`, `SystemCallFilter=@system-service`, `MemoryMax`/`CPUQuota`, and `TimeoutStopSec` long enough to save worlds. Do **not** set `MemoryDenyWriteExecute` (JIT). In Docker the counterparts are `--user uid:gid` (itzg defaults to 1000:1000), `--read-only` with a writable data volume and `--tmpfs /tmp`, `--security-opt no-new-privileges`, `--cap-drop ALL`, `--memory`, `--pids-limit`.

### Cited Findings
- `ProtectSystem=strict`: "the entire file system hierarchy is mounted read-only, except for the API file system subtrees"; `full` additionally makes `/etc/` read-only vs `true` (`/usr/` and boot loader dirs); "Use ReadWritePaths= in order to allow-list specific paths for write access if ProtectSystem=strict is used" — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- `PrivateTmp=true`: `/tmp/` and `/var/tmp/` "are not shared with processes outside of the namespace"; `disconnected` uses a fresh tmpfs; `NoNewPrivileges=true` "ensures that the service process and all its children can never gain new privileges through execve()"; `ProtectHome=true` makes `/home/`, `/root`, `/run/user` "inaccessible and empty"; `ProtectKernelTunables` makes `/proc/sys`, `/sys` read-only and hides `/proc/kallsyms`, `/proc/kcore`; `ProtectKernelModules`: "explicit module loading will be denied"; `ProtectControlGroups=true` makes `/sys/fs/cgroup/` read-only; `ProtectClock`, `ProtectHostname`, `LockPersonality`, `RestrictRealtime` ("any attempts to enable realtime scheduling... are refused"), `RestrictSUIDSGID`, `RestrictNamespaces=true` ("access to any kind of namespacing is prohibited"), `RestrictAddressFamilies` (applies to `socket()`, enforced on x86-64) — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- `SystemCallFilter=@system-service` is "A reasonable set of system calls used by common system services, excluding any special purpose calls"; denied calls kill with `SIGSYS` unless `SystemCallErrorNumber=` — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- `MemoryDenyWriteExecute` rejects `mmap(PROT_EXEC|PROT_WRITE)` and `mprotect(PROT_EXEC)` and is "incompatible with programs and libraries that generate program code dynamically at runtime" (JIT engines) — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html); a kernel developer notes the BPF filter is stateless so it "simply rejects any mprotect(PROT_EXEC)" — [LKML MDWE thread](https://lkml.iu.edu/2204.2/05883.html); linux-audit pairs it with blocking `memfd_create`, which is likely to break the JVM too — [linux-audit: MemoryDenyWriteExecute](https://linux-audit.com/systemd/settings/units/memorydenywriteexecute/)
- `LimitNOFILE=`: the man page table says "Do not use" and "Be careful when raising the soft limit above 1024" (select(2)); the hard limit now defaults to 524288; prefer `MemoryMax=` for memory control — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- `DynamicUser=` allocates a UID at start and implies `NoNewPrivileges`, `RestrictSUIDSGID`, `ProtectSystem=strict`, `ProtectHome=read-only`, `PrivateTmp=disconnected`; persistent data must go in `StateDirectory=` (`/var/lib/<name>`, owned by the unit's user, not removed on stop) — [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- A current (Debian 13, Paper) unit that a hosting company publishes uses exactly: `User=minecraft`, `WorkingDirectory=/opt/minecraft`, `ExecStart=/usr/bin/java @/opt/minecraft/aikars.flags -jar paper.jar nogui`, `Restart=on-failure`, `RestartSec=10`, `SuccessExitStatus=0 143`, `TimeoutStopSec=90` ("gives Paper time to save large worlds"), `NoNewPrivileges=true`, `ProtectSystem=strict`, `ReadWritePaths=/opt/minecraft`, `ProtectHome=true`, `PrivateTmp=true`, `ProtectKernelTunables=true`, `ProtectControlGroups=true`, `RestrictSUIDSGID=true` — [1337hosting: Minecraft server on Debian 13](https://1337hosting.com/tutorials/minecraft-server-debian-13-paper) (vendor tutorial)
- Another guide uses `SuccessExitStatus=0 130 143` and `ProtectSystem=full`; without 130/143 a normal stop leaves the unit "failed" — [Vultr docs: Paper on Ubuntu](https://docs.vultr.com/how-to-deploy-a-paper-minecraft-server-on-ubuntu-2004) (vendor); `systemd-analyze security <unit>` scores a unit and `systemd-run` lets you test a directive in a transient unit — [StackHarbor: systemd sandboxing](https://stackharbor.com/en/knowledge-base/systemd-service-sandboxing-hardening/)
- minecraft.wiki: "Only give out necessary permissions to run a Minecraft server" and don't run as superuser; it lists a third-party systemd service "that protects the server with read-only and inaccessible jails" — [minecraft.wiki: Setting up a Java Edition server](https://minecraft.wiki/w/Tutorial:Setting_up_a_Java_Edition_server)
- Docker: `--security-opt no-new-privileges` "Disable container processes from gaining new privileges"; `--read-only` "Mount the container's root filesystem as read only"; `--user <uid>[:<gid>]`; `--tmpfs`; `--memory`; `--cpus`; `--pids-limit`; `--init` "Run an init inside the container that forwards signals and reaps processes" — [Docker docs: docker container run](https://docs.docker.com/reference/cli/docker/container/run/)
- itzg/docker-minecraft-server (the de-facto image) "switches to user ID 1000 and group ID 1000" by default, overridable via `UID`/`GID` env or `--user`; RCON is enabled by default in that image — [docker-minecraft-server docs](https://docker-minecraft-server.readthedocs.io/en/latest/configuration/misc-options/); a scanner author found "only a few hundred servers with the RCON port open accepted the default 'minecraft' password" that the Docker image ships — [matdoes.dev: Minecraft server scanning](https://matdoes.dev/minecraft-scanning)
- Arch wiki on Docker isolation: by default containers share the daemon's user namespace; `"userns-remap": "default"` maps container UIDs to an unprivileged host range; rootless Docker (`docker-rootless-extras`, AUR) runs the daemon itself unprivileged — [Arch wiki: Docker](https://wiki.archlinux.org/title/Docker#User_namespace_isolation)

### Inferences
- A per-server template `minecraft@.service` with `User=mc-%i`, `WorkingDirectory=/srv/minecraft/%i`, `ReadWritePaths=/srv/minecraft/%i`, plus the hardening list above and `MemoryMax=` ≈ `-Xmx` + 1–2 GB, `CPUQuota=`, `TimeoutStopSec=120`, `SuccessExitStatus=0 143`, gives per-server isolation at the filesystem level: an op on server A who abuses `/function`/datapacks cannot touch server B's files. Run `systemd-analyze security minecraft@a.service` and expect a mid score; Java needs `AF_INET/AF_INET6/AF_UNIX`, writable `/tmp` (PrivateTmp suffices), and must not have MDWE.
- Fabric servers write `mods/`, `config/`, `logs/`, `world/` inside the server dir, so one `ReadWritePaths` entry covers them; if the JDK is outside `/usr` (e.g. a Prism-bundled runtime), it is still readable under `strict`.
- Docker equivalent: `--user 1000:1000 --read-only --tmpfs /tmp -v data:/data --security-opt no-new-privileges --cap-drop ALL --memory 6g --pids-limit 512` and **change the image's default RCON password or set `ENABLE_RCON=false`**; never publish 25575.

### Gaps
- No source tested the full `@system-service` filter against Java 25/Fabric 26.3; treat the filter list as "start here and relax if the JVM dies with SIGSYS" (check `journalctl -u` for `SYSCALL` lines).
- `itzg` docs on read-only root fs and `SKIP_CHOWN` were not reached in the fetched page.

## Minecraft-level: online-mode, whitelist, op levels, secure profiles/chat, command blocks and `/function` with op kids, RCON, Query, log-ips, logs

### Takeaway
`online-mode=true` is non-negotiable on the internet (offline mode lets anyone log in under an op's name, and scanners actively try known admin names), `white-list=true` (now the 26.3 default) + `enforce-whitelist=true`, `enforce-secure-profile=true` (default; unsigned chat is logged `[Not Secure]` and can't be reported). Op level 2 is enough for `/function`, `/give`, `/tp`, `/gamemode`, `/dialog`, command blocks; level 3 adds `/op`, `/ban`, `/kick`, `/whitelist`; level 4 adds `/stop`, `/save-all`, `/perf`, `/jfr`. Give kids level 2 (set `op-permission-level=2` so a stray `/op` can't hand out more), keep `function-permission-level=2`, and accept that a level-2 op can wreck the world (`/fill`, `/kill @e`, `/gamerule`, datapack commands) but not the host; isolate each class/server in its own unit and keep backups. Disable RCON and Query, leave `log-ips=true`, and keep the gzipped `logs/` for incident review.

### Cited Findings
**server.properties (26.3 wiki, defaults)**
- `online-mode` default true: "Only players verified with the Minecraft account database can join. Disabling it is for offline use only, since it lets unverified accounts connect" — [minecraft.wiki: Server.properties](https://minecraft.wiki/w/Server.properties)
- `white-list` default **true** ("Default changed to true in 26.3 Snapshot 2"); "Ops are automatically whitelisted"; `enforce-whitelist` default false: players not on the list "are kicked after the whitelist reloads" — [minecraft.wiki: Server.properties](https://minecraft.wiki/w/Server.properties); hosting blogs quote the 26.3 changelog line "The white-list property is now true by default" and note upgraded servers keep their existing value — [Nodecraft: 26.3 for your server](https://nodecraft.com/blog/game-news-tips/minecraft-java-26-3-wilderness-bound-is-out-what-it-means-for-your-server), [space-node 26.3 guide](https://space-node.net/blog/minecraft-26-3-server-update-guide-2026) (vendor blogs)
- `op-permission-level` default 4 (0–4, applied by `/op`); `function-permission-level` default 2 (1–4, since 1.14.4-pre4); `enforce-secure-profile` default true: "Only players with a Mojang-signed public key can join. If disabled, chat is unsigned and cannot be reported"; `enable-rcon` false, `rcon.password` blank ("If RCON is enabled and this is blank, RCON will not start"), `rcon.port` 25575, `broadcast-rcon-to-ops` true, `broadcast-console-to-ops` true, `enable-query` false, `query.port` 25565 UDP, `log-ips` true (1.20.2) "Shows client IP addresses in console and log output", `prevent-proxy-connections` false (kicks players whose ISP/AS differs from Mojang's view), `hide-online-players` false, `rate-limit` 0 (packets before kick), `enable-status` true ("If false, the server appears offline but still accepts connections"), `accepts-transfers` false, `player-idle-timeout` 0, `pause-when-empty-seconds` 60, `max-players` 20; `enable-command-block` was **removed in 25w35a** in favour of a game rule — [minecraft.wiki: Server.properties](https://minecraft.wiki/w/Server.properties)

**Why offline mode is dangerous; whitelist only works with online mode**
- "Whitelist only works with online mode. Offline mode servers make whitelist ineffective, as players can join with a different username included in the whitelist"; "Be careful giving any player an operator status"; scanners target default ports, so the wiki suggests a non-default port + SRV record, `enable-status=false` to hide from status-ping scanners, default game mode Adventure to limit griefing, and LAN/VPN for private play — [minecraft.wiki: Setting up a Java Edition server](https://minecraft.wiki/w/Tutorial:Setting_up_a_Java_Edition_server)

On offline-mode servers with a whitelist, it may use a username of a player who has previously been online" — [matscan FAQ](https://matdoes.dev/matscan.md)
- Velocity docs: a backend in offline mode means "someone could impersonate any player on your server", hence the firewall / localhost-bind / forwarding-secret requirements (details in the DDoS section) — [Velocity docs: Security](https://docs.papermc.io/velocity/security/)

**Op levels and blast radius**
- Levels are cumulative. 0: TPS graph, see command-block/console output; 1: bypass spawn protection; 2 ("Gamemaster"): "Use command blocks. Open Test Blocks GUIs. - `hide-online-players=true` hides the player list from status requests — [minecraft.wiki: Server.properties](https://minecraft.wiki/w/Server.properties)

**RCON, Query, logs**

### Inferences
- Concrete settings for this program: `online-mode=true`, `white-list=true`, `enforce-whitelist=true`, `enforce-secure-profile=true`, `op-permission-level=2`, `function-permission-level=2`, `enable-rcon=false`, `enable-query=false`, `log-ips=true`, `hide-online-players=true` (keeps kids' names out of status pings), `enable-status` left true unless you want the server list to show it offline, `rate-limit` a few hundred to kick packet floods from a single client, `player-idle-timeout` 30 to free slots. Optionally `prevent-proxy-connections=true` (kids all join from the studio or home, so VPN-via-proxy false positives are unlikely, but test).
- A level-2 op kid can: run every datapack function (`/function`), `/reload`, `/datapack disable`, `/gamerule`, `/fill`/`/clone` up to 32768 blocks per command, `/kill @e`, `/tp` everyone, `/give` anything, `/gamemode` anyone, `/summon` lag machines, `/dialog` other players, and place command blocks (`command_blocks_work` true) that keep running after they leave; they **cannot** `/op`, `/ban`, `/kick`, `/whitelist`, `/stop`, or touch the host. Blast radius = that one world, its performance, and other kids' experience. Mitigations: per-server systemd user + dir (no cross-world damage), hourly world backups (rolling), `max_command_forks`/`max_command_sequence_length` lowered for lag-bomb resistance, a teacher account at level 4, `log_admin_commands` on so the `latest.log` shows who ran what, and `command_blocks_work=false` on servers where the datapacks don't need command blocks (Command Forge section 2 does, so leave it on there only).
- Because `/op` from a level-2 op fails, `op-permission-level=2` also prevents the "kid ops their friend" cascade; existing `ops.json` entries keep their stored level, so edit them when lowering.
- Chat signing matters for a kids' server for two reasons: reports to Mojang remain possible (signed), and the `[Not Secure]` log tag is your signal that a client-side mod (e.g. No Chat Reports) or an offline-mode path is in play.
- Logs: vanilla rotates `logs/latest.log` into dated `.log.gz` files; keep them (they are small) for at least a school term, since a parent complaint may arrive weeks later; with `log-ips=true` they contain IPs, so treat the directory as personal data (see privacy section).

- minecraft.wiki does not state what permission level command blocks execute at in Java (they behave as level 2 in practice; not confirmed by the fetched pages).
- Not verified from a primary source: the exact 26.3 `logs/` rotation naming (`YYYY-MM-DD-N.log.gz`).
- `text-filtering-config` is Realms-internal ("Mojang has not announced it for outside use"); no supported server-side chat filter for a vanilla/Fabric server was found in these sources.

## DDoS/griefing exposure of a home IP, tunnels (playit.gg) and a Velocity proxy on a VPS, internet-wide scanners and why whitelist+online-mode matters immediately

### Takeaway
Any open 25565–2557x port is found by whole-IPv4 scanners within hours to days, and griefing groups run their own; a status ping leaks MOTD, version and online player names unless `hide-online-players`/`enable-status` are set. Whitelist + online-mode stops joins; nothing stops the port being found. A Velocity proxy on a VPS (backend firewalled to the VPS IP, modern forwarding with a secret, Fabric needs FabricProxy-Lite) or an outbound tunnel (playit.gg) hides the home IP from players, so a grudge-DDoS hits the VPS/tunnel rather than the studio connection; neither is "DDoS protection" by itself, and the backend must never be reachable directly because it runs offline-mode behind the proxy.

### Cited Findings
- Scanner mechanics: the author "borrowed Bithole's masscan fork and modified it to scan for Minecraft servers on every port, not just 25565"; a full-IPv4 pass took "several hours" from a cloud VPS; a second machine re-checks known servers hourly; the database "also stores players seen online"; the honeypot was pinged by Souper, Natekomodo, Shodan and joined by bots with random names, a griefer, and Copenheimer users "including its lead developer"; the LiveOverflow server "was not whitelisted, so it appeared in Shodan results and was joinable" — [matdoes.dev: Minecraft server scanning (2022)](https://matdoes.dev/minecraft-scanning)
- matscan: "several griefing and harassment groups run their own scanners, so securing your server matters even though matscan's data isn't public"; recommendations: backups + CoreProtect-style rollback, whitelist for private servers, online-mode or an auth plugin, restrict BungeeCord backends / use BungeeGuard or Velocity; it joins from 151.115.73.107 — [matscan FAQ](https://matdoes.dev/matscan.md)
- Copenheimer "scans all the IPv4 addresses in order to find Minecraft servers exposed to the internet"; the original is closed-source, OpenHeimer is a public reimplementation — [OpenHeimer on pkg.go.dev](https://pkg.go.dev/github.com/ecstaticedit/openheimer); anti-scanner mods exist (ServerHider "PLEASE use Whitelist with this plugin!", Sneaky Server shows status only to players who have joined before, AntiScan "meant to be used in conjunction with online mode and a whitelist", Anti MOTD Scanner "cannot stop TCP port scans or scanners that join with real accounts") — [Modrinth: ServerHider](https://modrinth.com/mod/serverhider), [Sneaky Server](https://www.modpackindex.com/mod/113911/sneaky-server), [AntiScan](https://www.modpackindex.com/mod/115435/antiscan), [Anti MOTD Scanner](https://modrinth.com/mod/anti-motd-scanner)
- Forum anecdotes: a self-hoster "got griefed within two weeks of running without [a whitelist]"; another enabled it after a stranger joined; one Aternos user saw scanner accounts from a known griefing group — [blendit.bsd.cafe thread](https://blendit.bsd.cafe/comment/1401860), [Aternos board thread](https://board.aternos.org/thread/13274-hackers-on-my-aternos-server/) (anecdotal)
- Velocity on a VPS: the only reply in the PaperMC thread says that with no Velocity flaw the home IP "would be safe" and "The home network would be protected from DDoS attacks, but the proxy would not be" — [PaperMC forums thread (March 2025)](https://forums.papermc.io/threads/protecting-my-home-ip-with-velocity-proxy-%E2%80%93-am-i-safe.1591/)
- Velocity security doc: backends run offline-mode so "someone could impersonate any player"; "strongly recommends the use of a firewall" so only the proxy reaches backends; modern forwarding (1.13+; Paper or **FabricProxy-Lite for Fabric**) adds impersonation protection but "is not a replacement for a firewall" and relies on the forwarding secret; if proxy and backend share a machine set `server-ip=127.0.0.1`; encrypted tunnels (WireGuard etc.) are the heavy option; IP-whitelist plugins are a last line — [Velocity docs: Security](https://docs.papermc.io/velocity/security/)
- A DDoS-filter vendor's guide: if an attacker learns the backend's direct address they bypass the filter and attack directly — [MineGuard blog (vendor, German)](https://mineguard.pro/de/blog/velocity-ddos-protection-minecraft-network-guide)
- playit.gg: the agent opens an outbound tunnel so no router port is forwarded and the home IP is not shown; free tier of up to three tunnels (user blog, not independent) — [teklynk blog](https://www.teklynk.com/blog/how-to-host-a-game-server-from-your-home-using-playItgg); playit's own docs: "The Proxy Protocol provides a way for your server to receive your client's true IP" (Velocity/Paper/Geyser guides), Premium adds regional tunnels and custom domains, a "How to lower ping" guide routes players to the nearest datacenter — [playit.gg support index](https://playit.gg/support/), [playit.gg: Proxy Protocol in Velocity](https://playit.gg/support/proxy-protocol-velocity/) (warns normal clients can't connect once proxy protocol is required)
- r/admincraft advice (via mirror): rent a DDoS-protected VPS and GRE-tunnel to home; a replier found GRE needs a dedicated home IP — [redlib mirror of r/admincraft](https://redlib.belloworld.it/r/admincraft/comments/1g6im4p/how_do_i_hide_my_ip) (anecdotal)
- Tailscale Funnel cannot carry Minecraft: it "only works over TLS-encrypted connections" on ports 443/8443/10000 — [Tailscale KB: Funnel](https://tailscale.com/kb/1223/funnel)

### Inferences
- Threat ranking for a studio box: (1) random scanner joins/bot floods on an open, unwhitelisted or offline-mode port (certain, within days); (2) a kid or sibling sharing the IP and a grudge-booter (plausible, home-connection DDoS is cheap); (3) targeted intrusion of the host (unlikely if SSH is keys-only/Tailscale and nothing else is exposed).
- Cheapest structural fix for (2): never give out the home IP. Options in rising effort: playit.gg tunnel (zero router config, free tier, kids connect to a `*.ply.gg` name, the server sees the tunnel's IP unless you add proxy protocol via Velocity); Velocity on a $5 VPS with the home backend reachable only from the VPS IP (nftables `ip saddr <vps> tcp dport 25565 accept`, everything else dropped) and FabricProxy-Lite on each Fabric backend; or Tailscale for everyone (kids install Tailscale, no public port at all; practical only for a small, parent-managed group).
- Even behind a proxy/tunnel, keep `online-mode` on the proxy, whitelist on the proxy or backends, and `enforce-secure-profile`; the backend being offline-mode is exactly why its port must not be reachable from anywhere but the proxy.
- "Within hours" is consistent with the sources (full-IPv4 sweep in hours, hourly re-checks, multiple groups) even though no source states a measured time-to-first-bot for a brand-new port.

### Gaps
- No independent measurement of playit.gg's or a cheap VPS's actual DDoS absorption; vendor and anecdotal only.
- No 2025–2026 r/admincraft thread with a documented offline-mode breach was retrievable (Reddit blocks fetches; mirrors returned only the IP-hiding thread).
- playit.gg's official free-tier limits and IP-masking claim were not read from playit's own pages (index page only).

## Child safety and privacy: chat logs, who sees whom, Allow Server Listings / profile keys, Microsoft child-account rules, COPPA-flavoured points for a US studio

### Takeaway
Treat usernames, UUIDs, IPs, and chat logs as children's personal data: keep them only as long as needed, on the encrypted host, and write that down. Microsoft child accounts (under 16 in the US) have multiplayer and messaging gated by a parent in Xbox privacy settings, so parents must flip "join multiplayer games" (and chat if you use it) before a kid can join your server at all; Realms is not required. Players' names appear in server status pings unless the server hides them (`hide-online-players`) or the client turns off "Allow Server Listings". COPPA applies to commercial operators collecting personal info from under-13s; the 2025 amendments (compliance date 22 April 2026) add a written retention policy inside the privacy notice; persistent identifiers used solely for "internal operations" are an exception. Not legal advice.

### Cited Findings
- Microsoft/Mojang parental controls: accounts "for users under 16 in the US and EU (19 in South Korea) count as child accounts"; "Only the parent account can edit these controls"; settings live on the Xbox account site under the child's gamertag; under Online Safety a parent can allow joining multiplayer games and clubs; the Privacy tab controls who can message/invite (Everyone / Friends / Block); features exist in 1.16.4+ and "not for modded versions"; a separate article "Managing Multiplayer Game Access for a Child Account in Minecraft" covers consent and Realms/multiplayer access — [help.minecraft.net: Parental controls](https://help.minecraft.net/en-us/article/parental-controls) (quoted via search summary; full article fetch timed out)
- A Microsoft Q&A answer: parent signs in to Xbox privacy & online safety, selects the child, allows multiplayer, then the child must sign out of Minecraft and restart; a related case stayed blocked until Family Safety "play games rated up to" content restrictions were raised — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5510567/how-to-enable-multiplayer-settings-for-minecraft-f); Bark's guide says blocking multiplayer "stops the child from joining any multiplayer games in Minecraft — even shared local worlds, realms, or servers" and that chat/invite settings are separate — [Bark parental guide](https://www.bark.us/tech-guide/gaming-minecraft/) (secondary)
- Client "Allow Server Listings" (default ON) "Controls whether your player name appears in server listings"; "Only Show Secure Chat" hides unverifiable messages; "Chat: Hidden" turns off chat on all servers — [minecraft.wiki: Options](https://minecraft.wiki/w/Options); server-side `hide-online-players=true` hides the player list in status requests — [minecraft.wiki: Server.properties](https://minecraft.wiki/w/Server.properties)
- Chat reporting: reports go to Mojang moderators and can lead to online-play bans; reports need signed chat (`enforce-secure-profile=true`) — [minecraft.wiki: Java Edition 1.19.1](https://minecraft.wiki/w/Java_Edition_1.19.1); `enforce-secure-profile=false` means "chat is unsigned and cannot be reported" — [minecraft.wiki: Server.properties](https://minecraft.wiki/w/Server.properties)
- COPPA FAQ: "The Rule was designed to protect children under age 13"; personal information includes "a screen or user name that functions as online contact information" and persistent identifiers such as "an IP address"; it covers "the passive tracking of children's personal information through a persistent identifier"; consent must come "before collecting personal information online from children under 13, unless an exception applies"; "email plus" is acceptable for internal-use-only data, stronger methods when disclosing to third parties; persistent identifiers used for "the sole purpose of providing support for the internal operations" are exempt; retain data "for only as long as is necessary to fulfill the purpose for which it was collected"; "COPPA expressly states that the law applies to commercial websites and online services" (nonprofits generally excluded unless operating for members' profit); civil penalties "up to $53,088 per violation"; the Rule "was amended on April 22, 2025" — [FTC: Complying with COPPA FAQ](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions)
- Amended rule timeline: effective June 23, 2025 with a 365-day grace period ending April 22, 2026; operators must maintain a written retention policy under §312.10 stating purposes, retention periods and deletion procedures, placed inside the online privacy notice (a link to a separate doc does not satisfy it); no fixed retention period but indefinite retention is barred — [Fenwick: amended COPPA and data retention](https://www.fenwick.com/insights/publications/what-the-amended-coppa-rule-means-for-data-retention-practices), [Toy Association: COPPA requirements take effect April 22](https://toyassociation.org/PressRoom2/News/2026-News/updated-coppa-rule-requirements-take-effect-april-22.aspx) (law-firm/industry summaries)
- Chat is server-logged: `[Not Secure]` tags, `log_admin_commands`, and `log-ips` all land in `latest.log` — [minecraft.wiki: Java Edition 1.19.1](https://minecraft.wiki/w/Java_Edition_1.19.1), [minecraft.wiki: Server.properties](https://minecraft.wiki/w/Server.properties)

### Inferences
- Practical privacy posture: whitelist by username (collected from parents on the sign-up form), keep `logs/` for a fixed window (e.g. the term + 90 days) then delete, store them only on the LUKS-encrypted host, don't publish a public status page that shows player names, set `hide-online-players=true`, and ask parents to turn on only "join multiplayer games" (leave messaging at Friends if your activities don't need text chat; the datapacks here are chat-driven, so you probably need chat on and should say so).
- A whitelist is itself a list of children's usernames tied to UUIDs: it is data you hold. Keep sign-up forms minimal (child's Minecraft username + parent contact).
- Whether COPPA formally applies depends on whether the studio is a commercial operator "directed to children" collecting online; a one-page privacy notice with a retention statement, parent email consent, and no third-party sharing is the proportionate posture regardless. Confirm with counsel or a COPPA safe-harbor program if the studio charges fees.

## Remote admin workflow: SSH + tmux, Tailscale, panel on the tailnet only, Mosh; monitoring/alerting (systemd failure email, Uptime Kuma, mcstatus) and centralised logs

### Takeaway
Reach the box only over Tailscale (Tailscale SSH or sshd on `tailscale0`), run each server under systemd (console via `journalctl -fu minecraft@x` and commands via a stdin FIFO or an RCON bound to localhost if you must), use tmux only as a personal scratchpad, and if you want a web panel put it behind `tailscale serve` so it never has a public URL. Mosh needs UDP 60001–60999 and is pointless over Tailscale. For alerts: `OnFailure=status_email@%n.service` on each unit, and Uptime Kuma (TCP-port monitor on 25565, or a Push monitor fed by a `mcstatus` cron) with its UI bound to `127.0.0.1:3001` and served over the tailnet. Centralised logs for one box = journald with persistent storage plus the Minecraft `logs/` dir in the backup set.

### Cited Findings
- Tailscale Serve proxies tailnet traffic to a local service over HTTPS with automatic certs (`tailscale serve 3000` → `https://<device>.<tailnet>.ts.net`); "Only devices and users within your tailnet" can reach it and ACLs apply; requests carry identity headers such as `Tailscale-User-Login`; Funnel is the public variant and the two cannot share a port — [Tailscale KB: Serve](https://tailscale.com/kb/1312/serve), [Tailscale KB: Funnel](https://tailscale.com/kb/1223/funnel)
- Tailscale SSH `check` mode and session recording as described above — [Tailscale KB: Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)
- Mosh "uses UDP on the transport layer with AES-128 OCB mode encryption", authenticates via OpenSSH, and "sessions by default use the first available UDP port in the 60001-60999 range, so it should be accessible in the server" — [Arch wiki: Mosh](https://wiki.archlinux.org/title/Mosh)
- systemd has "no built-in equivalent to cron's MAILTO"; the wiki's recipe is `/usr/local/bin/systemd-email` (a `sendmail -t` script that mails `systemctl status --full "$2"`), a template `status_email_user@.service` (`Type=oneshot`, `ExecStart=/usr/local/bin/systemd-email address %i`), and `OnFailure=status_email_user@%n.service` in the watched unit's `[Unit]`; a sendmail provider from `smtp-forwarder` packages is required — [Arch wiki: systemd — Notifying with e-mail](https://wiki.archlinux.org/title/Systemd#Notifying_with_e-mail), [Arch wiki: systemd/Timers](https://wiki.archlinux.org/title/Systemd/Timers)
- Uptime Kuma monitor types: HTTP(s), TCP, HTTP keyword/JSON, WebSocket, Ping, DNS, **Push**, Steam Game Server, Docker containers (no Minecraft-specific type listed); notifications via Telegram, Discord, Slack, Pushover, email/SMTP and "90+" services; runs on port 3001, docker-compose or Node ≥ 20.4; restrict with `-p 127.0.0.1:3001:3001`; 2FA is a feature; no NFS for its data dir — [Uptime Kuma on GitHub](https://github.com/louislam/uptime-kuma)
- `mcstatus` is a Python library/CLI that queries Java servers via Server List Ping and Query (`JavaServer.lookup(...).status()` returns player counts and latency) — [mcstatus on PyPI](https://pypi.python.org/pypi/mcstatus/)
- Arch's maintenance page: check failed units with `systemctl --failed` and the journal regularly; `checkservices` to restart processes with stale libraries after upgrades — [Arch wiki: System maintenance](https://wiki.archlinux.org/title/System_maintenance#Check_for_errors)
- minecraft.wiki: keep the server, mods and backups current; the Linux section notes a third-party systemd unit that performs "safe stop and restart operations using rcon" — [minecraft.wiki: Setting up a Java Edition server](https://minecraft.wiki/w/Tutorial:Setting_up_a_Java_Edition_server)

### Inferences
- Workflow that fits one admin: Tailscale on the box and on the laptop/phone; `tailscale set --ssh` with a `check` rule (`checkPeriod` ~12h) for the admin user; nftables accepts SSH only on `tailscale0`; `systemctl status 'minecraft@*'`, `journalctl -fu minecraft@classA`, and a small `mc` helper that writes commands to the server's stdin (systemd `StandardInput=` with a FIFO, or `tmux send-keys` if the unit runs the JVM inside tmux) so RCON can stay off. If a panel (e.g. Crafty) is wanted, bind it to localhost and publish with `tailscale serve --bg 8443`.
- Monitoring that is enough: Uptime Kuma in Docker bound to `127.0.0.1:3001` + `tailscale serve`, one TCP monitor per game port, one Push monitor fed by a `systemd` timer running `mcstatus <host>:<port> status` so you also catch "port open but server hung"; notifications to email and a phone channel; `OnFailure=` email on each `minecraft@` unit and on `nftables.service`; persistent journald (`Storage=persistent`) and the `logs/` directories in the nightly backup give you the incident-review trail without a log server.
- Mosh adds nothing once SSH rides Tailscale (WireGuard already survives roaming); skip it rather than open a UDP range.

- No source compared Crafty / Pterodactyl / MineOS security for a Tailscale-only deployment; left as an inference.
- No source was found for a ready-made `OnFailure` + ntfy/Discord webhook pattern on Arch; the wiki recipe is email via sendmail only.
