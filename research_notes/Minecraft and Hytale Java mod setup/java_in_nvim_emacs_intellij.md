## Key question 1 — Neovim 0.12: nvim-jdtls vs plain `vim.lsp.config`, Mason vs Arch package, JDK for jdtls, workspaces, DAP, Lombok, Gradle import, decompiler, Minecraft-sized projects

### Takeaway
Use `nvim-jdtls` on top of Neovim's built-in `vim.lsp` (it adds the jdt:// decompiled-class handler, refactor commands, DAP wiring, and test runners that plain `vim.lsp.enable('jdtls')` lacks), install `jdtls`, `java-debug-adapter` and `java-test` through Mason (the Mason jdtls package also ships `lombok.jar`), and run jdtls on the system JDK 27 (jdtls needs ≥ 21; 1.62.0 added Java 27). The real friction for Minecraft mods is not jdtls itself but the Gradle side: the Fabric template's Gradle 9.7.1 wrapper does not run on Java 27, so a JDK 25 must be installed and handed to Gradle, and `genSources` output is attached by hand.

### Inferences
- Minimal working nvim-jdtls setup for this machine (Mason route; everything cited above). In `lazy-plugins.lua` add `{ 'mfussenegger/nvim-jdtls', dependencies = { 'mfussenegger/nvim-dap' } }`, add `"jdtls"` to the Mason `ensure_installed` (via `mason-tool-installer` or `:MasonInstall jdtls java-debug-adapter java-test`), and keep jdtls **out** of mason-lspconfig's automatic enabling (`automatic_enable = { exclude = { 'jdtls' } }`), because nvim-jdtls's README says not to call `vim.lsp.enable('jdtls')` when using `start_or_attach`. Then `~/.config/nvim/ftplugin/java.lua`:

  ```lua
  local mason = vim.fn.stdpath('data') .. '/mason'
  local root = vim.fs.root(0, { 'gradlew', 'mvnw', '.git' }) or vim.fn.getcwd()
  local ws = vim.fn.stdpath('cache') .. '/jdtls-ws/' .. vim.fn.fnamemodify(root, ':p:h:t')
  local bundles = {}
  vim.list_extend(bundles, vim.split(vim.fn.glob(mason .. '/share/java-debug-adapter/*.jar'), '\n', { trimempty = true }))
  vim.list_extend(bundles, vim.split(vim.fn.glob(mason .. '/share/java-test/*.jar'), '\n', { trimempty = true }))
  require('jdtls').start_or_attach {
    name = 'jdtls',
    cmd = {
      mason .. '/bin/jdtls',
      '--jvm-arg=-javaagent:' .. mason .. '/packages/jdtls/lombok.jar',
      '--jvm-arg=-Xmx4G',
      '-data', ws,
    },
    root_dir = root,
    settings = {
      java = {
        import = { gradle = { wrapper = { enabled = true }, ['java'] = { home = '/usr/lib/jvm/java-25-openjdk' } } },
        configuration = { runtimes = {
          { name = 'JavaSE-25', path = '/usr/lib/jvm/java-25-openjdk', default = true },
          { name = 'JavaSE-27', path = '/usr/lib/jvm/java-27-openjdk' },
        } },
        contentProvider = { preferred = 'fernflower' },
      },
    },
    init_options = { bundles = bundles },
    on_attach = function(client, bufnr) -- reuse the kickstart on_attach keymaps here, plus:
      vim.keymap.set('n', '<leader>jo', require('jdtls').organize_imports, { buffer = bufnr, desc = 'organize imports' })
      vim.keymap.set('n', '<leader>jt', require('jdtls').test_nearest_method, { buffer = bufnr, desc = 'test method' })
    end,
  }
  ```
  Reasoning behind each line: `-Xmx` is unset by `jdtls.py` so a large mod project (Loom pulls Minecraft + hundreds of library jars) should get an explicit cap; `java.import.gradle.java.home` must point at a JDK ≤ 26 because the Fabric template's Gradle 9.7.1 cannot run on Java 27 (compatibility table) while jdtls itself is fine on 27 (jdtls 1.62.0 added Java 27 support; `jdtls.py` has explicit Java-24+ handling); the `java-test` share dir is used as a whole, so the two excluded jars named in the README should be filtered if present (the Mason share dir links `extension/server/` wholesale). The `javaagent` Lombok flag is only needed for projects that use Lombok (rare in mods); `java.jdt.ls.lombokSupport.enabled` defaults to true and loads Lombok from the project classpath, which may make the agent flag unnecessary — unverified.
- `java.import.gradle.java.home` vs `JAVA_HOME`: Buildship inside jdtls runs the project's Gradle wrapper (`java.import.gradle.wrapper.enabled` true by default), so the JDK that runs Gradle is the one in that setting (or `org.gradle.java.home` in `gradle.properties`), separate from the JDK that runs jdtls. With JDK 27 as system default and no override, importing the Fabric 26.3 template through jdtls should fail at the Gradle step the same way `./gradlew` would in a terminal (inference from the compatibility table; not reproduced).
- Plain `vim.lsp.enable('jdtls')` via nvim-lspconfig works for completion/diagnostics and even picks a per-project workspace dir, but go-to-definition into a library class returns a `jdt://` URI that Neovim core cannot open yet (issue #39526 open), so the jump fails silently without nvim-jdtls's `java/classFileContents` handler. This makes nvim-jdtls effectively mandatory for Minecraft work, where most jumps land in Minecraft/Fabric API jars.
- `genSources` for jdtls: Loom produces a `*-sources.jar` next to the mapped Minecraft jar; jdtls/Buildship attaches sources that Gradle reports, but no source documents whether the Loom-generated jar is attached automatically in jdtls. Expect to need the vscode-java-style `java.project.sourcePaths`/attach-source workflow or to rely on FernFlower decompilation of Minecraft classes (which works but loses Javadoc/parameter names). Treat as unverified.
- Mason vs AUR: both give jdtls 1.61.0 today; Mason adds `lombok.jar`, the `java-debug-adapter`/`java-test` jars, and a stable path layout that config snippets (LazyVim, nvim-lspconfig docs) assume; AUR keeps it under pacman and `jdtls` on PATH. Either runs on the system JDK 27.
- Memory: `-Xms1G` and no `-Xmx` means the JVM default max heap (¼ of RAM) applies; on a Minecraft project jdtls commonly needs several GB, so set `-Xmx` explicitly (same knob lsp-java and eglot-java expose as `-Xmx1G` defaults, which is too small for a mod project).

## Key question 2 — Emacs 31: lsp-java vs eglot + eglot-java, dap-mode, jdtls source, Gradle from Emacs, evil/use-package, java-ts-mode, Gradle 9 / JDK 25 limits

### Takeaway
Both routes wrap the same jdtls and both still use the old `java/classFileContents` request (which jdtls 1.61+ keeps answering), so decompiled navigation works in both. `lsp-java` 4.0 (Emacs ≥ 29.1, lsp-mode ≥ 10, dap-mode ≥ 0.5) auto-downloads jdtls 1.57.0, registers `java-ts-mode`, and gives you `dap-java` with test debugging; `eglot-java` 1.35 is lighter, auto-installs the current Homebrew-stable jdtls, runs Gradle tasks/tests, but registers only `java-mode` in its own code and leaves debugging to `dape` plus a hand-supplied java-debug jar. Both default to `-Xmx1G`, which must be raised for a Minecraft workspace.

## Key question 4 — Shared: which JDK runs the tool vs the project, Gradle toolchains, formatting, git ignores

### Takeaway
Three JDK roles must be kept apart: the JVM that runs jdtls/IDEA (any ≥ 21; JDK 27 is fine for jdtls 1.62, IDEA ships its own runtime), the JVM that runs the Gradle daemon (bounded by the project's wrapper version — Gradle 9.7.1 tops out at Java 26, so JDK 27 cannot run the Fabric template), and the compile/toolchain JDK the build asks for (25 for Minecraft 26.x and Hytale). ### Inferences
- For a beginner learning Java through Minecraft/Hytale: use IntelliJ IDEA (free unified edition, pacman package) with the Minecraft Development plugin for the first months. The reasons are concrete, not taste: the official docs' screenshots and steps match it; the plugin understands `@Mixin`/`@Inject`/`@Shadow` and access wideners, which plain jdtls treats as ordinary annotations and strings (so a typo in a Mixin target is a runtime crash, not a red squiggle); Gradle run configurations (`runClient`) and the debugger work without any config; and the inspections teach Java idioms while you type.
- Neovim or Emacs is reasonable from day one *if* the person already lives in that editor and is willing to debug tooling: the cited Neovim configs and the Emacs packages show it works, and go-to-definition into decompiled Minecraft works through nvim-jdtls / lsp-java / eglot-java. Expect to run `./gradlew genSources` and `runClient` from a terminal, to tune `-Xmx` and the Gradle JVM by hand, and to live without Mixin validation.
- A sensible split for Dave's situation (JDK 27 default, kickstart Neovim, Emacs 31): IDEA for the student's first Minecraft/Hytale projects and for anything Mixin-heavy; Neovim with the nvim-jdtls ftplugin above for his own editing of the same Gradle project (both editors can open the same checkout; the `.gitignore` already hides each one's files); Android Studio (already installed as flatpak) for FTC.
