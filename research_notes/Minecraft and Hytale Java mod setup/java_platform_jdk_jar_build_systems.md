## Key question 1: JDK vs JRE vs JVM, distributions, LTS cadence, the tools, and which JDK runs a tool vs compiles your code

### Takeaway
A JDK is a JRE plus the compiler and developer tools; the JVM is the bytecode interpreter inside both. OpenJDK is the one open-source codebase (GPLv2 + Classpath Exception); every "distribution" (Oracle JDK, Temurin, Microsoft, Corretto, Arch's `jdk*-openjdk`, JetBrains Runtime) is a build of it. Feature releases ship every six months; LTS releases are 17, 21, 25 (next presumably 29); JDK 27 (GA 2026-09-15) is a non-LTS feature release. A separate question from "which JDK is installed" is "which JDK does each tool use": Gradle itself needs JVM 17–27, and the toolchain block decides what compiles your code.

### Inferences
- "LTS" is a vendor support promise, not something in the OpenJDK source; the OpenJDK project page for 27 says nothing about LTS because support windows are decided by Oracle, Adoptium, and other distributors. The two-year LTS rhythm (17 → 21 → 25) implies 29 in September 2027; 27 is a feature release that will stop getting updates when 28 ships (March 2027).
- Three different "which JDK" decisions exist in one project: the JDK that runs Gradle (must be 17–27 for Gradle 9.8), the toolchain JDK that compiles/tests (set in `build.gradle`), and the `--release`/`sourceCompatibility` level that controls bytecode and language level. The IDE's "project SDK" is a fourth view that must agree with the toolchain or the editor shows false errors.

## Key question 2: Which JDK: OpenJDK, Adoptium Temurin, or Oracle JDK (distribution comparison)

### Takeaway
OpenJDK is the source project; all mainstream JDKs are builds of it that pass the same compatibility tests, so for Minecraft mods and FTC builds the vendor doesn't change behaviour. The practical difference is licensing and update length: Oracle JDK's free NFTC window for an LTS ends one year after the next LTS ships, whereas Temurin, Microsoft, Corretto, and Arch's packages give free updates for years. On this Arch machine, install `jdk25-openjdk` for Minecraft 26.x (and keep `jdk-openjdk` 27 if wanted); FTC builds use Android Studio's own bundled JetBrains Runtime unless `JAVA_HOME` points elsewhere.

## Key question 3: Jar files, manifest, classpath, fat jars, JPMS, Minecraft distribution, Android DEX — the minimal mental model for "class not found" and "mod jar isn't loading"

### Takeaway
A jar is a zip with an optional `META-INF/MANIFEST.MF`; the JVM finds classes by searching the classpath (directories and jars) in order, so `ClassNotFoundException` means a name lookup failed at load time and `NoClassDefFoundError` means a class that existed at compile time is missing at run time. Mod loaders don't use `Main-Class` or `Class-Path`; they read their own descriptor (`fabric.mod.json`, `META-INF/neoforge.mods.toml`) and nested jars, so "mod jar isn't loading" is almost always a descriptor/nesting/version problem, not a classpath one.

### Cited Findings
- "JAR file is a file format based on the popular ZIP file format and is used for aggregating many files into one. A JAR file is essentially a zip file that contains an optional META-INF directory."; `MANIFEST.MF` "is used to define package related data"; `Main-Class`: "the class name of the main application class which the launcher will load at startup time. The value must not have the .class extension"; `Class-Path`: "specifies the relative URLs of the libraries that this application needs. URLs are separated by one or more spaces" and entries are resolved "relative to the code base that the containing application was loaded from (the 'context JAR')", "Relative URLs not ending with '/' are assumed to refer to JAR files", "At most one Class-Path header may be specified"; signature files `x.SF` and `x.DSA`/`x.RSA`/`x.EC` under META-INF; `Multi-Release`, `Automatic-Module-Name` ("Defines the module name if this JAR file is deployed as an automatic module on the module path"), `Launcher-Agent-Class` — [JAR File Specification (JDK 25)](https://docs.oracle.com/en/java/javase/25/docs/specs/jar/jar.html)
- `ClassNotFoundException`: "Thrown when an application tries to load in a class through its string name using: The forName method in class Class. The findSystemClass method in class ClassLoader. The loadClass method in class ClassLoader. but no definition for the class with the specified name could be found." — [Javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ClassNotFoundException.html)
- `NoClassDefFoundError`: "Thrown if the Java Virtual Machine or a ClassLoader instance tries to load in the definition of a class (as part of a normal method call or as part of creating a new instance using the new expression) and no definition of the class could be found. The searched-for class definition existed when the currently executing class was compiled, but the definition can no longer be found." — [Javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/NoClassDefFoundError.html)
- Shadow plugin: "Shadow is a Gradle plugin for combining a project's dependency classes and resources into a single output Jar" (fat/uber jar); plugin id `com.gradleup.shadow` (old `com.github.johnrengelman.shadow` deprecated); can "relocate the package names for dependencies"; use cases "Creating an executable JAR distribution" run with `java -jar application-shadow.jar` and "Bundling and relocating common dependencies in libraries to avoid classpath conflicts"; newest row "9.5.0+" needs Gradle 9.2 and Java 17 — [gradleup.com/shadow](https://gradleup.com/shadow/)
- Fabric jar-in-jar: the `include` configuration "Declares a dependency that should be included as a jar-in-jar in the remapJar output"; "This dependency configuration is not transitive"; "For non-mod dependencies, Loom will generate a mod JAR with a fabric.mod.json"; `remapJar` "Appends any included mods for jar-in-jar" (the 26.x unobfuscated plugin uses plain `jar`; see sibling notes) — [Fabric wiki: fabric-loom](https://wiki.fabricmc.net/documentation:fabric_loom)
- Fabric project files: `fabric.mod.json` is "The main file that describes your mod to Fabric Loader" (fields `id`, `name`, `environment`, `entrypoints`, `depends`, `mixins`); `src/main/resources` holds `fabric.mod.json` and mixin configs; `src/main/java` common code, `src/client/java` client-only code — [Fabric docs: Project structure](https://docs.fabricmc.net/develop/getting-started/project-structure)
- NeoForge mod descriptor: "The neoforge.mods.toml file, located at src/main/resources/META-INF/neoforge.mods.toml, is a file in TOML format"; `modLoader` default `javafml`, `loaderVersion` `1`; `[[mods]]` with `modId`; `version` "When set to ${file.jarVersion}, it will be replaced with the value of the Implementation-Version property" of the jar manifest; `[[dependencies.<modid>]]` with `type` required/optional/incompatible/discouraged — [NeoForge docs: Mod files](https://docs.neoforged.net/docs/gettingstarted/modfiles)
- JPMS (JEP 261): "Class paths are a means to locate definitions of individual types and resources" while module paths locate "whole modules"; "Classes found on the class path are loaded as members of this loader's unnamed module"; "If a package is defined in both a named module and on the class path then the package on the class path will be ignored" — [JEP 261: Module System](https://openjdk.org/jeps/261)
- Minecraft distribution: `client.json` "is the file that accompanies client.jar in .minecraft/versions/<version> and lists the version's attributes"; `downloads.client` holds the client jar's sha1/size/url; `libraries` entries carry a Maven-style `name` "groupId:artifactId:version" plus `downloads.artifact.path/sha1/size/url`, stored "relative to the 'libraries' directory in .minecraft"; `javaVersion.component` = `java-runtime-epsilon` and `majorVersion` = 25 since 26.1 Snapshot 1; `mainClass` is the class the launcher starts — [Minecraft Wiki: Client.json](https://minecraft.wiki/w/Client.json)
- Android: "`d8` is a command-line tool that Android Studio and the Android Gradle plugin use to compile your project's Java bytecode into DEX bytecode that runs on Android devices"; input "can be in any combination of *.class files or containers, such as JAR, APK, or ZIP files"; "desugaring converts these useful language features into bytecode that can run on the Android platform"; `--min-api number` "Specify the minimum API level you want the output DEX files to support" — [developer.android.com/tools/d8](https://developer.android.com/tools/d8)
- FTC SDK build settings: `build.common.gradle` has `compileSdkVersion 30`, `minSdkVersion 24`, `targetSdkVersion 28`, `sourceCompatibility JavaVersion.VERSION_1_8`, `targetCompatibility JavaVersion.VERSION_1_8`; `build.dependencies.gradle` pulls `org.firstinspires.ftc:RobotCore:12.0.0` etc. via `implementation`; `TeamCode/build.gradle` has `implementation project(':FtcRobotController')` and namespace `org.firstinspires.ftc.teamcode` — [FtcRobotController repo files](https://github.com/FIRST-Tech-Challenge/FtcRobotController) (read via GitHub API 2026-10-13)

### Inferences
- Debug ladder for a modder: (1) `unzip -l mymod.jar` — is the descriptor at the root (`fabric.mod.json`) or under `META-INF/` (`neoforge.mods.toml`)? (2) are the classes under the package path the descriptor's entrypoint names? (3) does the descriptor's `depends`/`versionRange` match the running Minecraft and loader? (4) if a library is missing at runtime, it was `implementation`/`compileOnly` but never `include`d (Fabric) or jarJar'd (NeoForge), giving `NoClassDefFoundError` for a class that compiled fine. `Main-Class` and `Class-Path` only matter for `java -jar`; a mod jar has neither.
- Minecraft itself is a plain classpath application: the launcher reads `client.json`, downloads each library by Maven coordinate into `.minecraft/libraries`, builds a `-cp` list, and starts `mainClass` with the bundled runtime. Mod loaders insert themselves at this stage; nothing uses the JPMS module path.
- For FTC, the jar built from TeamCode never runs as a jar on the phone/Control Hub: the AGP compiles `.java` to `.class`, D8 turns `.class` (yours plus every dependency jar) into `classes.dex`, and the APK is installed. The `VERSION_1_8` source level is why FTC code can't use newer syntax (records, `var` in some spots, switch expressions) even on a modern JDK.

- `sources.jar`/`javadoc.jar` conventions are cited only through the Fabric template's `withSourcesJar()` (KQ4); the Maven classifier convention (`-sources.jar`, `-javadoc.jar`) is standard but not fetched from a spec page here.

## Key question 4: Build systems — Gradle concepts a Fabric template exercises, Maven, lighter tools, IDE/jdtls import

### Takeaway
The Fabric example mod exercises almost every Gradle concept a modder meets: the wrapper (`gradlew`, pinned to 9.7.1), `settings.gradle` with `pluginManagement` repositories (Fabric maven, Maven Central, Plugin Portal), `build.gradle` applying `net.fabricmc.fabric-loom`, `gradle.properties` holding every version, `implementation` dependencies by `group:artifact:version`, `options.release = 25`, `withSourcesJar()`, `processResources` templating `fabric.mod.json`, and the tasks `runClient`, `runServer`, `genSources`, `build`/`jar`. Maven's POM/lifecycle model still shows up in plugin and tutorial land; for learning, `javac`+`jar`, `java Foo.java` (multi-file since JDK 22), and jbang skip the build system entirely.

### Cited Findings
- Wrapper: "The recommended way to execute any Gradle build" is with the Wrapper; files `gradlew`/`gradlew.bat`, `gradle/wrapper/gradle-wrapper.jar` ("code for downloading the Gradle distribution"), `gradle-wrapper.properties` with `distributionUrl=https\://services.gradle.org/distributions/gradle-9.8.1-bin.zip`; "you need to check them into version control"; downloads go to `GRADLE_USER_HOME`; upgrade with `./gradlew :wrapper --gradle-version 9.8.1` run twice — [Gradle Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html)
- Fabric example mod (HEAD, read 2026-10-13): `build.gradle` → `plugins { id 'net.fabricmc.fabric-loom' version "${loom_version}"; id 'maven-publish' }`, `loom { splitEnvironmentSourceSets() ... }`, `dependencies { minecraft "com.mojang:minecraft:${project.minecraft_version}"; implementation "net.fabricmc:fabric-loader:${project.loader_version}"; implementation "net.fabricmc.fabric-api:fabric-api:${project.fabric_api_version}" }`, `processResources { filesMatching("fabric.mod.json") { expand "version": version } }`, `tasks.withType(JavaCompile).configureEach { it.options.release = 25 }`, `java { withSourcesJar(); sourceCompatibility = JavaVersion.VERSION_25; targetCompatibility = JavaVersion.VERSION_25 }`, a `jar { from("LICENSE") ... }` block, and `publishing`; `settings.gradle` → `pluginManagement { repositories { maven { name = 'Fabric'; url = 'https://maven.fabricmc.net/' }; mavenCentral(); gradlePluginPortal() } }` and `rootProject.name = 'modid'`; `gradle.properties` → `org.gradle.jvmargs=-Xmx1G`, `org.gradle.parallel=true`, `org.gradle.configuration-cache=true`, `minecraft_version=26.3`, `loader_version=0.19.5`, `loom_version=1.18-SNAPSHOT`, `version=1.0.0`, `group=com.example`, `fabric_api_version=0.162.0+26.3`; `gradle/wrapper/gradle-wrapper.properties` → `distributionUrl=...gradle-9.7.1-bin.zip`, `distributionBase=GRADLE_USER_HOME`, `distributionPath=wrapper/dists` — [FabricMC/fabric-example-mod](https://github.com/FabricMC/fabric-example-mod)
- Loom latest release 1.18 (2026-09-20) — [fabric-loom releases](https://github.com/FabricMC/fabric-loom/releases); Loom README: plugin applied as `id 'fabric-loom'` (old id), "Loom targets the latest version of Gradle 7 or newer" (README text is stale relative to the 9.x requirement in the release notes) — [fabric-loom README dev/1.17](https://github.com/FabricMC/fabric-loom/blob/dev/1.17/README.md)
- Loom tasks: `runClient` "A JavaExec task to launch Fabric Loader as a Minecraft client"; `runServer` same for a dedicated server; `genSources` "Decompile the minecraft jar using the default decompiler"; `remapJar` "Produces a jar containing the remapped output of the jar task" and runs on `build`; `downloadAssets`; `vscode` generates `.vscode/launch.json`; `ideaSyncTask` generates IntelliJ run configs; `migrateMappings` — [Fabric wiki: fabric-loom](https://wiki.fabricmc.net/documentation:fabric_loom)
- Fabric docs: generator at the Fabric Template Mod Generator (mod name, package, Minecraft version; optional Kotlin/data generators) → zip → open in IDE → "Import Gradle Project"; edit `gradle.properties` (`maven_group`, `archive_base_name`) and `fabric.mod.json` (`id`, `name`, `description`); avoid cloud-synced folders, non-ASCII characters, and spaces in paths — [Creating a project](https://docs.fabricmc.net/develop/getting-started/creating-a-project); "To develop mods for Minecraft 26.1, you will need JDK 25"; IntelliJ IDEA "(recommended), or alternatively Visual Studio Code" — [Setting up](https://docs.fabricmc.net/develop/getting-started/setting-up)
- NeoForge: requires "the Java 25 Development Kit (JDK) and 64-bit Java Virtual Machine (JVM)"; `gradlew build` outputs `build/libs/<archivesBaseName>-<version>.jar`; `gradlew runClient` runs from `runs/client`, `gradlew runServer` from `runs/server`; `gradle.properties` holds mod name/version; "Only edit the build.gradle and settings.gradle files if you know what you are doing" — [NeoForge docs: Getting started](https://docs.neoforged.net/docs/gettingstarted/)
- Dependency configurations (java-library plugin): `api` "dependencies which are transitively exported to consumers, for compile time and runtime"; `implementation` dependencies are "purely internal and not meant to be exposed to consumers"; `compileOnly` "required at compile time, but not at runtime"; `runtimeOnly` "only required at runtime, and not at compile time"; `testImplementation`, `testRuntimeOnly`; rule "Prefer the implementation configuration over api when possible" — [Java Library plugin](https://docs.gradle.org/current/userguide/java_library_plugin.html)
- Inspecting dependencies: "You can inspect the dependency tree using the dependencies task", e.g. `./gradlew :app:dependencies` — [Dependency management basics](https://docs.gradle.org/current/userguide/dependency_management_basics.html)
- Standard layout and lifecycle tasks: "Put your production source code under the src/main/java directory", tests under `src/test/java`, resources copied from `src/[sourceSet]/resources`; `jar` "packages the main compiled classes and resources from src/main/resources into a single JAR" and is attached to `assemble`; `test` is attached to `check` — [Building Java projects](https://docs.gradle.org/current/userguide/building_java_projects.html)
- Daemon: "a long-lived, persistent process that runs in the background and hosts Gradle's execution engine"; stops after "idle for 3 hours"; `gradle --stop`, `gradle --status`, `--no-daemon` — [Gradle Daemon](https://docs.gradle.org/current/userguide/gradle_daemon.html)
- CLI flags: `--offline` "Specifies that the build should operate without accessing network resources"; `--refresh-dependencies` "Refresh the state of dependencies"; `-q` "Log errors only"; `--info`; `--stacktrace` "Print out the stacktrace also for user exceptions (e.g. compile error)"; `gradle tasks` "gives you a list of the main tasks of the selected project" — [Command-line interface](https://docs.gradle.org/current/userguide/command_line_interface.html)
- Caches: Gradle User Home is `~/.gradle` (override with `GRADLE_USER_HOME`); `caches/modules-2` = "Downloaded module dependencies (POMs, JARs, metadata)"; `daemon/` = "Registry and logs of the Gradle Daemon"; `jdks/` = "JDKs downloaded by the toolchain support"; `wrapper/dists/` = "Distributions downloaded by the Gradle Wrapper"; cleanup runs at most every 24 h: wrapper "release versions are deleted after 30 days of inactivity, and snapshot versions after 7 days", downloaded resources kept 30 days, created resources/build cache 7 days, daemon logs 14 days; project `.gradle/` is "Project-specific cache directory generated by Gradle" and version dirs there "are deleted if they haven't been used for 7 days"; "In most cases they do not require manual management" — [Gradle directory layout](https://docs.gradle.org/current/userguide/directory_layout.html)
- Maven lifecycle: "There are three built-in build lifecycles: default, clean and site"; default phases `validate`, `compile`, `test`, `package` ("take the compiled code and package it in its distributable format, such as a JAR"), `verify`, `install` ("install the package into the local repository"), `deploy`; running a phase runs "all its preceding build phases"; "Plugins are artifacts that provide goals to Maven"; e.g. `mvn clean dependency:copy-dependencies package` — [Maven lifecycle introduction](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html)
- Multi-file source launch: JEP 458 (release 22, delivered) enhances the launcher "to be able to run a program supplied as multiple files of Java source code"; `java Prog.java` compiles the first file in memory, then any referenced `Helper.java` found by the usual package/directory layout; jars via `--class-path '*'` or `'libs/*'`; builds on JEP 330 (JDK 11 single-file launch); shebang scripts stay single-file — [JEP 458](https://openjdk.org/jeps/458)
- jbang: both documentation URLs tried returned 404 (https://www.jbang.dev/documentation/guide/latest/index.html and .../latest/); see Gaps.
- IDE import: jdtls bundles Buildship for Gradle and M2Eclipse for Maven and needs Java 21+ to run (KQ1); Android Studio stores the Gradle JDK choice in `.idea/gradle.xml` and uses the same Gradle build as the terminal (KQ1) — [eclipse.jdt.ls README](https://github.com/eclipse-jdtls/eclipse.jdt.ls); [developer.android.com/build/jdks](https://developer.android.com/build/jdks)

### Inferences
- Cache size: no official numbers exist; a first Fabric 26.x import downloads the Gradle distribution (~150 MB zip), the Minecraft client/server jars and libraries, Fabric API, and decompiled sources, so expect `~/.gradle` of a few GB after a couple of mod projects plus Loom's own cache under `~/.gradle/caches/fabric-loom`. Clean-up: let the 30-day rule work, or `rm -rf ~/.gradle/caches` (re-downloads everything) and `./gradlew --stop` first so no daemon holds files; project `.gradle/` and `build/` are safe to delete any time (`./gradlew clean` removes `build/`).
- Because the IDE (Buildship under jdtls, or IntelliJ's Gradle tooling) asks the Gradle build for the classpath instead of guessing, the one rule for editor/build agreement is: import the project as a Gradle project and re-sync after editing `build.gradle`/`gradle.properties`; never hand-add jars to the IDE.
- Maven appears in Paper/Spigot plugin tutorials and most pre-2015 Java teaching; in modding it is otherwise absent, so the reader needs the vocabulary (POM, `mvn package`, `~/.m2`) more than the skill.
