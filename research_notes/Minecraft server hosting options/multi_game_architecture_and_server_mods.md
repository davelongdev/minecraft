# Multi-game architecture and server-side Fabric mods for Minecraft Java 26.3 (state as of 2026-10-18)

Scope: how to run several separate Minecraft Java 26.3 games at once for a kids' program with plain vanilla clients, comparing (A) several Fabric servers behind a Velocity proxy with (B) one Fabric server holding several worlds/dimensions, plus the server-side-mod facts the hosting decision depends on. Provider-independent.

Note on sourcing: besides web sources, several facts below were checked directly against the 26.3 client jar on this machine (`~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/libraries/com/mojang/minecraft/26.3/minecraft-26.3-client.jar`, read with `bsdtar` and `javap`); those are marked "[local 26.3 jar]". The client jar contains the shared server classes (integrated server), so the class and method names are the real 26.3 names (the game is unobfuscated since 26.1, so Fabric mods for 26.x use these Mojang names directly).

## Key question 1: Architecture A, several Fabric servers behind Velocity (one address, hop with a command or portal)

### Takeaway
Works on 26.3 today: Velocity's official compatibility page lists "Minecraft 1.7.2 through 26.3", the "Minecraft 26.3" pull request was merged 2026-09-14, and FabricProxy-Lite v2.12.0 (2026-03-28) declares 26.1 through 26.3. Each game gets its own process, world save, datapack set, scoreboard, and storage; the cost is N+1 Java 25 processes, N+1 ports (or a VPS), and offline-mode backends that must be firewalled.

### Cited Findings
- Velocity compatibility: Velocity is compatible with "Minecraft 1.7.2 through 26.3" ("as of this writing") — [PaperMC Velocity docs, Server compatibility](https://docs.papermc.io/velocity/server-compatibility/)
- Pull request "Minecraft 26.3" (#1867, RealBauHD) is merged, dated September 14, 2026; the search filter shows 0 open and 1 closed PR for "26.3" — [PaperMC/Velocity pull requests](https://github.com/PaperMC/Velocity/pulls?q=26.3). Earlier: commit "Minecraft 26.2 (#1807)" on Jun 16, 2026 and "Add 26.1.2 version string to 26.1 protocol version (#1769)" on Apr 10, 2026 — [Velocity commits, dev/3.0.0](https://github.com/PaperMC/Velocity/commits/dev/3.0.0)
- Current Velocity version lines per PaperMC's download API: a 4.x family (4.0.0 … 4.2.1-SNAPSHOT, 4.3.0 newest) and a 3.x family (3.4.0, 3.5.0, 3.5.1, 3.6.0-SNAPSHOT) — [fill.papermc.io v3 projects/velocity](https://fill.papermc.io/v3/projects/velocity). The getting-started page's sample startup log reads "Booting up Velocity 4.2.1-SNAPSHOT" — [Velocity Getting started](https://docs.papermc.io/velocity/getting-started/). (So "Velocity 3.4.x" is no longer the current line; 3.4.0 is a past release.)
- "Velocity requires at least Java 25." Backend servers are listed in the `[servers]` section of `velocity.toml` as name-and-address pairs, a `try` list sets the connection order, and because "this setup uses offline mode" the docs require following the player-information-forwarding and server-security guides — [Velocity Getting started](https://docs.papermc.io/velocity/getting-started/)
- Fabric backends: Fabric "works without modification", but the docs recommend adding forwarding support with FabricProxy-Lite, and CrossStitch for mods that add content; Mojang's vanilla server is "useful for protocol testing" but "for production the page recommends Fabric with FabricProxy-Lite"; running vanilla without player info forwarding "can induce subtle client problems"; Forge-Bukkit hybrids are not supported; proxy-behind-proxy is "completely unsupported" — [Velocity Server compatibility](https://docs.papermc.io/velocity/server-compatibility/)
- Forwarding modes: "Modern" (Velocity's native format, binary encoding with a MAC, requires Minecraft 1.13+), legacy BungeeCord ("fundamentally insecure"), and BungeeGuard. For Fabric, use the FabricProxy-Lite mod; "no actively supported Fabric mods support legacy forwarding". Backends run with `online-mode=false` because the proxy authenticates, and the forwarding secret must match — [Velocity Player information forwarding](https://docs.papermc.io/velocity/player-information-forwarding/)
- FabricProxy-Lite v2.12.0, published 2026-03-28, game_versions 26.1, 26.1.1, 26.1.2, 26.2, 26.3, loader fabric; the previous v2.11.0 (2025-10-03) covered 1.21.9–1.21.11 — [Modrinth API, fabricproxy-lite versions](https://api.modrinth.com/v2/project/fabricproxy-lite/version). Setup = Velocity `player-info-forwarding-mode = modern` + matching secret in `config/FabricProxy-Lite.toml`; FabricProxy-Lite is recommended over the original FabricProxy, which is no longer maintained — [CurseForge FabricProxy-Lite](https://www.curseforge.com/minecraft/mc-mods/fabricproxy-lite)
- Hopping between games: the `/server` command is available to anyone with `velocity.command.server`, which "by default, this is granted to all users"; `/server` with no arguments shows the current server and the other configured servers, `/server <name>` connects the player — [Velocity Built-in commands](https://docs.papermc.io/velocity/built-in-commands/)
- Vanilla `server.properties`: `online-mode` default `true` ("only allow players verified with the Minecraft account database"; turning it off is called risky), `server-port` default `25565`, `level-name` default `world` ("The world name and the world directory path"), `accepts-transfers` default `false` ("Whether to accept incoming transfers via a transfer packet"; when false incoming transfers are rejected) — [Minecraft Wiki, Server.properties](https://minecraft.wiki/w/Server.properties)
- Resource baseline for one vanilla-class server (wiki table, "Recommended" tier): 3–5 players on 3 GB RAM (Windows desktop), 10–15 players on 3 GB (Unix console), roughly 50–100 MB RAM per player, figures assume render distance ≤ 10 and a new world — [Minecraft Wiki, Server/Requirements/Dedicated](https://minecraft.wiki/w/Server/Requirements/Dedicated)
- Minecraft 26.3: released September 15, 2026, minimum "Java SE 25", data pack format 121.0, protocol version 777 — [Minecraft Wiki, Java Edition 26.3](https://minecraft.wiki/w/Java_Edition_26.3). 26.1 (March 24, 2026) was the first version to require Java 25; on an older Java the server stops immediately — [GameServerKings, Updating your server version](https://www.gameserverkings.com/knowledge-base/minecraft/updating-your-server-version/)

### Inferences
- Player experience with vanilla clients: one address in the server list, `/server <name>` to hop (no client mod needed), each backend gets its own world spawn/inventory/scoreboard. "Portal" hopping needs a Velocity plugin or a backend-side mod that triggers the proxy's connect request; the vanilla `/transfer` mechanism (backend sends the vanilla client to another host:port, gated by `accepts-transfers`) is a proxy-free alternative that keeps separate addresses visible to the client (the command itself was not re-verified in this pass; see Gaps).
- Datapack scoping is natural: each backend is its own save with its own `world/datapacks/`, scoreboard, and command storage, so packs that reuse a namespace (e.g. `oneblock` in both `one-block` and `one-block_2`) can coexist only in this architecture.
- Hosting fit: A needs N game processes + 1 proxy process, each with its own port, and the backends must be unreachable from the internet (they run `online-mode=false`). That means a VPS/dedicated box or a hosting plan that sells multiple servers plus a proxy; a single shared "one server, one port" plan cannot do A.
- Resource estimate: budget roughly 1.5–2 GB per Fabric 26.3 backend for a handful of kids plus ~0.5–1 GB for Velocity, all on Java 25 — extrapolated from the wiki's 3 GB / 3–5 player figure for a vanilla server; no 26.3-specific measurement found.
- Failure modes: forwarding secret mismatch (players bounced with a forwarding error), a backend still on `online-mode=true` (proxy logins rejected), exposing offline-mode backends directly (anyone can log in as anyone), and version lag (a new Minecraft drop needs Velocity + FabricProxy-Lite + Fabric Loader/API updates before kids' auto-updated clients can connect; 26.3 Velocity support landed 2026-09-14, the day before the 26.3 release).

### Gaps
- Velocity's official changelog/release notes for 26.3 could not be read directly (GitHub "Releases" is empty for the repo; PaperMC publishes builds through its download API and docs). Support is established by the merged PR and the compatibility page, not by a release note.
- No 26.3-specific benchmark of Fabric server RAM/CPU per instance was found; the wiki table is version-agnostic.
- The vanilla `/transfer` command (added 1.20.5) was not re-fetched in this pass; only the `accepts-transfers` server property is cited.
- No source was found on portal-based hopping plugins verified for Velocity 4.x + 26.3.

## Key question 2: Architecture B, one Fabric server with several worlds/dimensions

### Takeaway
Also works on 26.3 (Multiworld 1.14.2 for Fabric/Quilt 26.3 was published 2026-10-09; datapack-defined dimensions exist since 1.16), but data packs, scoreboards, and command storage are per server/save, not per dimension, so all games share one namespace space and one `/reload`; it needs only one process and port.

### Cited Findings
- Data packs are installed per world save: "manually placing them in the `.minecraft/saves/<world>/datapacks` folder of a world"; load order is stored in `level.dat`; "If a file exists in multiple data packs only the file in the last data pack is used" — [Minecraft Wiki, Data pack](https://minecraft.wiki/w/Data_pack)
- On a dedicated server the pack goes in a folder named `datapacks` inside the server's world folder (`world` by default), then "Type /reload from the console or as a level 3 operator if the server was running during the installation", and verify with `/datapack list enabled` — [Minecraft Wiki, Tutorial: Installing a data pack](https://minecraft.wiki/w/Tutorial:Installing_a_data_pack)
- Data packs can add and change dimensions and dimension types since 1.16 Pre-release 1; the `dimension` and `dimension_type` folders are marked experimental, so a pack using them "triggers the experimental settings warning", and worlds with experimental settings cannot be uploaded to Realms — [Minecraft Wiki, Data pack](https://minecraft.wiki/w/Data_pack)
- A custom dimension is a file at `data/<namespace>/dimension/<name>.json` with a `type` (dimension type ID) and a `generator` (`noise`, `flat`, or `debug`); new dimensions are reached with commands such as `/execute in <dimension> run teleport` — [Minecraft Wiki, Dimension definition](https://minecraft.wiki/w/Dimension_definition)
- `/reload` applies changes to "registry tags, loot tables, recipes, advancements, item modifiers, predicates, functions, and structure templates"; "Other features need a restart: the world must be reopened in singleplayer, or the server rebooted in multiplayer" — [Minecraft Wiki, Data pack](https://minecraft.wiki/w/Data_pack). `/reload` does not reload data pack definitions the game considers experimental; "Players must leave and rejoin the world to load these"; if a pack has invalid data "changes are not applied and the game continues using the previous data"; permission level 2 — [Minecraft Wiki, Commands/reload](https://minecraft.wiki/w/Commands/reload)
- Multiworld (Fabric/Quilt) 1.14.2, published 2026-10-09, game_versions include 26.2 and 26.3; its changelog notes "Portals Currently broken" — [Modrinth API, multiworld versions](https://api.modrinth.com/v2/project/multiworld/version). The mod "Adds support for teleporting & creating multiple worlds"; "Added worlds will be saved in the main overworld's dimension folder" at `world\dimensions\id\path`; it uses the Fantasy library by NucleoidMC; "On Fabric 1.21+, Multiworld Portal support requires iCommonLib"; active versions listed as 26.3, 26.2, 26.1, 1.21.11, 1.21.1, 1.20.1 — [Modrinth, Multiworld](https://modrinth.com/mod/multiworld)
- Fantasy "is a library that allows for dimensions to be created and destroyed at runtime on the server" and "supports both temporary dimensions which do not get saved, as well as persistent dimensions which can be safely used across server restarts" — [NucleoidMC/fantasy README](https://github.com/NucleoidMC/fantasy)
- Fabric API itself ships a `fabric-dimensions-v1` module (listed among the repo's top-level modules) — [FabricMC/fabric repository](https://github.com/FabricMC/fabric)
- Analogue on the plugin side: "Datapacks cannot currently be separated per-world in Bukkit and forks" — [PurpurMC docs, Purpur packs installation](https://purpurmc.org/docs/purpurpacks/installation/)
- Scoreboard and command storage are single objects owned by the server, not by a dimension: `MinecraftServer` exposes `public ServerScoreboard getScoreboard()`, `public CommandStorage getCommandStorage()`, `public ServerLevel getLevel(ResourceKey<Level>)`, `public Iterable<ServerLevel> getAllLevels()`, `public PackRepository getPackRepository()`, `public CompletableFuture<Void> reloadResources(Collection<String>)` — [local 26.3 jar, `javap net.minecraft.server.MinecraftServer`]; yarn 1.21.11 names for the same: `getScoreboard()`, `getDataCommandStorage()`, `getWorld(RegistryKey<World>)`, `getWorlds()`, `getDataPackManager()`, `reloadResources(Collection<String>)` — [Fabric Yarn 1.21.11 javadoc, MinecraftServer](https://maven.fabricmc.net/docs/yarn-1.21.11+build.4/net/minecraft/server/MinecraftServer.html)

### Inferences
- Datapack scoping in B: every game's pack is enabled on the single save and active in every dimension. Functions, tags, predicates, advancements, scoreboard objectives, storage namespaces, `load`/`tick` tags, and `/trigger` objectives are global; two packs that reuse a namespace (the repo's `one-block` and `one-block_2` both use `oneblock`) overwrite each other file-by-file ("only the file in the last data pack is used"). Packs written for a world at the origin (e.g. `one-block`'s 0 64 0 course, the Void-preset platform) would need positional changes or per-dimension `execute in` wrappers.
- Player experience in B: one address, one server; hopping = `/execute in <dim> run tp` (vanilla) or Multiworld's commands; players share tab list, chat, and scoreboard sidebar unless the packs are rewritten to be per-dimension aware. Inventories, scores and advancements carry across dimensions (same player data).
- Operational coupling: one `/reload` or one broken pack affects all games at once ("Registry loading errors" fail the whole reload); one crash takes all games down; conversely one process is cheaper and fits any single-server hosting plan.
- Adding a datapack-defined dimension to a live server needs a restart (dimension definitions are among the data that `/reload` does not apply); a runtime-dimension mod (Fantasy/Multiworld) avoids that but adds a dependency and, per its own changelog, currently has broken portals.

### Gaps
- No source states explicitly whether vanilla `/reload` rescans the `datapacks` folder for newly dropped packs; the wiki tutorial's instruction to run `/reload` after adding a pack on a running server implies it does, and the program's own practice (copy zip, `/reload`) matches, but the wiki pages for `/reload` and `/datapack` don't say so in words.
- Whether per-dimension datapack scoping exists in any 26.3 Fabric mod: none found. Multiworld's worlds are dimensions inside the main save, so they share the save's packs.
- No performance comparison of one server with N dimensions versus N servers was found.

## Key question 3: Server-side-only Fabric mods with unmodified vanilla clients (rules and 26.3 versions)

### Takeaway
A Fabric server running only server-side mods accepts vanilla clients; the hard rule is that the mod must not add registry entries (blocks, items, fluids, block entities, data components) because Fabric API's registry sync kicks clients missing them. For 26.3 the current stack is Fabric Loader 0.19.5 (stable), Fabric API 0.163.0+26.3 (2026-10-14), Java 25.

### Cited Findings
- "Server-side mods are mods that run exclusively on the server, without the need for a mod on the client." "Fabric servers running such mods can support Fabric, vanilla, or even Forge clients." PolyMc "Makes many mods work purely on server side, allowing vanilla client to join and use them" by "modyfing packets send to clients"; "Playability will vary depending on mods." — [Fabric Wiki, Server-side mods](https://wiki.fabricmc.net/serverside-mods)
- Registry sync kicks: Fabric's registry sync runs on connect and "kicks the client with a warning if any block, item, fluid, or block entity is missing"; a server-only mod that added block entities caused players without Fabric to be kicked on join, with no way for the author to exempt their own entries — [Lightrun summary of FabricMC/fabric issue "registry sync cannot be skipped"](https://lightrun.com/answers/fabricmc-fabric-fabric-registry-sync-cannot-be-skipped). A mod registering a data component for items caused a registry mismatch so that "Vanilla clients as well as clients who have the mod installed locally could join, but clients with just Fabric API were rejected" — [Modrinth version changelog (WC4UgDcZ/vAm2WOgJ)](https://modrinth.com/project/WC4UgDcZ/version/vAm2WOgJ)
- Workarounds (all third-party, each with compatibility risk): RegSyncFix disables syncs server-side ("you may encounter unexpected behavior if the mods are not the same as the server") — [Modrinth, RegSyncFix](https://modrinth.com/mod/regsyncfix); ModernRegSyncFix forks it "and adds support for Minecraft versions 26.1 onwards" — [ModpackIndex, ModernRegSyncFix](https://www.modpackindex.com/mod/117527/modernregsyncfix); Bypass Fabric Check intercepts the `FabricConfigurationTask` sent to non-local players, dedicated server only, toggled with `/bypass on|off` — [Mado Hosting listing, Bypass Fabric Check](https://www.mado-hosting.com/minecraft-mods/bypass-fabric-check)
- Modrinth marks every project's client/server requirement (`client_side` / `server_side`); Fabric API is marked optional on both sides; "If any mod adds content, every player needs Fabric and the same mods" — [GameServerKings, Fabric server setup](https://www.gameserverkings.com/knowledge-base/minecraft/fabric-server-setup/)
- Fabric API for 26.3: 0.163.0+26.3 (2026-10-14), 0.162.0+26.3 (2026-10-06), 0.161.0+26.3 (2026-09-18), 0.160.7+26.3 (2026-09-17), 0.160.6+26.3 (2026-09-16), all loader `fabric`; none of these changelogs mention dialogs, custom click actions, or Java requirements — [Modrinth API, fabric-api versions for 26.3](https://api.modrinth.com/v2/project/fabric-api/version?game_versions=%5B%2226.3%22%5D)
- Fabric Loader: 0.19.5 is the newest stable (0.20.0 listed, stable=false; 0.19.4/0.19.3/0.19.2 stable=false) — [Fabric Meta, loader versions](https://meta.fabricmc.net/v2/versions/loader); the same list is offered for game 26.3 — [Fabric Meta, loader versions for 26.3](https://meta.fabricmc.net/v2/versions/loader/26.3). Loader 0.19.3 (01 Jun) updated Mixin to 0.17.3 — [fabric-loader release 0.19.3](https://github.com/FabricMC/fabric-loader/releases/tag/0.19.3)
- Fabric API module list on the 26.3 branch has no dialog, click-action, or custom-click module; modules present include `fabric-networking-api-v1`, `fabric-command-api-v2`, `fabric-permission-api-v1`, `fabric-dimensions-v1`, `fabric-message-api-v1` — [FabricMC/fabric repository](https://github.com/FabricMC/fabric)
- "Most mods will also require you to install Fabric API into the mods folder." — [fabricmc.net, Use](https://fabricmc.net/use/server/)
- Java: 26.3 minimum "Java SE 25" — [Minecraft Wiki, Java Edition 26.3](https://minecraft.wiki/w/Java_Edition_26.3); "Velocity requires at least Java 25" — [Velocity Getting started](https://docs.papermc.io/velocity/getting-started/)

### Inferences
- Rules for a vanilla-joinable server mod on 26.3: register nothing in synced registries (no blocks/items/fluids/block entities/data components/entity types), send no custom payloads the client must understand (unknown `minecraft:custom_payload` channels are ignored by vanilla clients but anything expecting a reply breaks), and only use vanilla packets/dialogs/text components. Mixins into server classes, Fabric events, commands, scoreboard/storage access, and packet filtering are all fine.
- A mod that only listens for `ServerboundCustomClickActionPacket` (Key question 4) and filters entity-tracking packets (Key question 5) satisfies these rules, so it is joinable by unmodified kids' clients.

### Gaps
- The fabricmc.net server install page could not be read (the fetch returned the generic "Use" page); exact installer flags and the server launcher jar naming were not re-verified. Fabric Meta confirms 26.3 + Loader 0.19.5 is an offered pair.
- No official Fabric doc page enumerating the "vanilla-joinable" rules was found; the rules above are assembled from the registry-sync issue, Modrinth's side flags, and the Fabric wiki wording.

## Key question 4: Dialog `dynamic/custom` actions to a server-side mod (bypassing "Confirm Command Execution")

### Takeaway
Confirmed end to end: a dialog `dynamic/custom` action builds a `minecraft:custom` click event carrying all input values as an NBT compound; the vanilla client sends `ServerboundCustomClickActionPacket(Identifier id, Optional<Tag> payload)` with no confirmation screen (the "Confirm Command Execution" screen is tied to `run_command` for commands needing elevated permissions); the vanilla server only logs it, so a Fabric mod mixin on `ServerCommonPacketListenerImpl.handleCustomClickAction` (or `MinecraftServer.handleCustomClickAction`) receives it and can write `CommandStorage` or run functions via `Commands.performPrefixedCommand`. Fabric API provides no event for it; Paper has an API but Paper is not Fabric.

### Cited Findings
- Dialog button actions: static types `open_url`, `run_command`, `suggest_command`, `change_page`, `copy_to_clipboard`, `show_dialog`, `custom`; dynamic types `dynamic/run_command` (`template`, "a string with a macro template to be interpreted as a command", e.g. `/say $(message)`) and `dynamic/custom` (`id`, a namespaced ID, and `additions`, "Fields to be added to payload"). The static `custom` action "Sends a custom event to the server; has no effect on vanilla servers." `dynamic/custom` "will build a `minecraft:custom` event using all input values"; input values go "inside a compound tag" under each input's `key`; `text` → string tag unmodified, `boolean` → `1b`/`0b`, `number_range` → float tag; for `single_option` each option's `id` is "The value to be sent on submit" — [Minecraft Wiki, Dialog](https://minecraft.wiki/w/Dialog)
- Permissions for `run_command`: "Since they are being run from chat, the player must have the required permissions." "Privileged commands can only be run by server operators." Commands must not send chat messages directly (`say`, `tell`, `teammsg`). 25w21a: "A new dialog received while the warning screen is visible is restored after 'Back'." 1.21.6 Pre-Release 1: the `minecraft:custom` click event "has been expanded to carry full a NBT tag"; every dialog can have inputs — [Minecraft Wiki, Dialog](https://minecraft.wiki/w/Dialog)
- The confirmation screen's exact strings in 26.3: `multiplayer.confirm_command.title` = "Confirm Command Execution"; `multiplayer.confirm_command.permissions_required` = "You are trying to execute a command that requires elevated permissions.\nThis might negatively affect your game.\nAre you sure?\nCommand: %s"; also `…parse_errors` ("You are trying to execute an unrecognized or invalid command…"), `…signature_required` ("…a command that will send chat messages using your name. It can only be run from the chat screen…"), buttons `…run_command` = "Run Command", `…suggest_command` = "Copy to Chat Screen". The client has a `net/minecraft/client/gui/screens/dialog/DialogScreen$WarningScreen` class — [local 26.3 jar, `assets/minecraft/lang/en_us.json` and class listing]
- Packet: `net.minecraft.network.protocol.common.ServerboundCustomClickActionPacket` is a record `(Identifier id, Optional<Tag> payload)` with an `UNTRUSTED_TAG_CODEC` for the payload, implementing `Packet<ServerCommonPacketListener>` — [local 26.3 jar, `javap`]. Yarn's name for the same packet is `CustomClickActionC2SPacket`, "a record with an Identifier id and an optional NBT payload" — [Fabric Yarn 1.21.11 javadoc, CustomClickActionC2SPacket](https://maven.fabricmc.net/docs/yarn-1.21.11+build.4/net/minecraft/network/packet/c2s/common/CustomClickActionC2SPacket.html); the client sends it through `DialogNetworkAccess.sendCustomClickActionPacket(Identifier, Optional)` — [Fabric Yarn 1.21.7 javadoc, DialogNetworkAccess](https://maven.fabricmc.net/docs/yarn-1.21.7+build.1/net/minecraft/client/gui/screen/dialog/DialogNetworkAccess.html)
- Server handling in vanilla 26.3: `ServerCommonPacketListenerImpl.handleCustomClickAction(ServerboundCustomClickActionPacket)` calls `PacketUtils.ensureRunningOnSameThread(...)` and then `this.server.handleCustomClickAction(packet.id(), packet.payload())`; `MinecraftServer.handleCustomClickAction(Identifier, Optional<Tag>)` only logs "Received custom click action {} with payload {}" — [local 26.3 jar, `javap -c`]. Yarn 1.21.11 shows the same handler as `ServerCommonNetworkHandler.onCustomClickAction(CustomClickActionC2SPacket)`, with fields `protected final MinecraftServer server` and `protected final ClientConnection connection` and no `player` field on the common handler — [Fabric Yarn 1.21.11 javadoc, ServerCommonNetworkHandler](https://maven.fabricmc.net/docs/yarn-1.21.11+build.4/net/minecraft/server/network/ServerCommonNetworkHandler.html)
- Fabric API has no dialog/custom-click module (module list) — [FabricMC/fabric repository](https://github.com/FabricMC/fabric); Fabric API 26.3 changelogs through 0.163.0 mention nothing about dialogs or custom click actions — [Modrinth API, fabric-api 26.3 versions](https://api.modrinth.com/v2/project/fabric-api/version?game_versions=%5B%2226.3%22%5D)
- Paper (not Fabric) exposes it as API: `DialogAction.CustomClickAction` "executes a custom action with additional data", with an identifier and optional compound tag — [Purpur javadoc, DialogAction.CustomClickAction](https://purpurmc.org/javadoc/io/papermc/paper/registry/data/dialog/action/DialogAction.CustomClickAction.html); the DialogAPI Paper plugin "supports custom actions via Mojang's native ServerboundCustomClickActionPacket system" and links buttons to registered custom actions by namespaced key — [AlepandoCR/DialogAPI](https://github.com/AlepandoCR/DialogAPI)
- Writing storage / running functions from a mod (26.3 names): `MinecraftServer.getCommandStorage()` → `CommandStorage.get(Identifier)`, `set(Identifier, CompoundTag)`, `keys()`; `MinecraftServer.getCommands()` → `Commands.performPrefixedCommand(CommandSourceStack, String)` and `performCommand(ParseResults<CommandSourceStack>, String)`; `MinecraftServer.getFunctions()` → `ServerFunctionManager.get(Identifier)` returning `Optional<CommandFunction<CommandSourceStack>>`, `execute(CommandFunction, CommandSourceStack)`, `getGameLoopSender()`, `getTag(Identifier)`; `MinecraftServer.getScoreboard()` — [local 26.3 jar, `javap`]. Yarn 1.21.11 equivalents: `DataCommandStorage getDataCommandStorage()`, `CommandManager getCommandManager()`, `CommandFunctionManager getCommandFunctionManager()` — [Fabric Yarn 1.21.11 javadoc, MinecraftServer](https://maven.fabricmc.net/docs/yarn-1.21.11+build.4/net/minecraft/server/MinecraftServer.html)
- 26.3 sign change (related to click events generally): "By default, commands and other click events contained in sign text are no longer executed when the block is clicked"; a new boolean `allow_op_features` (default `false`) restores previous behaviour; signs from older worlds get it set to `true` — [Minecraft Wiki, Java Edition 26.3](https://minecraft.wiki/w/Java_Edition_26.3)

### Inferences
- The datapack side needs no change in shape: replace `{"type":"dynamic/run_command","template":"function npc:internal/form_apply ..."}` with `{"type":"dynamic/custom","id":"npc:form_apply","additions":{...}}`; the server receives `id = npc:form_apply` and `payload = {name:"…", look:"…", greeting:"…", …additions}`. Because the packet is not a command, no permission check and no "Confirm Command Execution" screen apply, and the kids no longer need op for form submission (op was only needed to run `/function`).
- Where to hook: a `@Inject` at the head of `ServerCommonPacketListenerImpl.handleCustomClickAction` (or an override check in `ServerGamePacketListenerImpl`, which is the subclass that has the `player`) gives access to the player; hooking `MinecraftServer.handleCustomClickAction` is simpler but receives only the id and payload with no player context, so the listener-level mixin is the right spot. The handler already runs on the server thread after `ensureRunningOnSameThread`, so touching storage/scoreboard there is safe.
- Bridging back to datapacks: copy the payload into `storage <ns>:<path>` with `CommandStorage.set`, then run `function <ns>:<fn> with storage <ns>:<path>` through `Commands.performPrefixedCommand(player.createCommandSourceStack().withPermission(2).withSuppressedOutput(), "...")` (or `getFunctions().execute(fn, source)`), so existing macro functions like `form_create` keep working unchanged. Treat the payload as untrusted (vanilla decodes it with an "untrusted" NBT codec): validate id namespace and payload keys/lengths, never splice strings into commands without the storage indirection.
- Known limits inherited from dialogs: a `"` in a text box still breaks any command that re-serialises it as SNBT by hand, but via storage + macro the value stays a string tag and the macro parser handles escaping (`text` inputs are stored "unmodified" as string tags).

### Gaps
- No existing Fabric mod or example repository that server-side-handles `ServerboundCustomClickActionPacket` was found (searches returned only Paper plugins and client-side dialog tools); the mixin approach is inferred from the decompiled handler, not from a published example.
- No official Mojang/wiki text spells out precisely when the "Confirm Command Execution" screen appears for dialog `run_command`; the evidence is the 26.3 client strings (`permissions_required`, `parse_errors`, `signature_required`) plus the wiki's permission notes.
- Not verified whether the dialog closes automatically after a `dynamic/custom` action the same way as after `run_command` (the wiki's `after_action` field was not re-read in this pass).

## Key question 5: Per-player entity visibility from a server-side mod

### Takeaway
Feasible and done by existing server-side Fabric mods (Vanish for 26.3, Ghosty for 1.21.1), but Fabric API's `EntityTrackingEvents.START_TRACKING` fires after the spawn packet is sent, so hiding requires a mixin into the vanilla per-player tracker (`ChunkMap$TrackedEntity.updatePlayer(ServerPlayer)` / `ServerEntity`) rather than a Fabric API event.

### Cited Findings
- Fabric API 0.163.0+26.3 `EntityTrackingEvents`: "Events related to a tracking entities within a player's view distance." `START_TRACKING`: "An event that is called after a player has started tracking an entity. This event is called after the entity's spawn packet is sent to the player." `STOP_TRACKING`: "An event that is called before a player stops tracking an entity. The entity still exists on the server and on the player's client." — [Fabric API 0.163.0+26.3 javadoc, EntityTrackingEvents](https://maven.fabricmc.net/docs/fabric-api-0.163.0+26.3/net/fabricmc/fabric/api/networking/v1/EntityTrackingEvents.html). Older builds (1.16/1.17) documented `START_TRACKING` as firing "before the player's client is sent the entity's spawn packet", so the timing wording changed by 0.119.2+1.21.5 — [Fabric API 0.41.0+1.17 javadoc](https://maven.fabricmc.net/docs/fabric-api-0.41.0+1.17/net/fabricmc/fabric/api/networking/v1/EntityTrackingEvents.html); [Fabric API 0.119.2+1.21.5 javadoc, StartTracking](https://maven.fabricmc.net/docs/fabric-api-0.119.2+1.21.5/net/fabricmc/fabric/api/networking/v1/EntityTrackingEvents.StartTracking.html)
- Vanilla 26.3 tracker classes: `net/minecraft/server/level/ChunkMap$TrackedEntity` with `public void updatePlayer(ServerPlayer)`, `updatePlayers(List<ServerPlayer>)`, `removePlayer(ServerPlayer)`, `broadcastRemoved()`; and `net/minecraft/server/level/ServerEntity` — [local 26.3 jar, `javap`]
- Vanish (DrexHD, MIT, source github.com/DrexHD/Vanish): "Fabric vanish mod to completely hide from other players using /vanish"; the vanished player is "completely invisible and undetectable", removed from `/list`, server-list sample and count, command selectors, and from join/leave/death/advancement messages; sounds and container animations suppressed; Modrinth flags `client_side: unsupported`, `server_side: required`; supported versions include 26.3, 26.2, 26.1.x, 1.21.x — [Modrinth API search](https://api.modrinth.com/v2/search?query=vanish&facets=%5B%5B%22categories%3Afabric%22%5D%2C%5B%22server_side%3Arequired%22%5D%2C%5B%22versions%3A26.3%22%5D%5D&limit=10); [Modrinth, Vanish](https://modrinth.com/mod/vanish)
- Ghosty (lightsing, MIT, source github.com/lightsing/ghosty): "Ghosty sits between the vanilla server's entity tracker and the client" and filters entity updates by range, field of view, and occlusion; exposes `EntityVisibilityEvents.PRE` ("fired before any internal Ghosty checks"; returning FAIL forces the entity to be sent) and `POST` ("fired after all internal checks have finished computing", can modify the update behaviour before packets are sent); Modrinth page lists Minecraft 1.21.1 and Fabric only — [Modrinth, Ghosty](https://modrinth.com/mod/esp-ghosty)
- Disguises is described as a server-side Fabric mod with observer-specific overrides (one player sees a different disguise than everyone else) — [ModpackIndex, Disguises](https://www.modpackindex.com/mod/155763/disguises) (listing only; not verified for 26.3)
- PolyMc/Polymer demonstrate the general technique of rewriting packets server-side so vanilla clients see something different — [Fabric Wiki, Server-side mods](https://wiki.fabricmc.net/serverside-mods)

### Inferences
- Approach for "each kid sees only their own NPCs/entities": tag entities with an owner (scoreboard or custom data), then a mixin on `ChunkMap$TrackedEntity.updatePlayer(ServerPlayer)` that skips (and, if already tracked, removes) the entity for non-owners; the vanilla `removePlayer`/`broadcastRemoved` paths send the despawn. This is exactly the layer Ghosty and Vanish operate at, and it needs nothing on the client. `STOP_TRACKING` from Fabric API can still be used for bookkeeping, but `START_TRACKING` cannot cancel the spawn.
- Sounds, particles, and chat triggered by hidden entities need separate per-player filtering (Vanish's feature list shows the breadth: `/list`, join messages, sounds, container animations).
- The repo's current workaround (islands 1024 blocks apart, out of render distance) already achieves per-player isolation without a mod; a visibility mod only becomes necessary if games must share one space.

### Gaps
- No 26.3-verified, general-purpose "hide entity X from player Y" library was found; Ghosty's API is the closest but its listing stops at 1.21.1. Vanish is player-only.
- Fabric API's `StartTracking`/`StopTracking` method signatures for 26.3 were not shown on the javadoc index page fetched (only the field descriptions), so the exact 26.3 callback signatures are unconfirmed (older builds: `onStartTracking(Entity, ServerPlayerEntity)`).

## Key question 6: Datapacks on a dedicated server, `/reload` and hot-loading, whitelist, and child-account multiplayer blocks

### Takeaway
Datapacks go in `<level-name>/datapacks/` (default `world/datapacks/`) and are applied with `/reload` (functions, tags, predicates, loot, advancements, structures; not dimensions); 26.3 flips `white-list` to `true` by default; Microsoft child accounts have multiplayer blocked by default and a parent must set "You can join multiplayer games" to Allow at account.xbox.com before the kid can join any server.

### Cited Findings
- Server install: pack into the `datapacks` folder inside the server's world folder (`world` by default), then `/reload` "from the console or as a level 3 operator if the server was running during the installation", verify with `/datapack list enabled` — [Minecraft Wiki, Tutorial: Installing a data pack](https://minecraft.wiki/w/Tutorial:Installing_a_data_pack). `level-name` default `world` is "The world name and the world directory path" — [Minecraft Wiki, Server.properties](https://minecraft.wiki/w/Server.properties)
- `/datapack enable <name> [first|last|before <existing>|after <existing>]`, `disable`, `list [available|enabled]` (permission level 2), `create <id> <description>` (level 4, added 1.21.6/25w15a, "Creates new empty directory data pack for current world"); enabling fails if the pack needs a feature flag not enabled at world creation; built-in packs enabled at creation cannot be disabled since 1.20.5 — [Minecraft Wiki, Commands/datapack](https://minecraft.wiki/w/Commands/datapack)
- `/reload` (permission level 2) refreshes the active data packs; invalid data → "changes are not applied and the game continues using the previous data"; experimental definitions require leaving and rejoining — [Minecraft Wiki, Commands/reload](https://minecraft.wiki/w/Commands/reload); what `/reload` covers vs. what needs a restart — [Minecraft Wiki, Data pack](https://minecraft.wiki/w/Data_pack). A `--safeMode` server option (1.16) loads only the vanilla pack, and the game offers Safe Mode if a pack breaks loading — [Minecraft Wiki, Data pack](https://minecraft.wiki/w/Data_pack)
- A Fabric mod can trigger the same reload programmatically: `MinecraftServer.reloadResources(Collection<String> dataPacks)` returns `CompletableFuture<Void>`, and `getPackRepository()` exposes the pack list — [local 26.3 jar, `javap`]; yarn: `reloadResources(Collection<String>)`, `getDataPackManager()` — [Fabric Yarn 1.21.11 javadoc, MinecraftServer](https://maven.fabricmc.net/docs/yarn-1.21.11+build.4/net/minecraft/server/MinecraftServer.html)
- Whitelist: 26.3 "The `white-list` property is now `true` by default." — [Minecraft Wiki, Java Edition 26.3](https://minecraft.wiki/w/Java_Edition_26.3); `white-list` = "Whether the whitelist is enabled" (players not on it can't connect), `enforce-whitelist` default `false` (kicks already-online non-whitelisted players after the list reloads) — [Minecraft Wiki, Server.properties](https://minecraft.wiki/w/Server.properties)
- 26.3 server note: "Some log lines that server software might look out for have been removed", with the notes pointing to the Minecraft Server Management Protocol instead — [Minecraft Wiki, Java Edition 26.3](https://minecraft.wiki/w/Java_Edition_26.3)
- Child accounts: parents manage them at account.xbox.com/settings; on the Online Safety tab, "You can join multiplayer games" must be set to Allow — [minecraft.net, Parental Controls in Minecraft](https://www.minecraft.net/en-us/article/parental-controls). Child accounts start with multiplayer and communication blocked; while blocked the player "cannot join any multiplayer game in Minecraft, including shared local worlds, Realms, or servers" — [minecraft.net, How to Stay Safe Online](https://www.minecraft.net/en-us/article/minecraft-multiplayer-server-safety). Java and Bedrock both have multiplayer off by default on child accounts — [minecraft.net, Parents' Guide](https://www.minecraft.net/en-us/article/parents--guide-minecraft). The same settings are reachable through the Xbox Family Settings app — [Xbox Support, Manage a member's safety settings to access Minecraft features](https://support.xbox.com/en-AU/help/family-online-safety/online-safety/manage-a-members-safety-settings-to-access-minecraft-features)
- Community reports (Microsoft Q&A, not official docs): settings changes can take time to propagate and can be overridden by family-group setup; the child must sign into the Java launcher with the same account; a child account "can't manage its own privacy settings" and needs an adult organizer; some users report the Java "Multiplayer is disabled" state persisting after changing settings; changing the birth date does not convert a child account to an adult one — [Microsoft Q&A, Multiplayer option disabled](https://learn.microsoft.com/en-us/answers/questions/4220013/minecraft-java-edition-multiplayer-option-disabled); [Microsoft Q&A, bugged child account](https://learn.microsoft.com/ru-ru/answers/questions/5912527/multiplayer-blocked-in-minecraft-java-edition-bugg); [Microsoft Q&A, family group multiplayer access](https://learn.microsoft.com/answers/a/12366846)

### Inferences
- Both architectures use the same per-save install path; A has N such folders, B has one. Hot-loading in practice = copy the zip, `/reload` (or have the mod call `reloadResources`); a restart is only needed for dimension/worldgen/feature-flag changes.
- Because 26.3 ships with the whitelist on by default, the teacher will need to `/whitelist add` each kid (or set `white-list=false`) on every new 26.3 server; behind Velocity, the whitelist applies on the backends, the proxy does not whitelist by itself.
- The child-account block is independent of the hosting choice: it affects joining any third-party server, LAN world, or Realm, so it must be sorted per family before class, with the launcher relogged after the parent changes the setting.
- The `/reload` permission-level discrepancy (wiki command page: level 2; tutorial: "level 3 operator") does not matter in practice if the teacher is level 4.

### Gaps
- No help.minecraft.net article on the Java "Multiplayer is disabled" message was retrieved (searches returned minecraft.net and Xbox Support pages instead); the official text on how family settings gate third-party Java servers comes from the minecraft.net safety/parental-control pages, which are several years old.
- Whether `/reload` re-scans `datapacks/` for new files is implied by the wiki tutorial, not stated.
- Not checked: whether Velocity 4.x adds its own whitelist/allowlist feature.
