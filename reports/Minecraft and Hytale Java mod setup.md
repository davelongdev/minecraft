# Install JDK 25, then mod from any editor

*Research date 2026-10-13. Sources are the six notes in `research_notes/Minecraft and Hytale Java mod setup/` (toolchain, Hytale, editors, Java platform, learning Java, workflow and classroom), checked against the live templates, Maven repositories, and this laptop on that date. This report builds on two earlier ones and doesn't repeat them: [Minecraft Java mods in 2026](/home/dave/minecraft/reports/Minecraft%20Java%20mods%20in%202026.md) (why Fabric, the thirty-line key mod) and [Minecraft modding approaches compared](/home/dave/minecraft/reports/Minecraft%20modding%20approaches%20compared.md) (stay on data packs, add one mod). The Java fundamentals (JDK vendors, jar files, Gradle) live in a standalone reader document, [java-notes.md](/home/dave/minecraft/java-notes.md), which this report summarises and points to rather than duplicates. Hytale facts are split into official, community, and inferred throughout, because the game is one day past a breaking update.*

**The one thing standing between this laptop and a working mod project is a second JDK: install `jdk25-openjdk` from Arch's `extra` repository and make it the default, because JDK 27 can't run the Gradle wrapper that any of the three templates ship.** Gradle only starts on Java 27 from version 9.8.0, and the Fabric template pins 9.7.1, the NeoForge template 9.2.1, and the Hytale community template 9.3.1, while Minecraft 26.3, Fabric Loom 1.18, NeoForge, and the Hytale server all want Java 25 anyway ([Gradle compatibility matrix](https://docs.gradle.org/current/userguide/compatibility.html); [Minecraft Wiki: 26.3](https://minecraft.wiki/w/Java_Edition_26.3)). After that one `pacman` command, a Minecraft project is a template download plus `./gradlew runClient`, a Hytale plugin is a `git clone` plus `./gradlew runServer`, and the built jar copies into the Prism Flatpak's data tree. Every official doc assumes IntelliJ IDEA, which since 2025.3 is one free product (Arch package `intellij-idea-community-edition` 2026.2.3) with a Minecraft Development plugin that understands Mixins; Neovim 0.12 and Emacs 31 both work through the same Eclipse language server (jdtls) and give completion, navigation into decompiled Minecraft code, and a debugger, at the cost of raising the server's memory cap, handing it JDK 25 for Gradle, and living without Mixin checking. The Java you need is the Java 21 subset (classes, static fields, generics, lambdas, records, pattern matching), about 20 to 40 hours of study for someone fluent in Python and C, followed by the loader docs' own first-item and first-block pages. The daily loop is edit, `runClient`, read `run/logs/latest.log`, and a version bump once a quarter. Hytale is the easier Java (official Javadoc, unobfuscated server, no mixins, no mappings) and the riskier platform (Update 7 on 2026-10-12 deleted whole chunk-access interfaces, every plugin needed a rebuild after Update 6, and every tester needs a paid account). For the makerspace, the earlier recommendation stands for the current 8–14 command program; a Java track for 10–14s is feasible later as "edit one class in a pre-built project" with Gradle, JDKs, and accounts kept on the instructor's side.

## JDK 27 alone can't run any of the three templates' Gradle wrappers

A quick definition first. The **JDK** (Java Development Kit) is the compiler (`javac`), the runtime (`java`, which hosts the **JVM**, the virtual machine that runs compiled bytecode), and a handful of tools; **Gradle** is the build tool every modding template uses, and the **Gradle wrapper** (`./gradlew` plus `gradle/wrapper/`) is a small script that downloads and runs the exact Gradle version the template's author pinned ([Gradle Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html)). That pin is what bites here. Gradle's own table says a JVM between 17 and 27 can run Gradle 9.8.1, but Java 25 needs at least Gradle 9.1.0, Java 26 needs 9.4.0, and **Java 27 needs 9.8.0** ([Gradle compatibility](https://docs.gradle.org/current/userguide/compatibility.html)). The Fabric example mod's wrapper is **Gradle 9.7.1** ([fabric-example-mod wrapper](https://raw.githubusercontent.com/FabricMC/fabric-example-mod/master/gradle/wrapper/gradle-wrapper.properties)), the NeoForge 26.3 MDK's is **9.2.1** ([MDK-26.3 wrapper](https://raw.githubusercontent.com/neoforgemdks/MDK-26.3-ModDevGradle/main/gradle/wrapper/gradle-wrapper.properties)), and the Hytale community guide names **9.3.1** ([hytalemodding.dev setup](https://hytalemodding.dev/en/docs/guides/plugin/setting-up-env)). This laptop has exactly one JDK, `jdk-openjdk 27.u35-1`, set as default (verified with `archlinux-java status` on 2026-10-13), so `./gradlew` in any of the three will fail before it does anything useful. Nobody tested that failure in these notes; it follows from the wrapper versions and the table, and the fix is the same either way.

| Project | Gradle wrapper | Newest Java that wrapper runs on | JDK the project compiles with |
|---|---|---|---|
| Fabric example mod (26.3) | 9.7.1 | 26 | 25 (`options.release = 25`) |
| NeoForge MDK-26.3-ModDevGradle | 9.2.1 | 25 | 25 (toolchain) |
| Hytale `plugin-template` | 9.3.1 (per guide) | 25 | 25 |

The target version is 25 for reasons beyond Gradle. Minecraft 26.1 (2026-03-24) was "the first to require Java 25" and the first release shipped "fully unobfuscated"; 26.3 "Wilderness Bound" (2026-09-15) still requires Java SE 25, and 26.4 is in snapshot for a Q4 release ([Minecraft Wiki: 26.1](https://minecraft.wiki/w/Java_Edition_26.1); [26.3](https://minecraft.wiki/w/Java_Edition_26.3); [26.4](https://minecraft.wiki/w/Java_Edition_26.4)). Loom 1.18, Fabric's Gradle plugin, is itself compiled for Java 25 and replaced a native helper library with "Java 25's Foreign Function and Memory API" ([Loom 1.18 build.gradle](https://raw.githubusercontent.com/FabricMC/fabric-loom/dev/1.18/build.gradle); [Loom 1.18 release](https://github.com/FabricMC/fabric-loom/releases/tag/1.18)). NeoForge asks for a "Java 25 JDK with a 64-bit JVM" and officially supports Microsoft's OpenJDK 25 builds while saying any JDK should work ([NeoForge: Getting Started](https://docs.neoforged.net/docs/gettingstarted/)). Hytale's server "requires 64-bit Java 25" per the hosting guides that mirror the official server manual ([gameserverkings](https://www.gameserverkings.com/knowledge-base/hytale/hytale-dedicated-server/)). Arch has `jdk25-openjdk 25.0.4.1.u1-1` in `extra`, it installs beside `jdk-openjdk` 27 without conflict, and the wiki's rule is that "all these JVMs can be installed without conflict" ([Arch package search](https://archlinux.org/packages/?q=openjdk); [Arch Wiki: Java](https://wiki.archlinux.org/index.php?title=Java&action=raw)).

The install is three commands, and you have a choice about the third:

```sh
sudo pacman -S jdk25-openjdk
sudo archlinux-java set java-25-openjdk    # option A: make 25 the default for everything
java -version                               # quick check: should print 25
```

Option A is the beginner-proof route and the one this report recommends: every tool that needs a JDK (Gradle, jdtls, `java -jar HytaleServer.jar`) then finds 25, and jdtls only needs 21 or newer ([eclipse.jdt.ls README](https://github.com/eclipse-jdtls/eclipse.jdt.ls)). Option B keeps 27 as the system default and tells Gradle alone to use 25, with `org.gradle.java.home=/usr/lib/jvm/java-25-openjdk` in `~/.gradle/gradle.properties`, which works for terminal builds, IntelliJ, and jdtls's Gradle importer alike; the path follows Arch's `/usr/lib/jvm/java-NN-openjdk` naming and wasn't verified by installing. Either way, keep JDK 27 if you like; it's a non-LTS feature release (GA 2026-09-15) that stops getting updates when 28 ships, while 25 is the current LTS with Temurin updates promised to at least September 2031 ([OpenJDK JDK 27](https://openjdk.org/projects/jdk/27/); [Adoptium support](https://adoptium.net/support/)).

Three different "which JDK" decisions hide in one project, and most "wrong Java version" confusion comes from mixing them up: the JDK that runs Gradle's background process (the **daemon**; bounded by the wrapper version as above), the **toolchain** JDK that compiles and tests your code (`java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }` in NeoForge's template; Fabric's template uses the older `options.release = 25` flag, which compiles against Java 25's API no matter which JDK does the compiling), and the IDE's "project SDK", which must agree with the toolchain or you'll see red squiggles that `./gradlew build` doesn't ([Gradle toolchains](https://docs.gradle.org/current/userguide/toolchains.html); [Building Java projects](https://docs.gradle.org/current/userguide/building_java_projects.html)). Gradle finds every JDK under `/usr/lib/jvm` on its own; it only downloads one if a project applies the `org.gradle.toolchains.foojay-resolver-convention` settings plugin, which the NeoForge ModDevGradle README recommends and the Fabric template doesn't ship ([ModDevGradle README](https://github.com/neoforged/ModDevGradle)).

That is as far as this report goes on fundamentals, because [java-notes.md](/home/dave/minecraft/java-notes.md) covers them for exactly this reader. Its short version: OpenJDK is the one GPLv2-with-Classpath-Exception source tree, and Oracle JDK, Eclipse Temurin, Microsoft's build, Amazon Corretto, Arch's `jdk*-openjdk`, and the JetBrains Runtime are all builds of it that pass the same compatibility test kit, so the vendor never changes how a mod behaves; the differences are update length and licensing, where Oracle's free "No-Fee Terms" for an LTS run out "one full year after the next LTS release" while Temurin and the distro packages don't ([OpenJDK licence](https://openjdk.org/legal/gplv2+ce.html); [Oracle free licence](https://blogs.oracle.com/java/free-java-license); [Temurin](https://adoptium.net/temurin/)). On Arch the distro package is the right answer; Temurin is for Windows, macOS, or the FTC team's laptops. A **jar** is "essentially a zip file that contains an optional META-INF directory"; the JVM finds classes by searching the **classpath** in order, so `ClassNotFoundException` means a name lookup failed and `NoClassDefFoundError` means something that compiled fine is missing at run time ([JAR specification](https://docs.oracle.com/en/java/javase/25/docs/specs/jar/jar.html); [NoClassDefFoundError](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/NoClassDefFoundError.html)). Mod loaders never read a jar's `Main-Class`; Fabric reads `fabric.mod.json` at the jar root, NeoForge reads `META-INF/neoforge.mods.toml`, and Hytale reads `manifest.json`, so "my mod isn't loading" is almost always a descriptor or version-range problem. Gradle's vocabulary (wrapper, `build.gradle`, `gradle.properties`, `implementation` dependencies by `group:artifact:version`, tasks, the `~/.gradle` cache) is in the same document with a glossary.

The Prism side needs no system JDK at all. Prism 9+ "Auto-download Mojang Java" works in the Flatpak and AppImage builds ([Prism: Installing Java](https://prismlauncher.org/wiki/getting-started/installing-java/)), and on this machine the 26.3 instance already runs on the downloaded `java-runtime-epsilon`, a Microsoft OpenJDK 25.0.1 (`JavaVendor=Microsoft` in `prismlauncher.cfg`, verified locally). Prism's Flatpak data lives at `~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/`, with each instance's mods folder at `instances/<name>/minecraft/mods/` ([Prism: Data Location](https://prismlauncher.org/wiki/getting-started/data-location)). Two local facts matter for the workflow: the Flatpak's sandbox doesn't mount the host home (its `filesystems` list is only `xdg-download:ro` and a few others, per `flatpak info --show-permissions`), so a jar built in `~/minecraft/` has to be copied into that data tree, and the `26.3` instance's `mmc-pack.json` lists only Minecraft 26.3 and LWJGL 3.4.3, so no mod loader is installed there yet. Loaders install from the instance's Version page, Install tab ([Prism: Version](https://prismlauncher.org/wiki/help-pages/instance-version/)).

## Fabric and NeoForge are a download each; Hytale is a Gradle project against an official Maven repository

The loader comparison is in the earlier report and won't be re-argued: Fabric for this program's key mod, NeoForge if you ever need its ecosystem. What's new since 26.1 is that both toolchains got simpler, because Mojang stopped obfuscating the game. **Obfuscation** was Mojang's old practice of renaming every class and method to meaningless short names in the shipped jar; **mappings** (Yarn, Mojang's official names, Parchment) were the community's tables for turning those back into readable names, and every 1.21-era tutorial starts with a mappings line in `build.gradle`. Fabric's October 2025 post explains that from the first unobfuscated release Yarn "cannot be justified", Intermediary "will no longer exist", and new mods should use Mojang's names directly ([Removing Obfuscation from Fabric](https://fabricmc.net/2025/10/31/obfuscation.html)); NeoForge's 26.1 post says Parchment is no longer needed because "the official parameter names used by the developers of Minecraft are now available" ([NeoForge for 26.1](https://neoforged.net/news/26.1release/)). The practical consequence: the 26.3 Fabric template has **no `mappings` line at all**, and anything in an older tutorial about `loom.officialMojangMappings()` or Yarn version strings is dead text.

### Fabric 26.3: generate, `genSources`, `runClient`, `build`

Generate a project at fabricmc.net/develop/template (mod name, a lowercase dotted package name, Minecraft version; Advanced Options add Kotlin and data generators), unzip it to a path with no spaces, cloud sync, or non-ASCII characters, then edit `gradle.properties` and `fabric.mod.json` for your mod id and name ([Fabric: Creating a Project](https://docs.fabricmc.net/develop/getting-started/creating-a-project)). As of 2026-10-13 the example mod pins `minecraft_version=26.3`, `loader_version=0.19.5`, `loom_version=1.18-SNAPSHOT`, and `fabric_api_version=0.162.0+26.3`, with `org.gradle.jvmargs=-Xmx1G` and the configuration cache on ([gradle.properties](https://raw.githubusercontent.com/FabricMC/fabric-example-mod/master/gradle.properties)); Fabric's own 26.3 blog post named Loom 1.17 and Gradle 9.6.0 "at time of writing" on 2026-09-15, and the template simply moved on when Loom 1.18 shipped five days later ([Fabric for 26.3](https://fabricmc.net/2026/09/15/263.html)). Loader 0.19.5 is the only stable loader for 26.3 ([Fabric meta](https://meta.fabricmc.net/v2/versions/loader/26.3)), and Fabric API `0.162.0+26.3` (2026-10-06) is the newest 26.3 build, with `0.162.3+26.4` pre-releases already tracking 26.4 snapshots ([Fabric API releases](https://github.com/FabricMC/fabric/releases)).

The template's shape is worth knowing before you open it. `build.gradle` applies `net.fabricmc.fabric-loom`, calls `splitEnvironmentSourceSets()`, and compiles with `options.release = 25` ([build.gradle](https://raw.githubusercontent.com/FabricMC/fabric-example-mod/master/build.gradle)). A **source set** is Gradle's name for one tree of source files compiled as a unit; the split gives you `src/main/java` for code that runs on both sides and `src/client/java` for rendering, key bindings, and anything else that must never load on a dedicated server, so calling client code from the common side is a compile error rather than a server crash ([Fabric: Project Structure](https://docs.fabricmc.net/develop/getting-started/project-structure); [Loom options](https://docs.fabricmc.net/develop/loom/options)). `fabric.mod.json` declares two **entrypoints** (the classes Fabric instantiates at start-up: `com.example.ExampleMod` implementing `ModInitializer` and a client class implementing `ClientModInitializer`), two Mixin config files, and dependencies `fabricloader >=0.19.5`, `minecraft ~26.3`, `java >=25`, and `fabric-api *` ([fabric.mod.json](https://raw.githubusercontent.com/FabricMC/fabric-example-mod/master/src/main/resources/fabric.mod.json)). The `~26.3` range accepts 26.3.x hotfixes and rejects 26.4, which is a clear loader error rather than a mystery crash ([fabric.mod.json reference](https://docs.fabricmc.net/develop/loader/fabric-mod-json)).

The commands are the same from any editor: `./gradlew genSources` once (it decompiles Minecraft so your editor can show game source; "can take a while"), `./gradlew runClient` or `runServer` to play, `./gradlew build` to get `build/libs/<archive_base_name>-<version>.jar` ([Fabric: Generating Sources](https://docs.fabricmc.net/develop/getting-started/intellij-idea/generating-sources); [Fabric wiki: setup](https://wiki.fabricmc.net/_export/raw/tutorial:setup); [Fabric: Building a Mod](https://docs.fabricmc.net/develop/getting-started/building-a-mod)). Loom 1.18 made run configurations Gradle-task based by default and added an experimental `./gradlew microsoftLogin` task so a dev client can be signed in ([Loom 1.18](https://github.com/FabricMC/fabric-loom/releases/tag/1.18)); the default dev client runs without a login as an offline-named player, which is what every tutorial assumes (inferred from the task being optional; not confirmed on this machine). The third-party DevAuth mod documents support only through 1.21.11, so try `microsoftLogin` first ([DevAuth](https://github.com/DJtheRedstoner/DevAuth)). Installing into Prism is `cp build/libs/<mod>-1.0.0.jar` into `instances/26.3/minecraft/mods/` next to `fabric-api-0.162.0+26.3.jar`, after installing Fabric Loader 0.19.5 from the instance's Version page; skip the `-sources.jar` that `withSourcesJar()` also writes.

**Mixins** deserve one paragraph because every template wires them in and no beginner needs them. A Mixin is a class that rewrites a vanilla class's bytecode at load time (`@Mixin` names the target, `@Inject` adds code to a method without removing the original), and Fabric's own wiki says learning them without knowing what Java bytecode is "is not recommended" ([Fabric wiki: Mixin introduction](https://wiki.fabricmc.net/tutorial:mixin_introduction)). The Fabric API events page says it plainly: "events often substitute for mixins" ([Fabric: Events](https://docs.fabricmc.net/develop/events/)). Adding items, blocks, commands, and key bindings never touches them; MixinExtras has been bundled in Fabric Loader since 0.15 and was updated again in 0.19.5 ([Loader 0.19.5](https://github.com/FabricMC/fabric-loader/releases/tag/0.19.5)). Because 26.x has no obfuscation, the "refmap" and remapping worries in 1.21-era Mixin tutorials no longer apply; targets are written with Mojang's names.

### NeoForge 26.3: same shape, one source set, a slower first import

Download a template from the NeoForge Mod Generator with ModDevGradle selected, or clone `neoforgemdks/MDK-26.3-ModDevGradle`; the `neoforgemdks` organisation keeps a generated repo per Minecraft version and plugin flavour and accepts no issues or PRs ([neoforgemdks](https://github.com/neoforgemdks)). The 26.3 MDK pins ModDevGradle `2.0.148` (the newest on the plugin portal, 2026-09-29), a Java 25 toolchain, NeoForge `26.3.0.69-beta`, and runs named `client`, `server`, `gameTestServer`, and `data` ([MDK build.gradle](https://raw.githubusercontent.com/neoforgemdks/MDK-26.3-ModDevGradle/main/build.gradle); [plugin portal](https://plugins.gradle.org/plugin/net.neoforged.moddev)). NeoForge's Maven already lists `26.3.0.76` without the `-beta` suffix, which under NeoForge's scheme means breaking changes are no longer allowed, so raise `neo_version` in `gradle.properties` if you start now ([NeoForge Maven](https://maven.neoforged.net/api/maven/versions/releases/net/neoforged/neoforge); [NeoForge for 26.1](https://neoforged.net/news/26.1release/)). No NeoForge blog post announces 26.2 or 26.3 at all; the newest news item is from May 2026 ([neoforged.net/news](https://neoforged.net/news/)).

Three differences from Fabric matter day to day. The mod descriptor, `neoforge.mods.toml`, sits in `src/main/templates/META-INF/` and is filled from `gradle.properties` (`mod_id`, `mod_name`, `mod_license`, `mod_version`) at build time, so you edit the properties file, not the TOML ([MDK neoforge.mods.toml](https://raw.githubusercontent.com/neoforgemdks/MDK-26.3-ModDevGradle/main/src/main/templates/META-INF/neoforge.mods.toml); [NeoForge: Mod Files](https://docs.neoforged.net/docs/gettingstarted/modfiles)). There is one source set, not a client/common split. And the first Gradle import "can take up to an hour because Gradle downloads and decompiles dependencies", against Fabric's shorter decompile-only `genSources` ([NeoForge: Getting Started](https://docs.neoforged.net/docs/gettingstarted/)). The docs say runs happen in `runs/client` and `runs/server` while the ModDevGradle README says each run defaults to `run`; the MDK sets neither explicitly, so look after the first `runClient`. Access transformers (NeoForge's text-file way of making a private vanilla member public, the counterpart of Fabric's access wideners) are picked up automatically from `src/main/resources/META-INF/accesstransformer.cfg` ([NeoForge: Access Transformers](https://docs.neoforged.net/docs/advanced/accesstransformers)). For a Python programmer the NeoForge event model is the more conceptual of the two: handlers register with a method reference (`NeoForge.EVENT_BUS.addListener(YourMod::onLivingJump)`) or `@SubscribeEvent`, and listening to an abstract event class such as `BlockEvent` crashes the game, which is inheritance made concrete ([NeoForge: Events](https://docs.neoforged.net/docs/concepts/events/)).

### Hytale: official API and Maven repo, community templates, and an API that moves every update

Hytale needs the confirmed/inferred split the reader asked for, so here it is explicitly. **Official, from hytale.com and docs.hytale.com:** the game entered paid Early Access on 2026-01-13 for Windows, macOS, and Linux x64 at US$19.99, sold only through hytale.com ([hytale.com launch post](https://hytale.com/news/2026/1/hytale-is-finally-here); [Wikipedia: Hytale](https://en.wikipedia.org/wiki/Hytale)). Linux is an "experimental" native build shipped as a Flatpak you download from hytale.com and install by hand (`flatpak install hytale-launcher-latest.flatpak`, run as `com.hypixel.HytaleLauncher`); it isn't on Flathub, and its data lives at `~/.var/app/com.hypixel.HytaleLauncher/data/Hytale/` ([hytale.com/download](https://hytale.com/download); [Update 5 pre-release notes](https://hytale.com/news/2026/4/hytale-pre-release-patch-notes-update-5); [Flathub Discourse](https://discourse.flathub.org/t/why-is-the-hytale-launcher-still-not-on-flathub/11713)). Modding is server-side by design: Java plugins (jars with a `manifest.json`) plus data-driven asset packs, with "visual scripting" planned and text scripting such as Lua deliberately rejected; the client is C# and closed ([Hytale modding strategy](https://hytale.com/news/2025/11/hytale-modding-strategy-and-status)). Singleplayer runs a local server, so plugins work there too. There is an official Javadoc, "Hytale Server API 0.7.0", whose entry packages are `com.hypixel.hytale.server.core.plugin`, `com.hypixel.hytale.component` (an entity-component system, or **ECS**, where game objects are bags of data components processed by systems, the pattern Pybricks users have not met but Unity users have), and `com.hypixel.hytale.event` ([docs.hytale.com/api](https://docs.hytale.com/api/)). There is an official Maven repository: `https://maven.hytale.com/release` serves `com.hypixel.hytale:Server` in versions 0.5.10, 0.6.6, 0.6.7, 0.6.8, and 0.7.0, last updated 2026-10-12 (fetched by `curl`) ([maven.hytale.com metadata](https://maven.hytale.com/release/com/hypixel/hytale/Server/maven-metadata.xml)). The server source is readable under a Shared Source agreement (v2.0, effective 2026-07-21): game licence plus a GitHub-linked account gets you private read-only repositories you may read and derive from but not republish ([Shared Source agreement](https://hytale.com/shared-source-license)). The current release is 0.7.0, "Chapter I: Out of the Breach", shipped 2026-10-12, one day before this research ([Chapter I post](https://hytale.com/news/2026/10/chapter-i-out-of-the-breach)).

**Community-documented, not official:** the setup recipe. hytalemodding.dev (the HytaleModding community, 22 repos, a 9,800-member Discord) says "Java 25 or later, OpenJDK recommended", IntelliJ IDEA Community, and `git clone https://github.com/HytaleModding/plugin-template.git MyFirstMod`, with the server API pulled as `implementation("com.hypixel.hytale:Server:+")` from the official repo, which "provides jars for the last five releases" ([hytalemodding.dev setup](https://hytalemodding.dev/en/docs/guides/plugin/setting-up-env); [HytaleModding org](https://github.com/HytaleModding)). That template is Kotlin DSL, applies a community Gradle plugin (`com.azuredoom.hytale-tools`), generates `manifest.json` from `gradle.properties`, and offers `./gradlew setupHytaleDev`, `runServer`, and `runServer -Ddebug=true -Dhotswap=true` for a debugger plus hot swap on the JetBrains Runtime ([plugin-template README](https://github.com/HytaleModding/plugin-template)). The alternative `realBritakee/hytale-template-plugin` (Groovy DSL, 258 stars) builds a shadow jar, downloads and caches the server jar from a URL you supply, copies the plugin into the server's `mods/`, and listens for a debugger on `localhost:5005` with `-Pdebug` ([hytale-template-plugin](https://github.com/realBritakee/hytale-template-plugin)). Testing is `./gradlew build` → `build/libs/<name>-<version>.jar`, `./gradlew runServer`, then in the game add a private server at `localhost` ([hytalemodding.dev build and test](https://hytalemodding.dev/en/docs/guides/plugin/build-and-test)); the server listens on UDP 5520 and asks for a one-time device-code sign-in on first run ([gameserverkings](https://www.gameserverkings.com/knowledge-base/hytale/hytale-dedicated-server/)). A plugin's main class extends `JavaPlugin`, takes a `JavaPluginInit` in its constructor, and overrides `setup()`, `start()`, and `shutdown()`, with commands and events reached through registries; this comes from an unofficial docs mirror dated January 2026 ([hytale-server docs mirror](https://gitea.minidev.space/hytale/hytale-server/src/branch/main/docs/01-getting-started.md)). Kaupenjoe's tutorial template (February 2026) uses a Java 25 toolchain and a different community plugin and Maven host ([Hytale-Tutorial-Plugin](https://github.com/Tutorials-By-Kaupenjoe/Hytale-Tutorial-Plugin)). Distribution is CurseForge, the official partner with an in-game Mod Browser since Update 6 where "paid mods are not allowed"; Modrinth "does not currently support Hytale and has no plans" ([CurseForge how-to](https://blog.curseforge.com/how-to-create-hytale-mods/); [Update 6 notes](https://hytale.com/news/2026/8/update-6-patch-notes); [Modrinth on Hytale](https://support.modrinth.com/en/articles/13415240-hytale-support-on-modrinth)).

**Inferred or unknown:** whether the server runs on JDK 27 (nothing says it doesn't; install 25 and match the documented requirement); what "early plugins" (a separate `earlyplugins/` folder gated by `--accept-early-plugins`) technically are; whether jdtls imports the template cleanly (it's an ordinary Gradle project resolving from a Maven repo, so it should, but nobody has written it up); whether there's a plugin hot-reload command as opposed to JVM hot swap; and the official Downloader CLI's exact flags, because support.hytale.com sits behind a Cloudflare challenge that scripts can't pass. The risk is the API itself, and this part is official: Update 6 (2026-08-27) moved the protocol from `hytale/2` to `hytale/3` so "servers and plugins need a rebuild before they will connect", and Update 7's "Modder-Facing Patch Notes" (2026-10-12) delete `ChunkAccessor`, `IWorldChunks`, and four related interfaces, remove `WorldChunk.setBlock`/`breakBlock` overloads, remove `ClientFeature` constants ("Plugins referencing them will not compile"), change a packet's wire layout, and rename assets so old ones fail to load ([Update 6 notes](https://hytale.com/news/2026/8/update-6-patch-notes); [Update 7 modder notes](https://hytale.com/news/2026/10/modder-facing-patch-notes-update-7)). Stable releases land every two to six weeks with weekly pre-releases, no API-stability policy or 1.0 date has been announced, and the YouTube beginner series are nine to ten months old, so use them for workflow, not code ([Wikipedia: Hytale](https://en.wikipedia.org/wiki/Hytale)). The honest summary: Hytale is the easier Java (published Javadoc, readable unobfuscated source, no mixins, no mappings, a Bukkit/Paper-shaped plugin model) and the riskier platform to build a term's teaching on.

### Neovim 0.12: nvim-jdtls on Mason's jdtls, with a memory cap and a Gradle JVM

Neovim's built-in `vim.lsp` can start jdtls on its own through nvim-lspconfig's `lsp/jdtls.lua`, but for Minecraft work that's not enough: when you jump to a Minecraft or Fabric API class, jdtls returns a `jdt://` URI for a decompiled class, and Neovim core can't open those yet (issue #39526, open since 2026-04-30), so the jump fails silently ([nvim-lspconfig jdtls.lua](https://raw.githubusercontent.com/neovim/nvim-lspconfig/master/lsp/jdtls.lua); [neovim #39526](https://github.com/neovim/neovim/issues/39526)). **nvim-jdtls** adds that handler (it still issues the older `java/classFileContents` request, which jdtls 1.61+ keeps answering after adding the LSP 3.18 replacement), plus refactoring commands, test runners, and automatic registration of a `java` debug adapter when nvim-dap is present ([nvim-jdtls README](https://github.com/mfussenegger/nvim-jdtls); [nvim-jdtls source](https://raw.githubusercontent.com/mfussenegger/nvim-jdtls/master/lua/jdtls.lua); [eclipse.jdt.ls PR #3855](https://github.com/eclipse-jdtls/eclipse.jdt.ls/pull/3855)). Its README frames the audience as people "who prefer configuration as code over GUI configuration. Ease of use is not the main priority", which is fair warning.

Where jdtls comes from: Arch's repos don't have it; the AUR has `jdtls 1.61.0-1`, and Mason's `jdtls` package is also 1.61.0 and additionally ships `lombok.jar`; Mason's `java-debug-adapter` (0.59.0) and `java-test` (0.46.0) supply the debugger and test-runner jars that nvim-jdtls wants in `init_options.bundles` ([AUR jdtls](https://aur.archlinux.org/packages/jdtls); [Mason jdtls](https://raw.githubusercontent.com/mason-org/mason-registry/main/packages/jdtls/package.yaml); [Mason java-debug-adapter](https://raw.githubusercontent.com/mason-org/mason-registry/main/packages/java-debug-adapter/package.yaml)). jdtls needs Java 21 or newer to run, and 1.62.0 (2026-10-01) "Added Java 27 support" ([eclipse.jdt.ls README](https://github.com/eclipse-jdtls/eclipse.jdt.ls); [CHANGELOG](https://raw.githubusercontent.com/eclipse-jdtls/eclipse.jdt.ls/master/CHANGELOG.md)). Two traps are specific to this machine and this project type. First, the `jdtls` launcher script sets `-Xms1G` and **no `-Xmx`**, so a Loom project (Minecraft plus hundreds of library jars) gets the JVM's default quarter-of-RAM cap; set one explicitly ([jdtls.py](https://raw.githubusercontent.com/eclipse-jdtls/eclipse.jdt.ls/master/org.eclipse.jdt.ls.product/scripts/jdtls.py)). Second, jdtls imports Gradle projects through Buildship, which runs the project's wrapper on whatever `java.import.gradle.java.home` says (the settings are the same ones vscode-java documents), so with JDK 27 as default and no override it would hit the same wrapper failure as the terminal ([vscode-java README](https://raw.githubusercontent.com/redhat-developer/vscode-java/master/README.md)). Option A above (25 as the system default) makes that second trap vanish.

Dave's `lsp-setup.lua` is kickstart-style and runs `mason-lspconfig`, which since v2 calls `vim.lsp.enable()` for every Mason-installed server; nvim-jdtls's README says not to also call `vim.lsp.enable('jdtls')` when using its `start_or_attach`, so exclude it: `require("mason-lspconfig").setup { automatic_enable = { exclude = { "jdtls" } } }` ([mason-lspconfig](https://github.com/mason-org/mason-lspconfig.nvim)). Then add `{ 'mfussenegger/nvim-jdtls', dependencies = { 'mfussenegger/nvim-dap' } }` to the plugin list, `:MasonInstall jdtls java-debug-adapter java-test`, and an `ftplugin/java.lua` along these lines (assembled from the cited READMEs; not yet run on this machine):

```lua
local mason = vim.fn.stdpath('data') .. '/mason'
local root = vim.fs.root(0, { 'gradlew', 'mvnw', '.git' }) or vim.fn.getcwd()
local ws = vim.fn.stdpath('cache') .. '/jdtls-ws/' .. vim.fn.fnamemodify(root, ':p:h:t')
local bundles = {}
vim.list_extend(bundles, vim.split(vim.fn.glob(mason .. '/share/java-debug-adapter/*.jar'), '\n', { trimempty = true }))
vim.list_extend(bundles, vim.split(vim.fn.glob(mason .. '/share/java-test/*.jar'), '\n', { trimempty = true }))
require('jdtls').start_or_attach {
  name = 'jdtls',
  cmd = { mason .. '/bin/jdtls', '--jvm-arg=-Xmx4G', '-data', ws },
  root_dir = root,
  settings = { java = {
    import = { gradle = { wrapper = { enabled = true },
                          java = { home = '/usr/lib/jvm/java-25-openjdk' } } },
    configuration = { runtimes = {
      { name = 'JavaSE-25', path = '/usr/lib/jvm/java-25-openjdk', default = true } } },
    contentProvider = { preferred = 'fernflower' },
  } },
  init_options = { bundles = bundles },
}
```

The per-project `-data` directory matters because jdtls's default workspace is derived from the folder name under `~/.cache/jdtls`, so two projects both called `mod` would share an index ([jdtls.py](https://raw.githubusercontent.com/eclipse-jdtls/eclipse.jdt.ls/master/org.eclipse.jdt.ls.product/scripts/jdtls.py)). After adding a dependency, run `:JdtUpdateConfig`; `:JdtWipeDataAndRestart` is the reset button. A public Neovim config built specifically for Fabric and NeoForge uses exactly this Mason trio plus `google-java-format` ([metalpietie/nvim-config](https://github.com/metalpietie/nvim-config)). What you give up relative to IntelliJ is Mixin awareness: the only Neovim attempt, `cotrin8672/mc-dev-lsp`, is a 0-star jdtls extension with non-standard navigation ([mc-dev-lsp](https://github.com/cotrin8672/mc-dev-lsp)). Whether jdtls attaches Loom's `genSources` output automatically is unverified; expect FernFlower decompilation (correct names, no Javadoc) as the baseline.

### Emacs 31: lsp-java is fuller, eglot-java is lighter, both need the same two fixes

Both Emacs routes wrap the same jdtls and both still send `java/classFileContents` for decompiled classes, so navigation into Minecraft works in either ([lsp-java.el](https://raw.githubusercontent.com/emacs-lsp/lsp-java/master/lsp-java.el); [eglot-java.el](https://raw.githubusercontent.com/yveszoundi/eglot-java/main/eglot-java.el)). **lsp-java** 4.0 requires Emacs 29.1, lsp-mode 10, and dap-mode 0.5, auto-downloads jdtls 1.57.0 (February 2026; `lsp-java-update-server` fetches newer), registers `java-mode`, `java-ts-mode`, and `jdee-mode`, and brings `dap-java` with test debugging; its docs still say "JDK 17" and "Limited Gradle support" ([lsp-java docs](https://emacs-lsp.github.io/lsp-java/); [dap-mode Java](https://emacs-lsp.github.io/dap-mode/page/configuration/)). **eglot-java** 1.35 sits on Emacs's built-in eglot, auto-installs the current Homebrew-stable jdtls, runs Gradle tasks and JUnit tests from Emacs, but registers only `java-mode` in its own code and leaves debugging to the separate `dape` package plus a Microsoft java-debug jar you supply in `:bundles` ([eglot-java README](https://github.com/yveszoundi/eglot-java); [dape README](https://raw.githubusercontent.com/svaante/dape/master/README.org)). The two fixes: both default to `-Xmx1G` (`lsp-java-vmargs`, `eglot-java-eclipse-jdt-args`), too small for a mod workspace, and both need the Gradle JVM pointed at 25 unless it's the system default. For Emacs 31's `java-ts-mode`, install the tree-sitter grammar first (`M-x treesit-install-language-grammar java`); hooking eglot-java onto `java-ts-mode` is an addition beyond what its code registers and wasn't verified. The lsp-java route, as a `use-package` block (untested here):

```elisp
(use-package lsp-java
  :after lsp-mode
  :hook ((java-mode java-ts-mode) . lsp-deferred)
  :custom
  (lsp-java-vmargs '("-XX:+UseParallelGC" "-XX:GCTimeRatio=4" "-XX:AdaptiveSizePolicyWeight=90"
                     "-Dsun.zip.disableMemoryMapping=true" "-Xmx4G" "-Xms100m"))
  (lsp-java-import-gradle-java-home "/usr/lib/jvm/java-25-openjdk")
  (lsp-java-configuration-runtimes
   '[(:name "JavaSE-25" :path "/usr/lib/jvm/java-25-openjdk" :default t)]))
(use-package dap-mode :after lsp-mode :config (dap-auto-configure-mode))
(use-package dap-java :ensure nil :after lsp-java)
```

For eglot-java the equivalent is `eglot-java-eclipse-jdt-args` with `-Xmx4G` and an `eglot-java-user-init-opts-fn` returning `(:bundles [...] :settings (:java (:import (:gradle (:java (:home "/usr/lib/jvm/java-25-openjdk"))))))`. Running Gradle from Emacs is `M-x compile` with `./gradlew runClient` from the project root, or `eglot-java-project-build-task`, which prompts for a task. Nobody has written up Minecraft modding in Emacs specifically; the evidence is the packages' source and general Java use.

Two shared housekeeping points. Formatting from any editor is Spotless plus google-java-format (`spotless { java { googleJavaFormat() } }`, `./gradlew spotlessApply`), with `google-java-format 1.37.0` in the AUR and in Mason ([Spotless](https://github.com/diffplug/spotless/blob/main/plugin-gradle/README.md); [AUR google-java-format](https://aur.archlinux.org/packages/google-java-format)). And the Fabric template's `.gitignore` already lists IntelliJ's `.idea/` and `*.iml` and the Eclipse-style `.classpath`, `.project`, `.settings/`, and `bin/` that jdtls writes, so one checkout can be opened by IDEA and Neovim in turn without either polluting git ([fabric-example-mod](https://github.com/FabricMC/fabric-example-mod)). The sensible split for this machine, given a kickstart Neovim and Emacs 31 already in daily use: IntelliJ for the first Minecraft and Hytale projects and anything Mixin-heavy, Neovim or Emacs for editing the same checkout once the Gradle side is familiar, Android Studio for FTC.

## Learn Java 21's working subset in 20 to 40 hours, then let the loader docs teach the dialect

Learn against JDK 25 because the toolchain demands it, but the language you'll use is "Java 21 plus nothing you'll notice", so Java 21-era material isn't stale for syntax. Oracle's language-changes table dates the features modding code leans on: `var` (10), switch expressions (14), text blocks (15), records and pattern matching for `instanceof` (16), sealed classes (17), pattern matching for `switch` and record patterns (21); Java 25's additions are module imports, "compact source files" with an instance `main` (JEP 512, aimed at beginners' first programs), and flexible constructor bodies ([Oracle: Java 25 language changes](https://docs.oracle.com/en/java/javase/25/language/java-language-changes-summary.html); [JEP 512](https://openjdk.org/jeps/512)). Nothing in the 26.x loader docs uses Java-25-only syntax, and every mod class is a normal class in a package, so the compact form is a nice first hello-world and nothing more. Skip modules and `jlink`, JavaFX and Swing, virtual threads, reflection (Mixins hide it), and certification material.

Modding Java is a narrow dialect, and the first-item page shows all of it in forty lines: `public static final` registry fields initialised at class-load time, a `register` helper taking a `Function<Item.Properties, Item>` and a constructor reference (`Item::new`), generics in keys (`ResourceKey<Item>`), builder-style chaining (`new Item.Properties().stacksTo(16)`), an empty `static void initialize()` whose only job is to force the class to load, and a lambda registered on an event ([Fabric: Creating Your First Item](https://docs.fabricmc.net/develop/items/first-item)). Add subclassing and `@Override` of game classes, annotations as metadata (`@Mod`, `@SubscribeEvent`, `@Mixin`), enums, records (used in codecs and packets), `Optional`, interfaces as entrypoints, and the mental model that client and server are separate programs even in singleplayer (Fabric: "there is always a server running, even in singleplayer and LAN") ([Fabric: Networking](https://docs.fabricmc.net/develop/networking)). For a Python and C programmer the mapping is direct: `static` fields are module-level globals with C-like initialisation order, where class loading replaces link-time init and Fabric's empty `initialize()` exists only to trigger it; generics are the type hints you already write, now enforced; lambdas pass functions with the restriction that captured locals are effectively final; checked exceptions are a compiler-enforced `try`/`except` or `throws` with no analogue in either language; `Optional` is an explicit `None` container; there are no pointers, but `null` plays the dangling pointer and `NullPointerException` the segfault; and a package is a directory path that also feeds the mod id. The sources agree the first-day cost is Gradle and the first dependency sync, not the language, and the practical rule is to treat `build.gradle` and `gradle.properties` as config to bump versions in, not code to write, until you need a dependency.

## The daily loop is edit, `runClient`, read `run/logs/latest.log`, and bump versions once a quarter

The template already contains "hello world": `ExampleMod.java` creates a logger named after the mod id and calls `LOGGER.info("Hello Fabric world!")` in `onInitialize()` ([ExampleMod.java](https://raw.githubusercontent.com/FabricMC/fabric-example-mod/master/src/main/java/com/example/ExampleMod.java)). From there the docs' progression is stable: a custom item (three Java edits plus a lang file, a 16×16 PNG, a model, and an item definition), a custom block (the same plus a blockstate file and a loot table in exactly the data-pack format the makerspace already writes), a command (one lambda on `CommandRegistrationCallback` building a Brigadier tree, where a `Command` returns a positive int for success), a key binding (client-only, `KeyMapping` plus `InputConstants.KEY_J`, polled in `ClientTickEvents.END_CLIENT_TICK` with a guard because "holding the key fires repeatedly"), and, as a capstone rather than a lesson, an entity, which the docs rate "moderate to high" and which needs ten Java classes and a texture ([first item](https://docs.fabricmc.net/develop/items/first-item); [first block](https://docs.fabricmc.net/develop/blocks/first-block); [commands](https://docs.fabricmc.net/develop/commands/basics); [key mappings](https://docs.fabricmc.net/develop/key-mappings); [first entity](https://docs.fabricmc.net/develop/entities/first-entity)). Hand-written JSON is the better default for someone who knows data packs; data generation (`fabricApi { configureDataGeneration() }`, a `fabric-datagen` entrypoint, `./gradlew runDatagen` writing to `src/main/generated`) pays off only past a handful of items ([Data Generation Setup](https://docs.fabricmc.net/develop/data-generation/setup)). A mod jar's root `data/` and `assets/` folders load as the mod's own always-on pack, which is how the first-block guide ships its loot table; the `resourcepacks/<name>/` plus `registerBuiltinResourcePack` route is for optional packs the player can toggle ([Fabric API resource package](https://maven.fabricmc.net/docs/fabric-api-0.160.4+26.3/net/fabricmc/fabric/api/resource/package-summary.html)).

Debugging has one directory and one page. Every Loom run uses `<project>/run` and passes `-Dfabric.development=true`, so logs are `run/logs/latest.log` and crash reports `run/crash-reports/` ([Loom introduction](https://docs.fabricmc.net/develop/loom/); [Fabric: Debugging Mods](https://docs.fabricmc.net/develop/debugging)). Missing textures only warn (the item shows pink-and-black), typos in JSON are the commonest run-time crash, and a start-up crash whose stack trace names `mod-id$handlerName` is a Mixin failure, which for a beginner who never writes Mixins means a version mismatch ([Fabric: crash reports](https://docs.fabricmc.net/players/troubleshooting/crash-reports)). Breakpoints need a Debug launch rather than Run; in IntelliJ that's a button, and from a terminal it's a JDWP agent flag in the run's `jvmArguments` plus an attach from nvim-dap or dape, a standard JVM mechanism that neither Fabric nor Loom documents, so it's unverified for Loom 1.18 specifically. Hot swap is where the **JetBrains Runtime** matters: stock HotSpot can only replace method bodies while the game runs, but JBR's DCEVM patch, enabled with `-XX:+AllowEnhancedClassRedefinition`, lets you add and remove methods, fields, and classes; Loom takes it as a `jvmArguments.add(...)` on the client run, ModDevGradle shows the same flag in its README, and JBR 25 builds exist (25.0.4.1, October 2026) though the releases page doesn't say which carry DCEVM ([Fabric: Launching the Game](https://docs.fabricmc.net/develop/getting-started/intellij-idea/launching-the-game); [JetBrainsRuntime](https://github.com/JetBrains/JetBrainsRuntime); [JBR releases](https://github.com/JetBrains/JetBrainsRuntime/releases)). A dev server is `./gradlew runServer`, then accept `eula.txt` and set `online-mode=false` so the unauthenticated dev player can join ([NeoForge: Getting Started](https://docs.neoforged.net/docs/gettingstarted/)). Tests exist on both loaders if you want them (Fabric: `fabric-loader-junit` plus a game-test DSL; NeoForge: a `gameTestServer` run and `unitTest { enable() }`), and `./gradlew build` runs Fabric's server game tests, so a plain compile check is faster as `./gradlew jar` ([Fabric: Automatic Testing](https://docs.fabricmc.net/develop/automatic-testing); [ModDevGradle README](https://github.com/neoforged/ModDevGradle)).

Version churn is the recurring tax, and it has a rhythm now: "three to four game drops are released each year in a quarterly schedule", 2026's being 26.1 (Mar 24), 26.2 (Jun 16), 26.3 (Sep 15), and 26.4 to come ([Minecraft Wiki: Game drop](https://minecraft.wiki/w/Game_drop)). Fabric and NeoForge each ship a blog post and new template per drop; Loom has released every one to two months (1.14 in December to 1.18 in September) with rising Gradle minimums; Fabric API publishes pre-releases per snapshot within days; NeoForge's 26.3 took about four weeks to reach a non-beta build ([Loom releases](https://github.com/FabricMC/fabric-loom/releases); [Fabric API releases](https://github.com/FabricMC/fabric/releases)). The update recipe on Fabric is to change `minecraft_version`, `loader_version`, `fabric_api_version`, and `loom_version` in `gradle.properties` to the numbers on fabricmc.net/develop, bump `"minecraft": "~26.4"`, reload Gradle, and fix compile errors against the blog's breaking-change list; 26.3's list is long (removed registries in favour of data components, GLFW replaced by SDL so use `InputConstants`, worldgen renames) even though the first-item, block, command, and key-binding flows were untouched ([Fabric for 26.3](https://fabricmc.net/2026/09/15/263.html)). Pin for a semester: freeze the four properties and commit the wrapper on day one, and since the docs lag a drop and 26.4 lands around December, 26.3 is the right pin for the fall. Multi-loader and multi-version tooling exists and is alive (Architectury API 22.0.5 for both loaders on 26.3; Stonecutter's comment-based preprocessor; Sinytra Connector running Fabric mods on NeoForge, but only for 26.1.2 and 1.21.1), and none of it belongs in a first year: one loader, one version, one semester ([Architectury on Modrinth](https://api.modrinth.com/v2/project/architectury-api/version); [Stonecutter](https://codeberg.org/stonecutter/stonecutter/raw/branch/0.9/README.md); [Sinytra Connector](https://github.com/Sinytra/Connector)).

Distribution is the earlier report's exported-Prism-instance answer, with the licensing note added. The Minecraft EULA says mods you write from scratch belong to you "as long as you don't sell them for money", and a mod must not contain "a substantial part of our copyrightable code" ([Minecraft EULA](https://www.minecraft.net/en-us/eula)); the Fabric template ships `"license": "CC0-1.0"` and the loader reference recommends SPDX identifiers ([fabric.mod.json reference](https://docs.fabricmc.net/develop/loader/fabric-mod-json)). Publishing to Modrinth is a good graduation exercise for a teen (slug, SPDX licence, version number, changelog) and the Minotaur Gradle plugin 2.10.0 automates uploads with a `MODRINTH_TOKEN` environment variable that must never land in the repo ([Minotaur](https://github.com/modrinth/minotaur)). Gradle's cache under `~/.gradle` will grow to a few gigabytes after a couple of projects (an estimate; Gradle publishes no figures); it cleans itself on 30-day and 7-day rules, and `./gradlew --stop` before any manual deletion ([Gradle directory layout](https://docs.gradle.org/current/userguide/directory_layout.html)).

## Kids at 10 to 14 can edit one class in a pre-built project, with Gradle, JDKs, and accounts kept on the instructor's side

The earlier reports' conclusion for the current program stands: commands and data packs are the medium for 8–14s, and the Java mod is instructor plumbing. This section is about a later, optional track for the older end of that band, and the evidence base for it is vendor practice rather than research. Commercial providers draw the same line everywhere: iD Tech's "Java Coding: Build Mods with Minecraft" is ages 10–12 (from $1,099 on campus, $429 online) and "Advanced Minecraft Modding with Java" is 13–17, where students work "on a living code base"; Code Ninjas runs MCreator for 6–10 and Java-export modding for 8–17; Youth Digital's old Mod Design 1 (ages 8–14, 30-plus hours, Eclipse, teachers on call) was the one well-documented scaffold ([iD Tech](https://wwwapi.idtech.com/courses/java-coding-build-mods-with-minecraft); [Code Ninjas listing](https://ggcity.org/reggister/public/classes/11210); [Youth Digital listing](https://kids.woot.com/offers/youth-digital-learn-java-with-minecraft-4)). Every one of them hides project creation, Gradle, and JDK installs from the child. No peer-reviewed study of Fabric or Forge Java with 10–14s surfaced; the closest work (LearnToMod's blocks-to-JavaScript NSF projects, Kutay's six-week study with fifth-graders, where variables, operators, and conditionals were the least successfully used concepts) is about blocks and computational thinking, not Java ([THE Journal on LearnToMod](https://thejournal.com/articles/2016/08/25/startup-receives-new-nsf-grant-to-expand-minecraft-student-reach.aspx); [Boğaziçi archive](https://digitalarchive.library.bogazici.edu.tr/items/77989368-95d9-4851-8220-40f2886311d4/full)). A practical reading: 10 for a supervised session, 12–13 for independent work.

The scaffold the vendors use can be reconstructed and fits this makerspace. Pre-generate one Fabric 26.3 project per laptop from the template generator, pin JDK 25 and the editor, and give each kid a `ModItems`-style class of their own inside the shared mod with a one-line `initialize()` call from the entrypoint, so the child edits an existing file and never creates a project; keep Mixins, networking, and datagen out of the kids' files. Session shapes follow from the docs' step counts and one measured data point, a free UK workshop for ages 10+ that fits JDK install, IntelliJ, the example mod, and a first item into about 1.5 hours and reports that Gradle sync is "the #1 stuck point in the whole series" (wrong JDK, firewalls blocking `services.gradle.org`, impatience), that the first sync "downloads about 500MB" and "can take 10-20 min on slow connections", and that the commonest kid errors are creating `ModItems.java` in the wrong package, forgetting to call the register method, and JSON typos ([jvdesignstudio workshop](https://jvdesignstudio.co.uk/workshops/minecraft-first-item-mod.html)). With caches warm, a 60–90 minute slot holds one of: change the log line and find it in `run/logs/latest.log` (10–20 min), a custom item (a full session), a custom block (another), a command (30–45 min, the most natural entry for kids who already type `/` commands, since Brigadier trees mirror what they know and the loot-table JSON is byte-for-byte the data-pack format), or a key binding (30–45 min, teaching the client/server split). These durations are inference. A seven-week public-domain course, "Basics of Java in Minecraft", already uses the Fabric toolchain to teach Java itself (environment, types and control flow, classes and inheritance, arrays, polymorphism, a planned project) and could be adapted ([coder0987/Basics-of-Java-in-Minecraft](https://github.com/coder0987/Basics-of-Java-in-Minecraft)).

The logistics that decide feasibility are offline Gradle and accounts. Gradle's `--offline` flag uses cached modules only and "makes no network requests for dependency resolution", a cache can be copied to another machine with the same Gradle version ("don't copy `*.lock` or `gc.properties` files"), and the incubating `GRADLE_RO_DEP_CACHE` points several builds at one read-only copy on a share ([Gradle: Dependency caching](https://docs.gradle.org/current/userguide/dependency_caching.html)). So the recipe is: build and `runClient` once online on one laptop, rsync `~/.gradle/caches` and `~/.gradle/wrapper` to the others, and run `./gradlew --offline runClient`; Loom's own Minecraft jars and assets live under that same cache tree. Keep each kid's project in its own folder, because Gradle's daemon and `run/` directory are per project. The dev client launched by Loom needs no Prism and no account (inferred from `microsoftLogin` being an optional task), so the modding sessions can run entirely from the project folder; Prism and accounts only enter when kids want the built jar in "real" Minecraft with friends. There, Prism's own code says "You must add a Microsoft account that owns Minecraft before you can add an offline account", and an account that doesn't own the game is offered Demo mode only ([Prism AccountListPage.cpp](https://raw.githubusercontent.com/PrismLauncher/PrismLauncher/develop/launcher/ui/pages/global/AccountListPage.cpp); [Prism LaunchController.cpp](https://raw.githubusercontent.com/PrismLauncher/PrismLauncher/develop/launcher/LaunchController.cpp)); the EULA puts a minor's account creation on the parent, and "using one Minecraft account on two computers won't let both join the same world" ([Minecraft EULA](https://www.minecraft.net/en-us/eula); [Minecraft Wiki: LAN world](https://minecraft.wiki/w/Tutorial:Setting_up_a_LAN_world)). Whether a nonprofit lending one licensed account to successive children on a shared laptop satisfies Mojang's terms is a question none of these sources settles. Hytale adds its own version of the same constraint: a local test server authenticates, so every seat needs a US$19.99 account, under-13 accounts need emailed parental consent, and the API churn means a multi-week project must pin the Maven version and the server jar together and avoid the chunk and block APIs Update 7 just rewrote ([Hytale account help](https://support.hytale.com/hc/en-us/articles/44134044725787-How-to-Create-a-Hytale-Account)). A one-session "custom command or chat event" Hytale plugin pinned to a known server version is realistic now; a term on it is not, until the studio announces an API freeze that it hasn't.

## Conclusion

The shape of the answer is that the hard part moved. Two years ago setting up Minecraft modding meant mappings, remapping, and a loader-specific IDE dance; after 26.1 it's an ordinary Gradle project with Mojang's names in it, which is why a language server in Neovim or Emacs is now a legitimate way to work and why Hytale, with an official Javadoc and Maven repository, is the easier Java of the two. What remains hard is everything around the code: the JDK that runs Gradle versus the one that compiles, a quarterly drop cadence that taxes every line of Java, a Hytale API that changes between fortnightly releases, and per-seat accounts that no amount of tooling removes. Spend the setup afternoon on the JDK and one template, spend the Java-learning hours on the Java 21 subset rather than on anything Java 25 added, and treat the editor choice as reversible, since the same checkout opens in all three.

For the makerspace, this reframes "could we teach Java modding?" into "what would the instructor own?" The answer is Gradle, JDKs, caches, version pins, and accounts, all of which a pre-built per-laptop project and a warm offline cache can hide from a 12-year-old, and none of which Hytale lets you hide yet. That makes a Fabric 26.3 "one class per kid" track a plausible thing to pilot with the oldest cohort once the thirty-line key mod has been built and ported through one drop, and it makes Hytale a thing to watch rather than to schedule.
