# Bind N with a thirty-line Fabric mod

Research date: 2026-10-12. Minecraft Java is on 26.3 (data pack format 121, Java 25); 26.4 is in snapshots. Sources are the five research notes in `research_notes/Minecraft modding approaches/`, pulled from loader docs, blog posts, Maven metadata, the Modrinth API, and the local 26.3 client jar.

**Pick Fabric, write a client-only mod, and have it send `trigger tut_key_n` exactly as if the kid had typed it; keep Command Forge itself a pure data pack.** In October 2026 only two loaders matter: Fabric and NeoForge both ship release-day builds for every quarterly drop, Forge is fading (its 26.3 Modrinth catalogue is 30% of Fabric's), and Quilt retired its own APIs in early 2026. Fabric wins for this use case because it has roughly 1.8× NeoForge's 26.3 mods, reaches each drop a day earlier, and already hosts several published "key → chat command" client mods you can copy. The toolchain converged after Mojang stopped obfuscating the game in 26.1: JDK 25, Gradle 9.6, Loom 1.17, Mojang's own names, no remapping, `./gradlew runClient` for a dev loop. A key-to-command mod needs about one class plus a `fabric.mod.json`, no mixins, no server component; on the data pack side it is a `trigger` objective and three lines in `player_tick`. Budget an afternoon for the first build (mostly toolchain) and 10–30 minutes per Minecraft drop afterwards, because a jar is pinned to one game version where your packs span 26.2 and 26.3 with `min_format`/`max_format`. Install by copying the jar into the Prism Flatpak's own data tree (`~/.var/app/org.prismlauncher.PrismLauncher/.../instances/Command Forge/minecraft/mods/`), and ship kids an exported instance `.zip` rather than publishing to Modrinth, whose review queue is currently two to four weeks. Do not teach Java to the 8–14s; the mod is instructor plumbing, and the research base gives no evidence that IDE modding outperforms commands for that age.

## Fabric and NeoForge are the only live loaders, and Fabric fits this job

The 26.1 release on 2026-03-24 reset the modding landscape: it is "the first to require Java 25" and "fully unobfuscated, with no accompanying obfuscated variant" ([Minecraft Wiki: 26.1](https://minecraft.wiki/w/Java_Edition_26.1)). Mojang framed this as "Modding is at the heart of Java Edition – and obfuscation makes modding harder", promised "crash logs will actually be readable", and left the EULA and Usage Guidelines unchanged ([Removing obfuscation in Java Edition](https://www.minecraft.net/en-us/article/removing-obfuscation-in-java-edition)). What Mojang did not do is announce a first-party Java API; the September 2026 Minecraft LIVE produced only a vague "official creator platform" pledge with no date or details ([Minecraft Wiki: LIVE Sept 2026](https://minecraft.wiki/w/Minecraft_Live_%E2%80%93_September_2026)). So the community loaders remain the only way to run code in the game, and Mojang's posture is to make their lives easier rather than replace them.

Both main loaders now ship on release day. Fabric API's first 26.3 build (0.160.5+26.3) was published the **evening before** 26.3 released, and Fabric already publishes for 26.4 snapshots ([Fabric API on Modrinth](https://modrinth.com/mod/fabric-api)); Fabric's 26.3 post names Loader 0.19.5, Loom 1.17, and Gradle 9.6.0 ([Fabric for Minecraft 26.3](https://fabricmc.net/2026/09/15/263.html)). NeoForge's 26.3.0.0-beta POM is dated release day, and it took **75 beta builds over four weeks** to reach the first non-beta 26.3.0.76 on 2026-10-11 ([NeoForge maven-metadata](https://maven.neoforged.net/releases/net/neoforged/neoforge/maven-metadata.xml)); NeoForge's own retrospective says its initial releases land "within roughly 40 minutes to 2 hours 55 minutes of each Minecraft release" and that maintainers are "short-staffed" ([NeoForge: 2025 retrospection](https://neoforged.net/news/2025-retrospection/); [NeoForge for 26.1](https://www.neoforged.net/news/26.1release/)). Forge still publishes (66.0.10 for 26.3, four days after release) but its ecosystem has moved: JEI, Sodium, and Architectury all ship `neoforge`, not `forge`, for 26.3 ([files.minecraftforge.net](https://files.minecraftforge.net/net/minecraftforge/forge/)). Quilt's own February 2026 post retired QSL, QFAPI, and Quilt Mappings because maintenance "has fallen largely on one developer" ([Bringing Quilt into the non-obfuscated era](https://quiltmc.org/en/blog/2026-02-03-non-obfuscated-updates)), so a "Quilt mod" on 26.x is a Fabric mod with a checkbox ticked.

The Modrinth numbers (project counts of type `mod`, queried 2026-10-12) show where developers actually are:

CurseForge is historically heavier on Forge/NeoForge, so this overstates Fabric's overall share, but for 26.x specifically the split is clear: the big content/modpack scene (Create, ATM-style packs) still sits on NeoForge 1.21.1, while the performance and utility scene that chases each new drop is on Fabric ([NeoForge retrospection](https://neoforged.net/news/2025-retrospection/)). For a mod that must track Command Forge's 26.3-only target and may need 26.4 next quarter, that is the decisive fact. The API philosophy difference is real but narrow for your purposes: Fabric is a thin loader plus modular Fabric API where "you can either use a mixin or create your own event" is the documented fallback ([Fabric docs: Events](https://docs.fabricmc.net/develop/events)); NeoForge is batteries-included with a central event bus, priorities, and cancellation ([NeoForge docs: Events](https://docs.neoforged.net/docs/concepts/events)). A keybind mod touches neither distinction, and the two key-mapping APIs are near-identical wrappers over the same vanilla `KeyMapping` class, so switching later is an import-level change. If you ever need both loaders, Architectury 22.0.5 ships for 26.3 on both ([Architectury API](https://modrinth.com/mod/architectury-api)); the Sinytra Connector bridge lags at 26.1.2 and should not be relied on ([Sinytra/Connector](https://github.com/Sinytra/Connector)).

## The toolchain converged: JDK 25, Gradle 9, Mojang names, no remapping

Deobfuscation removed the slowest and most confusing part of pre-2026 modding. Fabric's migration notes for 26.1 say the new `net.fabricmc.fabric-loom` plugin "doesn't remap Minecraft or mods", `modImplementation` becomes plain `implementation`, `remapJar` becomes `jar`, "Yarn is no longer officially supported, so move to Mojang's mappings", and "no mods from 1.21.11 or before will work without, at a minimum, recompilation" ([Fabric for Minecraft 26.1](https://fabricmc.net/2026/03/14/261.html)). NeoForge's side says the same thing in its dialect: "Parchment is no longer needed", set `JavaLanguageVersion.of(25)`, "Gradle 9.1.0 or newer is required" ([NeoForge for 26.1](https://www.neoforged.net/news/26.1release/)). The practical consequence for a Python/C programmer is that you compile against the real Minecraft jar with readable names, stack traces name real methods, and there is no intermediary layer to understand; Fabric meta literally returns intermediary `0.0.0` for 26.x ([Fabric meta API](https://meta.fabricmc.net/v2/versions/intermediary/26.3)).

The dev loop is: generate a project at fabricmc.net/develop/template (mod name, package, Minecraft version; Kotlin and data generators are optional extras; avoid cloud-synced folders and paths with spaces) ([Fabric docs: Creating a Project](https://docs.fabricmc.net/develop/getting-started/creating-a-project)), open it, `./gradlew runClient` to launch a dev client, `./gradlew build` to produce the jar. Fabric "recommends" IntelliJ IDEA with VS Code as the alternative and says "IntelliJ IDEA 2025.3 or later is required for mixins to work correctly" ([Fabric docs: Setting up](https://docs.fabricmc.net/develop/getting-started/setting-up); [Fabric 26.1 post](https://fabricmc.net/2026/03/14/261.html)). My read: for a 30-line mod with no mixins, the IDE is optional. The Gradle wrapper plus nvim covers edit, build, and run; reach for IntelliJ only when you need to browse Minecraft's source or write a mixin. Hot reload exists but is limited: a plain debugger hotswap only replaces method bodies, structural changes need JetBrains Runtime with `-XX:+AllowEnhancedClassRedefinition`, and data packs still reload with `/reload` ([Fabric wiki: hotswapping](https://wiki.fabricmc.net/_export/xhtml/tutorial:hotswapping)). For this mod, "edit, `gradlew build`, copy jar, relaunch instance" is the realistic loop, and it is fine because the Java half will rarely change; the behaviour you iterate on lives in the data pack. One toolchain caveat to verify on your machine: the notes record `java-27-openjdk` from pacman, and Gradle wants a JDK of at least 25 for its own JVM; if Gradle 9.6 refuses a JDK newer than it knows, install a JDK 25 package or let Gradle's toolchain support fetch one. Prism's bundled `java-runtime-epsilon` is a Java 25 *runtime*, good for running the game but not for compiling.

Read only material that targets 26.1 or later. Fabric's docs selector tops out at 26.2 and NeoForge's at 26.1 while the game is on 26.3, so the per-drop blog posts are the authoritative "what changed" lists ([Fabric docs: Develop](https://docs.fabricmc.net/develop/); [docs.neoforged.net](https://docs.neoforged.net/docs/gettingstarted/)). A tutorial is pre-26.x, and will not compile, if it mentions Yarn, intermediary, `modImplementation`, `remapJar`, Parchment as a requirement, Java 17/21, Gradle 8, `ResourceLocation` (renamed `Identifier` in 1.21.11), `ItemGroupEvents`, `HudRenderCallback`, or raw GLFW key codes ([Fabric 26.1](https://fabricmc.net/2026/03/14/261.html); [Fabric 26.3](https://fabricmc.net/2026/09/15/263.html); [NeoForge retrospection](https://neoforged.net/news/2025-retrospection/)). No confirmed 26.x video series was found; Kaupenjoe's courses stop at Forge 1.20.x ([Udemy listing](https://www.udemy.com/course/minecraft-modding-120x-for-forge/)). The old Fabric wiki now redirects beginners to docs.fabricmc.net and flags its own playlists as possibly out of date ([wiki.fabricmc.net](https://wiki.fabricmc.net/_export/raw/tutorial:start)).

## Mods reach the client; data packs stop at the server

The boundary is architectural, not a matter of missing commands. A data pack runs on the logical server, which "holds the authoritative world state" and the data packs, while the logical client handles rendering, input, and resource packs; in singleplayer the client hosts an integrated server and the two still talk only via packets ([Fabric wiki: Side](https://wiki.fabricmc.net/tutorial:side)). Everything the server can observe about a player's hands is therefore the whole list of inputs a data pack can react to: the seven `input` predicate booleans (`forward`, `backward`, `left`, `right`, `jump`, `sneak`, `sprint`, added 1.21.2) ([Minecraft Wiki: Predicate](https://minecraft.wiki/w/Predicate)), statistics such as `minecraft:jump` and `drop` and `minecraft.used:<item>` ([Minecraft Wiki: Statistics](https://minecraft.wiki/w/Statistics)), inventory NBT, and clicks that land on an entity or block (interaction entities, advancement triggers) ([Minecraft Wiki: Interaction](https://minecraft.wiki/w/Interaction)). An arbitrary letter key like N is simply never sent to the server; a 2025 feedback post asking for input detection in commands notes that command blocks "can't read movement directly", and the community answers are client mods such as ControlCommands, not vanilla features ([feedback.minecraft.net](https://feedback.minecraft.net/hc/en-us/community/posts/35962989701517-Add-player-input-detection-to-commands); [Modrinth: ControlCommands](https://modrinth.com/mod/controlcommands)). Command Forge's current "press space for more" paging, which consumes the jump statistic every tick, is exactly the indirection this boundary forces.

A mod is Java inside the game process on one or both sides. Fabric's developer guide enumerates what that unlocks beyond data packs: new item, block, fluid, and entity classes, block entities and renderers, custom screens, HUD elements, particles, key mappings, networking, mixins that rewrite vanilla bytecode, and class tweakers for access widening and enum extension ([Fabric developer guides](https://docs.fabricmc.net/develop/)). Fabric's own words on the one you care about: "Key mappings only exist on the client side" ([Fabric docs: Key Mappings](https://docs.fabricmc.net/develop/key-mappings)). Meanwhile Mojang keeps shrinking the gap from the other direction: 26.3 made fuel and compost item components, brewing recipes JSON, and block transformers a vanilla data type, which let Fabric delete `FuelRegistry`, `CompostingChanceRegistry`, and the brewing builders ([Fabric 26.3](https://fabricmc.net/2026/09/15/263.html)); 26.1 made villager trades data-driven ([Fabric 26.1](https://fabricmc.net/2026/03/14/261.html)). The practical rule for your program: anything that is game logic, content in a data-driven registry, or world state belongs in the data pack and stays portable to every host, including Realms, which "cannot use add-ons or mods" ([Windows Central Realms FAQ](https://windowscentral.com/gaming/minecraft-realms-faq-how-to-setup-price-and-other-questions-answered)); only client-side perception and input justify a mod.

Where the mod must be installed follows from which side its code runs on. Fabric's `fabric.mod.json` `environment` field takes `"*"`, `"client"`, or `"server"` (meaning the dedicated server, "Integrated servers are not included") with entrypoints `main`, `client`, and `server` ([fabric.mod.json spec](https://wiki.fabricmc.net/documentation:fabric_mod_json_spec)); NeoForge uses `@Mod(..., dist = Dist.CLIENT)` and warns "always test with dedicated servers" because `NoClassDefFoundError` is the classic side bug ([NeoForge docs: Sides](https://docs.neoforged.net/docs/concepts/sides)). A keybind-to-command mod, a HUD overlay, or client commands are **client only** and work against an unmodified server. Server commands, gamerule hooks, and a bundled data pack are **server only**. New blocks, items, or entities, and custom packets with a receiver on the other side, need **both**, and on Fabric a server with modded registry entries kicks clients that lack them ([fabricmc/fabric issue #3766](https://github.com/fabricmc/fabric/issues/3766)). For Command Forge, where every kid runs a singleplayer world in Prism, the distinction collapses to one jar in one `mods/` folder; it only resurfaces if the class ever moves to a shared server.

## A client-only mod that sends `trigger` needs no server half

The design that minimises everything is: register a key mapping for N, and when it is pressed, send a command through the player's existing connection. The 26.3 client jar exposes exactly the hook: `net.minecraft.client.multiplayer.ClientPacketListener` has `public void sendCommand(String)` alongside `sendChat(String)`, and `LocalPlayer` holds it as `public final ClientPacketListener connection` (confirmed with `javap` on `~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/libraries/com/mojang/minecraft/26.3/minecraft-26.3-client.jar`). This is the same path chat takes when a player presses Enter on `/trigger …`, so a vanilla or any other server accepts it as the player's own command, run with the player's own permissions. The published precedent is BindCommands, a Fabric mod with **613K downloads and files through 26.3**, whose key-to-command path is entirely client side (a mixin on `KeyMapping.click` that reads bound commands from config and sends via `ClientPacketListener`); its optional server entrypoint only pushes server-defined bindings to clients ([Modrinth: BindCommands](https://modrinth.com/mod/bindcommands); [GitHub: devs-immortal/bind-cmd](https://github.com/devs-immortal/bind-cmd)). Smaller siblings (d1ezz9's Chat Keybinds for 26.1.2, ChatMacro, AnyBind) all describe themselves as fully client-side and all treat a leading `/` as "send as a server command" ([d1ezz9's Chat Keybinds](https://modrinth.com/mod/d1ezz9s-chat-keybinds); [ChatMacro](https://modrinth.com/mod/chatmakro)).

The Fabric docs give every piece of the purpose-built version. In the client initializer, register the key: `KeyMappingHelper.registerKeyMapping(new KeyMapping("key.tutkeys.next", InputConstants.Type.KEYSYM, InputConstants.KEY_N, CATEGORY))`, with the category created via `KeyMapping.Category.register(...)`; then react in `ClientTickEvents.END_CLIENT_TICK.register(client -> { while (key.consumeClick()) { if (client.player == null) return; … } })` ([Fabric docs: Key Mappings](https://docs.fabricmc.net/develop/key-mappings)). The body of the loop is the one line the docs leave to you: `client.player.connection.sendCommand("trigger tut_key_n");` with no leading slash, matching how 26.x text components send `run_command` without one. Declare `"environment": "client"` and a `client` entrypoint in `fabric.mod.json`, depend on `fabric-api` (the wiki's older page names the sub-module `fabric-key-binding-api-v1`) ([Fabric wiki: Keybinds](https://wiki.fabricmc.net/tutorial:keybinds)), and the whole mod is one class. Use the `InputConstants.KEY_*` constants rather than numeric codes: 26.3 replaced GLFW with SDL for window and input, and "some input constants changed, including all mouse buttons" ([Fabric 26.3](https://fabricmc.net/2026/09/15/263.html)). A sketch, assembled from the cited docs rather than compiled, looks like this:

```java
public class TutKeysClient implements ClientModInitializer {
    private static KeyMapping NEXT;
    @Override public void onInitializeClient() {
        KeyMapping.Category cat = KeyMapping.Category.register(Identifier.fromNamespaceAndPath("tutkeys", "keys"));
        NEXT = KeyMappingHelper.registerKeyMapping(
            new KeyMapping("key.tutkeys.next", InputConstants.Type.KEYSYM, InputConstants.KEY_N, cat));
        ClientTickEvents.END_CLIENT_TICK.register(client -> {
            while (NEXT.consumeClick()) {
                if (client.player == null) return;
                client.player.connection.sendCommand("trigger tut_key_n");
            }
        });
    }
}
```

The data pack side is unchanged vanilla and fits Command Forge's existing per-tick structure: `scoreboard objectives add tut_key_n trigger` in `internal/init`, `scoreboard players enable @s tut_key_n` in `player_tick` (a trigger must be re-enabled after each use), and a check such as `execute if score @s tut_key_n matches 1.. run function tut:internal/key_n` followed by `scoreboard players set @s tut_key_n 0`. The function sees the press one tick after the key goes down, which is the same latency the jump-stat hack has now. Because the mod only sends text, the data pack also degrades gracefully: without the jar installed, N does nothing and the space-bar paging still works, so keep the jump path as the fallback. The permission story is the one place to think: `sendCommand` can only do what the kid could type. In a singleplayer world with cheats on, that is level 4 and even `function tut:…` would go through, but a LAN host with cheats grants every player level 4 while a dedicated server leaves them at level 0 ([Minecraft Wiki: Permission level](https://minecraft.wiki/w/Permission_level)); `trigger` is the command built for unprivileged players, which is why the design uses it rather than `function`. Note that 26.3 adds `CHAT_SEND_COMMANDS` as a permission atom (in `net.minecraft.server.permissions.Permissions` in the jar), so a server could in principle strip command sending, though defaults are unaffected.

Two refinements, both optional. First, a key mapping's `consumeClick()` does not fire while a GUI such as the chat box is open, which is the same problem behind Command Forge's "chat box open? press Esc first" prompt; Fabric's docs show how to also catch the key inside screens with `ScreenEvents.BEFORE_INIT` plus `ScreenKeyboardEvents.beforeKeyPress(screen)` and `keyMapping.matches(keyEvent)` ([Fabric docs: Key Mappings](https://docs.fabricmc.net/develop/key-mappings)), so N could advance quest text even with chat open, which is a genuine UX win over space. Second, if you ever want structured data or want to bypass permissions, a custom payload is a Java record implementing `CustomPacketPayload` with a `StreamCodec`, registered with `PayloadTypeRegistry.serverboundPlay()` and received via `ServerPlayNetworking.registerGlobalReceiver`, but it must be registered "on both physical sides" and the docs insist you "validate the content of the packet on the server side" ([Fabric docs: Networking](https://docs.fabricmc.net/develop/networking)). That turns a client-only jar into a both-sides mod; don't do it unless `trigger` stops being enough. The NeoForge equivalent of the whole design is the same shape: `@Mod(dist = Dist.CLIENT)`, a `Lazy<KeyMapping>` registered in `RegisterKeyMappingsEvent`, polled in `ClientTickEvent.Post` with `while (mapping.consumeClick())` ([NeoForge docs: Key Mappings](https://docs.neoforged.net/docs/misc/keymappings)); the one unverified detail is how a NeoForge client-only mod declares itself safe to join servers without it, since the Forge-era `displayTest = "IGNORE_ALL_VERSION"` key does not appear in current NeoForge docs ([Forge community wiki: Mods.toml](https://forge.gemwire.uk/wiki/Mods.toml_file)). One more reason to use Fabric here.

If you want to test the idea before writing any Java, install BindCommands (26.3 build) plus Mod Menu and Fabric API in the Command Forge instance and bind N to `/trigger tut_key_n`. It proves the data pack side in an hour. I would still write the purpose-built mod for class use: three third-party jars, a config GUI the kids can open, and a dependency on someone else's porting cadence (BindCommands' page description lagged its own 26.3 files) are worse than thirty lines you own.

## Install by copying into Prism's Flatpak tree; ship kids an exported instance

A mod is one `.jar` in an instance's `minecraft/mods/` folder, plus Fabric API for Fabric mods; Prism's wiki path is Edit → Version → install the loader, then the Mods tab → Download Mods from Modrinth or CurseForge, and "Fabric mods mostly need the Fabric API for your game version" ([Prism wiki: Downloading Mods](https://prismlauncher.org/wiki/getting-started/download-mods/)). The Mods tab also offers Add File, Enable/Disable, Check for Updates, and Export List ([PrismLauncher source: ExternalResourcesPage.ui](https://github.com/PrismLauncher/PrismLauncher/blob/develop/launcher/ui/pages/instance/ExternalResourcesPage.ui)). On this machine the Flatpak is version 11.1.1 with permissions `xdg-download:ro` and its own `~/.var/app/org.prismlauncher.PrismLauncher` tree, no user overrides, and every instance already has an empty `minecraft/mods/` folder (local `flatpak info --show-permissions`, 2026-10-12; manifest at [PrismLauncher/flatpak](https://github.com/PrismLauncher/flatpak/blob/main/org.prismlauncher.PrismLauncher.yml)). Flatpak apps can write only to the runtime, themselves, `~/.var/app/$FLATPAK_ID`, and `$XDG_RUNTIME_DIR/app/$FLATPAK_ID` unless `--filesystem` says otherwise ([Flatpak docs: Sandbox Permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)). So the reliable host-side install is the same move the repo already makes for pack zips:

```
cp build/libs/tutkeys-*.jar \
  "$HOME/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/instances/Command Forge/minecraft/mods/"
```

No `flatpak override` is needed because the sandbox already owns that tree; the `~/Downloads` + Add File route also works, and "View Folder" will keep failing from inside the sandbox for the reason CLAUDE.md already records. Fabric API itself can come through Prism's in-app Modrinth download, since the sandbox has network. Prism's data lives at `~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher` for the Flatpak, `~/.local/share/PrismLauncher` for a native Linux install, and `%APPDATA%/PrismLauncher` on Windows ([Prism wiki: Data Location](https://prismlauncher.org/wiki/getting-started/data-location/)), which covers the Windows playtest machine too.

For the kids' laptops, export rather than publish. Prism's main window has Export Instance with `.zip`, `.mrpack`, and CurseForge variants ([PrismLauncher MainWindow.ui](https://github.com/PrismLauncher/PrismLauncher/blob/develop/launcher/ui/MainWindow.ui)); mrpack export arrived in 7.0 and CurseForge export in 8.0 ([Prism news: 7.0](https://prismlauncher.org/news/release-7.0/); [8.0](https://prismlauncher.org/news/release-8.0/)). Import accepts a `.zip` or `.mrpack` "from a website (via a URL) or from your filesystem" ([Prism wiki: Import](https://prismlauncher.org/wiki/help-pages/zip-import/)). The `.zip` route is self-contained and includes your private jar and the world; an `.mrpack` is metadata plus `overrides/`, every file needs HTTPS download URLs with hashes, and Modrinth-hosted packs may only reference `cdn.modrinth.com`, `github.com`, `raw.githubusercontent.com`, or `gitlab.com` ([Modrinth: mrpack format](https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack)). Publishing the mod on Modrinth buys discoverability and in-app updates at the cost of a review queue that targets 24–48 hours but is "two to four weeks on average" as of 2026, with mandatory permission proofs for modpack contents since June ([Modrinth: Project Review Times](https://support.modrinth.com/en/articles/8793355); [Modrinth news](https://modrinth.com/news/article/modpack-permissions)). For a classroom, a GitHub release or a USB stick plus Import wins. One open question the notes could not settle: whether a Prism `.zip` export embeds the Minecraft and Fabric libraries for fully offline import or re-downloads them on first launch; plan on network for the first launch of each imported instance.

## Cost: an afternoon once, then a rebuild per drop, and no Java for the kids

The one-time cliff already happened. Fabric's 26.1 post lists it: unobfuscated game, Yarn gone, every mod recompiled, Java 25, Loom 1.15+, IntelliJ 2025.3+ for mixins, Fabric API renamed to Mojang names with no backward compatibility, `HudRenderCallback` removed ([Fabric 26.1](https://fabricmc.net/2026/03/14/261.html)). Since then 26.2 and 26.3 have been ordinary ports, but not free ones: mod changelogs for 26.2 report `Minecraft.screen` and `setScreen` relocating to `gui.screen()` and `setScreenAndShow`, `Gui` renamed `Hud`, and 26.2 builds that "aren't compatible with 26.1.x or 1.21.x" ([Balm 26.2 migration](https://balm.twelveiterations.com/migration/26.2); [Shulker Stuff changelog](https://www.curseforge.com/minecraft/mc-mods/shulker-stuff/files/8524622)). The structural difference from your data packs is version pinning: BindCommands' `fabric.mod.json` depends on `"minecraft": ">=26.3-"` and ships one file per game version from 1.16.5 through 26.3 ([bind-cmd fabric.mod.json](https://github.com/devs-immortal/bind-cmd/blob/HEAD/src/main/resources/fabric.mod.json)), whereas one pack zip loads in 26.2 and 26.3 via `min_format`/`max_format`. Expect each drop to cost a bump of `minecraft_version`, `loader_version`, and `fabric_api_version` in `gradle.properties`, a rebuild, a fix if one of the four or five symbols you touch moved, and a re-copy into each instance (the porting guide is short for a reason) ([Fabric docs: Porting](https://docs.fabricmc.net/develop/porting/)). Ten to thirty minutes when nothing moved, an hour or two when something did; these are my estimates, since no source publishes hours-to-port figures. Four drops a year means four such sessions, which argues for keeping the Java surface tiny and the behaviour in mcfunctions.

The Java itself is the small part for someone fluent in Python and C. The minimal mod uses classes, a lambda, a static field, and one interface; mixins, which "apply to bytecode rather than source code" and want some JVM knowledge ([Fabric wiki: Mixin Introduction](https://wiki.fabricmc.net/tutorial:mixin_introduction)), are avoidable entirely. The real first-day cost is Gradle and the first dependency sync; NeoForge's docs still warn the first import "can take up to an hour" ([NeoForge docs: Getting Started](https://docs.neoforged.net/docs/gettingstarted/)), and both loaders name "familiarity with Java" as the prerequisite. Kotlin is first-class on both (Fabric Language Kotlin 1.14.2 and Kotlin for Forge 6.4.0 both cover 26.3) ([Fabric Language Kotlin](https://modrinth.com/mod/fabric-language-kotlin); [Kotlin for Forge](https://modrinth.com/mod/kotlin-for-forge)), but adding a language runtime to a thirty-line mod is more surface, not less. If you want to script instead of compile, KubeJS (JavaScript, Fabric/Forge/NeoForge, 26.1 branch active in October 2026) and Katton (hot-reloading Kotlin scripts on Fabric/NeoForge, 26.1.x) exist ([KubeJS branches](https://github.com/KubeJS-Mods/KubeJS/branches/all); [Katton](https://modrinth.com/mod/katton)), but both sit a drop or two behind 26.3 and add a heavyweight dependency to solve a problem that is thirty lines of Java.

On the kids: do not put them in front of Gradle. Vendors consistently place real IDE-based Java at 10+ with 13–17 as the main band (iD Tech's "Java Coding: Build Mods with Minecraft" starts at ages 10–12 and the advanced course at 13–17) ([iD Tech course](https://wwwapi.idtech.com/courses/java-coding-build-mods-with-minecraft)), and the only comparative classroom study found, tiny and secondary-school, favoured blocks over text for interest and perceived difficulty ([EdUHK thesis](https://repository.eduhk.hk/en/publications/comparing-programming-interest-perceived-programming-difficulty-a/)). The one 2022 study of a six-week Minecraft coding programme with fifth-graders found variables, operators, and conditionals the least successfully used concepts ([Kutay & Öner, Boğaziçi archive](https://digitalarchive.library.bogazici.edu.tr/items/77989368-95d9-4851-8220-40f2886311d4/full)), which are exactly what `scoreboard players` and `execute if` make concrete. Commands remain the right medium for the program; a mod is instructor infrastructure. Hybrid patterns beyond the key bridge exist but do not pay here: NeoForge auto-applies every mod's `data/` folder as a data pack and generates its `pack.mcmeta` at runtime ([NeoForge docs: Resources](https://docs.neoforged.net/docs/resources/)), so one jar could carry tutorial plus keys, but that would move Command Forge's install from `saves/<world>/datapacks/` to `mods/`, require Fabric on every machine, and lose the world-level `/reload` loop you iterate with in class.

## Conclusion

The question "should Command Forge become a mod?" has a clean answer now that deobfuscation has made the Java toolchain boring: no, but it should gain a thirty-line client-side companion. The architecture that falls out is a strict split by side. Everything a kid can see or do that the server also sees stays in mcfunctions, portable across 26.2, 26.3, LAN, Realms, and vanilla servers; the one thing the server cannot see, an arbitrary key, is turned into a command the server already understands. `trigger` is the contract between the two halves, and because it is text the pack works, slightly less conveniently, when the jar is absent. That property is what lets you adopt the mod without making the tutorial depend on it.

The second-order implication is about cadence. Mojang now ships four drops a year, each pins mods to one version, and each quietly deletes loader APIs as vanilla absorbs their features, so every line of Java you write is a small recurring tax while every line of mcfunction is nearly free. Spend the Java budget only on perception and input, and spend it in Fabric, which is where the drop-chasing ecosystem and the copyable precedents live. If Mojang's promised "creator platform" ever adds a first-party way to read a key, the bridge becomes a one-line swap; if it never does, the bridge is the cheapest thing in the repo to maintain.
