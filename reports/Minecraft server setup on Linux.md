# Run six Fabric servers under systemd, not Docker

**Install Arch's `jre25-openjdk-headless`, give each game its own directory under `/srv/mc/<name>` with the one-file Fabric 26.3 launcher jar, and run them all from a single hardened `minecraft@.service` template: that's the best fit for a one-admin studio box, and it needs neither Docker nor a panel.** The reasons are specific to this machine. Arch ships Java 25 as a versioned package that stays at 25 across `pacman -Syu`, Mojang's manifest names Java 25 for 26.3 ([piston-meta](https://piston-meta.mojang.com/mc/game/version_manifest_v2.json)), and the vanilla server has paused itself when empty since 1.21.2, which removes the main thing wrappers used to do ([Server.properties](https://minecraft.wiki/w/Server.properties)). systemd then gives you per-server memory caps, P-core pinning on the hybrid i5-13400, filesystem sandboxing so an op kid on one world can't touch another, crash restart, and failure notifications for free, while the host's nftables `input` chain stays the only network path. Docker with the itzg image is the credible alternative (declarative mods, datapacks, and a backup sidecar), but it adds a daemon the box doesn't have and a firewall layer that bypasses host rules ([Docker docs](https://docs.docker.com/engine/network/packet-filtering-firewalls/)); the panels (Pelican rc.1, Pterodactyl, Crafty, AMP, MCSManager) solve multi-tenant problems you don't have. Size each server at a 3 GB G1 heap with Aikar's flags (six of them use ~24 GB of 62), pin main threads to P-cores because Linux 7.2 still misplaces single-threaded work on Alder/Raptor Lake, and ship a class `server.properties` with `online-mode=true`, `white-list=true`, `enforce-whitelist=true`, `op-permission-level=2`, `spawn-protection=0`, and `hide-online-players=true`. In the studio, kids type the box's reserved private IP and a port; from home they use a DDNS name (port-forward 25565–25570) or a playit.gg tunnel if the ISP is CGNAT, and every child account needs the Xbox "join multiplayer games" toggle flipped by a parent even for LAN play. Admin access goes over Tailscale only, with public SSH closed, and a LUKS root means either TPM2 auto-unlock or an SSH server in the initramfs before any unattended remote reboot is possible. Backups are `save-off` → `save-all flush` → restic → `save-on` on a timer, pulled to the laptop; upgrades to 26.4 are a new launcher URL plus a `max_format` bump to 122 tested on a scratch port first, because world upgrades are one-way.

## systemd beats Docker and panels for one admin on Arch

The process-management choice sets everything downstream (firewall, Java, backups, upgrades), so it's worth being clear about why the plain route wins here. Every option inherits the same baseline: Mojang's 26.3 version JSON declares `javaVersion.majorVersion: 25`, the Arch wiki's requirement table now reads "≥ 26.1 → 25" ([Arch wiki: Minecraft](https://wiki.archlinux.org/title/Minecraft)), and a 26.x jar on Java 21 dies immediately with an unsupported-class-file-version error ([space-node, third-party](https://space-node.net/blog/minecraft-26-3-server-update-guide-2026)). Fabric for 26.3 is Loader **0.19.5** (stable; 0.20.0 exists but is flagged unstable), Installer **1.1.2**, Fabric API **0.163.0+26.3**, and the whole server launcher is one predictable download, `https://meta.fabricmc.net/v2/versions/loader/26.3/0.19.5/1.1.2/server/jar`, verified returning a jar on 2026-10-19 ([Fabric meta: loader](https://meta.fabricmc.net/v2/versions/loader), [Modrinth API: fabric-api](https://api.modrinth.com/v2/project/fabric-api/version?game_versions=%5B%2226.3%22%5D&loaders=%5B%22fabric%22%5D)). That URL shape is why upgrades are cheap under every option: a 26.4 move is a new URL and a restart.

On Arch, `extra/jre25-openjdk-headless 25.0.4.1.u1-1` and `jdk25-openjdk` are in the official repos, installed under `/usr/lib/jvm/java-25-openjdk/`, side by side with the unversioned `jdk-openjdk` that already tracks 27 ([Arch wiki: Minecraft](https://wiki.archlinux.org/title/Minecraft)). Pinning is therefore implicit: start the server with the explicit path `/usr/lib/jvm/java-25-openjdk/bin/java` and `archlinux-java` defaults never matter. The AUR `fabric-server 26.3_0.19.5_1.1.2-1` package exists and installs the Edenhofer tmux-based `fabricd` script with a daily backup timer, but it hardcodes one root (`/srv/fabric`), one user, and one unit, and its Java floor (`>=21`) is below what 26.3 needs ([Arch wiki: Java Edition server](https://wiki.archlinux.org/title/Minecraft/Java_Edition_server), [Edenhofer README](https://github.com/Edenhofer/minecraft-server)); for 3–6 servers you'd be building six copies, so a hand-written template unit is less work. `mcrcon 0.7.2` is in the AUR for console commands ([AUR RPC](https://aur.archlinux.org/rpc/v5/info?arg[]=mcrcon)).

The itzg image is excellent and actively maintained (release 2026.10.0 on 2026-10-10; `latest`/`java25` = Java 25 on Ubuntu) and does the Fabric install, Modrinth mod resolution, datapack placement, RCON console, graceful stop, health checks, and a backup sidecar from YAML ([itzg releases](https://github.com/itzg/docker-minecraft-server/releases), [itzg docs: Fabric](https://docker-minecraft-server.readthedocs.io/en/latest/types-and-platforms/server-types/fabric/)). Three things count against it on this box. First, Docker publishes ports through the `nat`/`FORWARD` path before the host's `INPUT` chain, so the nftables ruleset you write for SSH and game ports doesn't protect containers; Docker's own docs say published ports "can bypass ufw rules" and "it is not possible to fully prevent Docker from creating firewall rules" ([Docker docs: packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls/)). The 29.x nftables backend is experimental and drops `DOCKER-USER` ([Docker docs: nftables](https://docs.docker.com/engine/network/firewall-nftables/)). Second, its container autopause is now discouraged by its own docs for 1.21.2+ because vanilla pauses natively, and a September 2026 bug let the tick watchdog kill resumed servers ([itzg docs: autopause](https://docker-minecraft-server.readthedocs.io/en/latest/misc/autopause-autostop/autopause/), [issue search](https://github.com/itzg/docker-minecraft-server/issues?q=26.3)). Third, the box has no Docker today; adding a root daemon for six JVMs you could run directly is surface area, not value. If you do go that way, the compose sketch below is the shape.

The panels are built for renting servers to strangers. Pelican reached **v1.0.0-rc.1 on 2026-10-10** (panel and Wings), runs on PHP 8.4/8.5 with SQLite by default and ships a `java_25` yolk that the Fabric egg lists, but its OS list is Ubuntu/Debian/RHEL only, with "other OSes might still work" ([Pelican releases](https://github.com/pelican-dev/panel/releases), [Pelican: getting started](https://pelican.dev/docs/panel/getting-started), [pelican-eggs/yolks](https://github.com/pelican-eggs/yolks)). Pterodactyl is at panel 1.15.1 with a 2.0.0 beta opened 2026-10-14 and still needs MySQL and Redis ([Pterodactyl releases](https://github.com/pterodactyl/panel/releases)); a 2026 comparison puts its idle footprint at **1.5–2 GB** and recommends it for commercial, multi-tenant use with five or more users ([MineGuard, vendor blog](https://mineguard.pro/en/blog/pterodactyl-vs-crafty-vs-mcsmanager-2026)). Crafty 4.11.0 (2026-09-16) is the Minecraft-only Python panel whose Docker image now bundles OpenJDK 25 and whose docs pick it for "a small private or family server on one machine", but all servers share one UID and the native installer is apt/dnf only ([Crafty releases](https://gitlab.com/api/v4/projects/crafty-controller%2Fcrafty-4/releases), [Crafty Dockerfile](https://gitlab.com/crafty-controller/crafty-4/-/raw/master/Dockerfile), [Crafty: Linux install](https://docs.craftycontrol.com/pages/getting-started/installation/linux/)). AMP is paid, closed-source, and its installer exits with code 10 ("neither apt nor yum are present") on Arch ([CubeCoders: exit codes](https://discourse.cubecoders.com/t/amp-exit-code-details/2248)). MCSManager v10.21.2 is the only panel whose installer lists Arch, but non-Docker instances share the daemon's UID ([MCSManager README](https://github.com/MCSManager/MCSManager/blob/master/README.md)). PufferPanel's own docs call its non-Docker mode insecure ([PufferPanel docs](https://docs.pufferpanel.com/en/latest/installing.html)), and MineOS hasn't released since 2023 ([mineos-node releases](https://github.com/hexparrot/mineos-node/releases)).

Here is the unit the recommendation rests on. It's synthesised from the systemd man page, a current Debian 13 Paper unit, and the community templates, not copied from any one source, and the sandbox list is the Java-safe one (no `MemoryDenyWriteExecute`, which systemd documents as incompatible with JIT engines) ([systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html), [1337hosting Debian 13 unit, vendor](https://1337hosting.com/tutorials/minecraft-server-debian-13-paper), [brianwarner minecraft@.service](https://github.com/brianwarner/minecraft-server-hosting/blob/main/minecraft@.service)). `SuccessExitStatus=0 143` keeps a normal stop from showing as failed ([Vultr, vendor](https://docs.vultr.com/how-to-deploy-a-paper-minecraft-server-on-ubuntu-2004)); `KillMode=none`, which older guides use, is deprecated upstream, so the unit relies on `ExecStop` plus `TimeoutStopSec` instead.

```ini
# /etc/systemd/system/minecraft@.service
[Unit]
Description=Minecraft Fabric server %i
After=network-online.target
Wants=network-online.target
PartOf=minecraft.target
OnFailure=notify@%n.service

[Service]
Type=simple
User=minecraft
Group=minecraft
WorkingDirectory=/srv/mc/%i
EnvironmentFile=/srv/mc/%i/.env
ExecStart=/usr/lib/jvm/java-25-openjdk/bin/java @/srv/mc/_shared/jvm.flags -Xms${HEAP} -Xmx${HEAP} -jar fabric-server-launcher.jar nogui
ExecStop=/usr/bin/mcrcon -H 127.0.0.1 -P ${RCON_PORT} -p ${RCON_PASSWORD} "say Server stopping" "save-all flush" "stop"
TimeoutStopSec=120
SuccessExitStatus=0 143
Restart=on-failure
RestartSec=10
StandardOutput=journal
StandardError=journal

# resources (verify CPU numbering with lscpu -e before pinning; see section 2)
MemoryMax=5G
CPUAffinity=0-11
Nice=-5

# sandbox: Java-safe (no MemoryDenyWriteExecute)
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/srv/mc/%i
ProtectHome=true
PrivateTmp=true
PrivateDevices=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
ProtectClock=true
ProtectHostname=true
LockPersonality=true
RestrictRealtime=true
RestrictSUIDSGID=true
RestrictNamespaces=true
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM

[Install]
WantedBy=minecraft.target
```

```ini
# /etc/systemd/system/minecraft.target
[Unit]
Description=All Minecraft servers
[Install]
WantedBy=multi-user.target
```

`/srv/mc/<name>/.env` is root-owned, mode 0600 (systemd reads it as PID 1, the game user never needs it), holding `HEAP=3G`, `RCON_PORT=25575+N`, and a random `RCON_PASSWORD` that also goes into that server's `server.properties`. `PartOf=minecraft.target` makes `systemctl restart minecraft.target` act on every enabled instance, which plain `systemctl start 'minecraft@*'` can't do. `ProtectSystem=strict` with one `ReadWritePaths` entry is what gives per-world isolation without six Unix users: an op kid who abuses `/function` or a datapack on server A has a process that can write only `/srv/mc/A`. If you want the stricter version, switch to `User=mc-%i` and create one user per server. Run `systemd-analyze security minecraft@one-block.service` after the first start and expect a middling score; `@system-service` is untested against Java 25 in any source, so if the JVM misbehaves, check `journalctl -u` for `SYSCALL` lines and relax the filter rather than removing the sandbox ([Arch wiki: systemd/Sandboxing](https://wiki.archlinux.org/title/Systemd/Sandboxing)).

If you'd rather have Docker, the equivalent per server is one compose service plus a backup sidecar: `image: itzg/minecraft-server:2026.10.0-java25`, `TYPE: FABRIC`, `VERSION: "26.3"`, `FABRIC_LOADER_VERSION: 0.19.5`, `MODRINTH_PROJECTS: fabric-api,spark`, `DATAPACKS: /packs/one-block_2.zip` with `./zips:/packs:ro`, `MEMORY: 3G`, `USE_AIKAR_FLAGS: "true"`, `ENABLE_WHITELIST: "true"`, `RCON_PASSWORD_FILE`, `ports: ["127.0.0.1:25565:25565"]` or `"25565:25565"`, `volumes: ["./one-block:/data"]`, `stop_grace_period: 2m`, `restart: unless-stopped`, and `deploy.resources.limits.memory: 4g`; the sidecar is `itzg/mc-backup` with `BACKUP_INTERVAL: 1h`, `PAUSE_IF_NO_PLAYERS: "true"`, `RCON_HOST: one-block`, `BACKUP_METHOD: restic`, and `depends_on: one-block: condition: service_healthy` ([itzg docs: variables](https://docker-minecraft-server.readthedocs.io/en/latest/variables/), [itzg/docker-mc-backup](https://github.com/itzg/docker-mc-backup)). Pin the image tag: the `java25` rebuild of 2026-10-16 SIGILL-crashed on CPUs without AVX (not an i5-13400 issue, but it shows why `latest` is a bad idea for a class server) ([itzg issues](https://github.com/itzg/docker-minecraft-server/issues?q=26.3)).

## Three-gigabyte G1 heaps pinned to P-cores

Java 25 is the only configuration Mojang tests; the launcher bundles `java-runtime-epsilon` for 26.1–26.3 ([26.3 version JSON](https://piston-meta.mojang.com/v1/packages/11f1aefe473eefba0af62e3286c33b692807b2eb/26.3.json)). A local test on 2026-10-18 showed the 26.3 server jar does start on JDK 27 (`--initSettings` exited 0), but it printed `sun.misc.Unsafe` deprecation warnings against JOML and "Restricted methods will be blocked in a future release", and nothing documents Fabric Loader or Mixin on 27, so run 25 and don't rely on the system default. Two JDK-level changes since the Java 21 era matter for copied flag strings: non-generational ZGC was removed in JDK 24, so `-XX:+ZGenerational` is now an obsolete-option warning that will later become a hard start failure ([JEP 490](https://openjdk.org/jeps/490)), and compact object headers became a product flag in JDK 25, `-XX:+UseCompactObjectHeaders` with no experimental unlock, with cited heap savings around 22 % on SPECjbb2015 and 15 % fewer GCs in other settings ([JEP 519](https://openjdk.org/jeps/519)).

For 2–4 GB heaps, every sourced position still says G1. Paper's canonical Aikar string is built on G1 with a large young generation because "Minecraft allocates mostly short-lived objects", matched `-Xms`/`-Xmx` so G1 uses the heap it's given, and `AlwaysPreTouch` to commit memory at start ([PaperMC: Aikar's flags](https://docs.papermc.io/paper/aikars-flags)). ZGC's own advocates only recommend it from 16 GB, or from 32 GB and more than 10 cores in MeowIce's README, which also warns against ZGC below 8–10 cores ([MeowIce flags](https://github.com/MeowIce/meowice-flags), [MineGuard ZGC vs G1, vendor](https://mineguard.pro/en/blog/zgc-vs-g1gc-minecraft-java-21-benchmark)); with six JVMs sharing ten cores, ZGC's concurrent threads would fight other instances' main threads. GraalVM's one controlled test moved a modpack from ~17.4 to ~20 TPS ([tallua benchmark](https://github.com/tallua/minecraft-graalvm-benchmark/blob/main/README.md)), not worth the extra runtime for a classroom. Put this in `/srv/mc/_shared/jvm.flags` (a Java argfile, the same mechanism the Debian 13 unit uses); the heap is supplied by the unit so one file serves every server:

```
-XX:+UseG1GC -XX:+ParallelRefProcEnabled -XX:MaxGCPauseMillis=200
-XX:+UnlockExperimentalVMOptions -XX:+DisableExplicitGC -XX:+AlwaysPreTouch
-XX:G1NewSizePercent=30 -XX:G1MaxNewSizePercent=40 -XX:G1HeapRegionSize=8M
-XX:G1ReservePercent=20 -XX:G1HeapWastePercent=5 -XX:G1MixedGCCountTarget=4
-XX:InitiatingHeapOccupancyPercent=15 -XX:G1MixedGCLiveThresholdPercent=90
-XX:G1RSetUpdatingPauseTimePercent=5 -XX:SurvivorRatio=32 -XX:+PerfDisableSharedMem
-XX:MaxTenuringThreshold=1 -XX:+UseCompactObjectHeaders
-Xlog:gc*:logs/gc.log:time,uptime:filecount=5,filesize=1M
```

The GC log line is Paper's and "can be left on at all times" ([PaperMC: Aikar's flags](https://docs.papermc.io/paper/aikars-flags)); `UseCompactObjectHeaders` is the one addition, a layout flag independent of GC tuning, unmeasured on Minecraft specifically, so compare `/spark gc` with and without it on one server before trusting it on all six.

Memory is not the constraint. The wiki's sizing is 2 GB "recommended" for 5–10 players and 4 GB "best" for 10+ at view distance ≤ 10, roughly 50–100 MB per player ([Server/Requirements](https://minecraft.wiki/w/Server/Requirements)); hosting guides treat 2 GB as the Fabric floor and 4 GB as comfortable ([Shockbyte RAM guide](https://shockbyte.com/help/knowledgebase/articles/how-much-ram-do-i-need-for-a-minecraft-server)). For void and superflat mini-game worlds with 3–6 kids each, a **3 GB heap** covers entity-heavy packs and `/reload` registry rebuilds; expect RSS around heap plus 0.5–1 GB, hence `MemoryMax=5G` as the cgroup ceiling with headroom (itzg's docs suggest ~25 % non-heap headroom ([itzg docs: JVM options](https://docker-minecraft-server.readthedocs.io/en/latest/configuration/jvm-options/))). Six instances pre-touching 3 GB each commit 18 GB and peak near 24–30 GB, leaving half the box for page cache. Oversizing heaps on G1 only makes the eventual old-gen pauses longer, so don't go to 6 GB "because it's there".

CPU is the real ceiling. The i5-13400 has **6 P-cores (4.6 GHz turbo, hyperthreaded) and 4 E-cores (3.3 GHz)**, 16 threads total ([mini-itx.com](https://www.mini-itx.com/~i5-13400)); a server "typically uses up to three cores" and single-core speed matters most ([Server/Requirements](https://minecraft.wiki/w/Server/Requirements)). Six instances is the natural ceiling where each main thread can own a P-core. Pinning is justified today: kernel bug 218195 documented the scheduler putting single-threaded work on E-cores from Linux 6.6 ([kernel.org bug 218195](https://bugzilla.kernel.org/show_bug.cgi?id=218195)), Intel's cluster-scheduling fix targets the **Linux 7.3** merge window ([Phoronix](https://phoronix.com/news/Linux-7.3-Better-Intel-Hybrid)), and a generic measurement puts wrong-class placement at roughly a quarter of single-thread performance ([LinuxLinks](https://www.linuxlinks.com/minisforum-m2-does-linux-schedule-panther-lake-correctly/9/)). The machine I'm writing this on is a different CPU, so the `CPUAffinity=0-11` in the unit is a placeholder: on the studio box run `lscpu -e` or `cat /sys/devices/system/cpu/cpu*/topology/core_cpus_list` and confirm which logical CPUs are the hyperthreaded P-core pairs (on most 13400 boards 0–11) and which are E-cores (12–15). The simple layout keeps every instance on the P-core set and lets the scheduler balance within it; the finer one gives each instance its own pair (`CPUAffinity=0 1`, `2 3`, …) via a drop-in per instance. Revisit when Arch ships 7.3. The CPU governor advice (performance or `energy_performance_preference=performance` for the bursty 50 ms tick pattern) is general knowledge, not sourced in this research; treat it as a thing to try with `/spark tps` open.

The class `server.properties` follows. The defaults were captured on this machine by running the official 26.3 jar with `--initSettings` on 2026-10-18; the notable 26.3 change is **`white-list=true` by default** (new servers only; upgraded ones keep their value), and `enable-command-block` no longer exists, replaced by a game rule ([Server.properties](https://minecraft.wiki/w/Server.properties), [Nodecraft 26.3 notes](https://nodecraft.com/blog/game-news-tips/minecraft-java-26-3-wilderness-bound-is-out-what-it-means-for-your-server)).

```properties
# class template, 26.3 (N = 0..5 per server)
server-port=2556N
motd=One Block
level-name=world
online-mode=true
enforce-secure-profile=true
white-list=true
enforce-whitelist=true
max-players=8
op-permission-level=2
function-permission-level=2
spawn-protection=0
gamemode=adventure
view-distance=8
simulation-distance=6
player-idle-timeout=0
pause-when-empty-seconds=60
max-tick-time=60000
sync-chunk-writes=true
network-compression-threshold=256
hide-online-players=true
log-ips=true
enable-status=true
enable-query=false
enable-rcon=true
rcon.port=2557N
rcon.password=<random, same as .env>
broadcast-rcon-to-ops=false
management-server-enabled=false
accepts-transfers=false
```

The reasoning per line: `spawn-protection=0` because the default 16 stops non-op kids placing or breaking blocks near spawn, exactly where `one-block`'s course starts; `simulation-distance` is the CPU lever (mob AI, block and random ticks) while `view-distance` costs RAM and bandwidth, and 8 vs 10 cuts first-load chunk traffic by about a third (289 vs 441 chunks per player) ([Space-Node view/simulation guide](https://space-node.net/blog/minecraft-view-distance-simulation-distance-guide-2026), [xgamingserver](https://xgamingserver.com/docs/minecraft/render-distance)); `enforce-whitelist=true` because a teacher who removes a name mid-session wants that player kicked, not left online ([Server.properties](https://minecraft.wiki/w/Server.properties)); `pause-when-empty-seconds=60` left at default so idle instances cost nothing between classes, set to 0 only on a server whose pack must keep ticking with nobody on; `max-tick-time` kept so a runaway datapack loop kills one instance (exit code 1, systemd restarts it) instead of hanging it ([Server.properties](https://minecraft.wiki/w/Server.properties)); `hide-online-players=true` keeps kids' names out of status pings. Command blocks are the `command_blocks_work` game rule (default true; added 25w35a) ([Game rule](https://minecraft.wiki/w/Game_rule)), so turn it off on servers whose packs don't need them and leave it on for Command Forge section 2. Bandwidth is a non-issue on the LAN; for home play the wiki's dedicated table implies roughly 0.7–1 Mbit/s upstream per player at draw distance ≤ 10 (8 Mbit/s for 10–15 players, 14 for 15–20), and void worlds send far less ([Server/Requirements/Dedicated](https://minecraft.wiki/w/Server/Requirements/Dedicated)).

## Kids type an IP in the studio and a name at home

A dedicated server never appears in the Multiplayer screen's LAN list. That list is fed only by the `224.0.2.60:4445` multicast a singleplayer "Open to LAN" world sends every 1.5 s ([LAN world](https://minecraft.wiki/w/LAN_world)); the existence of server-side mods such as LAN Announcer, whose whole job is to imitate that broadcast, is the evidence ([Modrinth: LAN Announcer](https://modrinth.com/mod/lan-announcer)). So the studio workflow is Multiplayer → Add Server with `192.168.x.y:2556N`, one bookmark per game on each laptop, and the box needs a fixed private address: the wiki says to set a static internal IP because DHCP can change it ([Java server tutorial](https://minecraft.wiki/w/Tutorial:Setting_up_a_Java_Edition_server)), and a DHCP reservation on the router is the lower-maintenance way to get one. mDNS `.local` names work on Linux and macOS but Windows tries LLMNR first and reports of flakiness persist ([slightfuture technote](https://slightfuture.com/technote/windows-mdns-dnssd/)), so print the IPv4 address on the card. The studio Wi-Fi pitfalls, in the order they bite: kids on a guest SSID (guest networks isolate clients from the main LAN by design, and disabling isolation on the guest SSID may not be enough ([Netgear community](https://community.netgear.com/discussions/business-wireless-for-business/wax220-guest-networkisolation-not-working-properly/2318061/replies/2318086))), client isolation on the main SSID, and the box on a different VLAN from the access point. "Connection timed out" means a firewall is dropping the attempt; "connection refused" means nothing is listening ([Java server tutorial](https://minecraft.wiki/w/Tutorial:Setting_up_a_Java_Edition_server)). And don't have kids inside the studio use the public name: without NAT loopback the router sends those packets toward the ISP and drops them, and consumer support varies by model ([OneUptime: hairpin NAT](https://oneuptime.com/blog/post/2026-03-20-nat-hairpinning-loopback/view)). Two cards, one with the private IP for class and one with the public name for home, is the robust version.

For home access, the first check is whether the studio's WAN address is a real public IP. A router WAN address in `100.64.0.0/10`, in a private range, or different from what whatismyip reports means CGNAT or double NAT, and inbound forwarding simply won't work ([OneUptime: detect CGNAT](https://oneuptime.com/blog/post/2026-03-20-detect-cgnat/view)); T-Mobile Home Internet is the common US case ([LocalXpose, vendor](https://localxpose.io/blog/t-mobile-home-internet-port-forwarding)). If the IP is public, classic forwarding is one TCP rule per server (25565–25570) to the reserved address; the server needs only TCP, since Query (UDP) and RCON are off or loopback-only ([Server.properties](https://minecraft.wiki/w/Server.properties)). For the name, DuckDNS is free with no renewal chore (five subdomains per account, per the Home Assistant add-on README ([hassio-addons README](https://github.com/home-assistant/hassio-addons/blob/684e197b0ec4f25b206346041ab66ffe1e3bfa92/duckdns/README.md))), whereas No-IP free hostnames must be confirmed every 30 days and an update client doesn't count as confirmation ([No-IP KB](https://www.noip.com/support/knowledgebase/why-is-my-hostname-missing-or-deleted-what-do-i-do)). If you want bare names per game instead of `name:25566`, you need a real domain with SRV records: `_minecraft._tcp.oneblock.example.com → 0 5 25566 mc.example.com`, where `mc.example.com` is an A record or CNAME to the DDNS name; the service label can't change, an A record must exist first, and SRV is Java-only ([Java server tutorial](https://minecraft.wiki/w/Tutorial:Setting_up_a_Java_Edition_server), [mcstatus FAQ](https://mcstatus.readthedocs.io/en/stable/pages/faq/)). Cloudflare-hosted DNS plus a cron DDNS script is the usual pairing ([cleberg.net walkthrough](https://cleberg.net/blog/cloudflare-dns-api/)).

The alternatives trade exposure and cost for convenience. playit.gg needs nothing on the kids' machines: the box runs an agent, players connect to a `*.ply.gg` address, Minecraft Java tunnels sit in the free tier (six TCP ports on the pricing table), but free tunnels are global anycast that "don't always route optimally" and the 2026 posts about free-region port exhaustion make the **$3/month or $30/year Premium** (regional US tunnels, custom domains) the realistic budget for weekly class use ([playit.gg](https://playit.gg/), [playit pricing](https://playit.gg/pricing), [playit Premium](https://playit.gg/support/playit-premium/)). Its structural benefit is that the studio IP is never published to families, so a grudge-booter hits playit, not the studio connection. Tailscale is the right tool for the admin and the wrong one for kids: sharing a machine means every family creates a Tailscale account, installs the client, and accepts an invite ([Tailscale: share a game server](https://tailscale.com/docs/use-cases/personal-or-at-home-use/share-private-game-server)), and Funnel can't carry Minecraft because it only listens on 443/8443/10000 over TLS ([Tailscale KB: Funnel](https://tailscale.com/kb/1223/funnel)). ngrok TCP wants a card on file and caps at 1 GB/month free ([ngrok pricing](https://ngrok.com/pricing)); Cloudflare Tunnel needs `cloudflared` on every kid's machine ([Cloudflare docs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/non-http/cloudflared-authentication/arbitrary-tcp/)). A VPS relay (WireGuard from the box to a small VPS that DNATs its public ports through the tunnel) gives one IP you control, hides the studio, and works under CGNAT ([1337hosting WireGuard relay](https://1337hosting.com/tutorials/port-forwarding-behind-cgnat-starlink-wireguard), [Hetzner tutorial](https://community.hetzner.com/tutorials/bypass-cgnat-with-a-wireguard-vps-relay/)); it's the later upgrade if DDoS ever becomes real, and the VPS price band is in the hosting report.

| Route | Kid-side install | Needs public IP | Hides studio IP | Several servers | Cost | Pick when |
|---|---|---|---|---|---|---|
| Port forward + DuckDNS, `name:port` | None | Yes | No | One rule per port | $0 | Default if the WAN IP is public |
| + own domain + SRV records | None | Yes | No | One SRV per game, bare names | ~$10/yr domain | Kids struggle with `:25566` |
| playit.gg | None | No | Yes | 6 free tunnels; Premium for regional | $0 / $30 yr | CGNAT, or you don't want the studio IP out there |
| Tailscale shared machine | Client + account per family | No | Yes | Yes | $0 (6 users) | Admin access only; not for 20 families |
| VPS WireGuard relay (+ optional Velocity) | None | No | Yes | Yes | VPS monthly | Later, if DDoS or Velocity hostnames matter |

Several servers on one address has three patterns, and the hosting report already concluded direct-join ports per game, no proxy ([Minecraft server hosting options](Minecraft%20server%20hosting%20options.md)); nothing here changes that. For the record: Velocity 4.3.0 needs Java 25, supports clients through 26.3, and maps hostnames to backends via `[forced-hosts]`, but every backend must then run `online-mode=false` with modern forwarding (FabricProxy-Lite, which lists 26.3) and be unreachable except from the proxy ([Velocity compatibility](https://docs.papermc.io/velocity/server-compatibility/), [Velocity configuration](https://docs.papermc.io/velocity/configuration/), [Modrinth: FabricProxy-Lite](https://modrinth.com/mod/fabricproxy-lite)). The vanilla middle ground is `/transfer <host> [port]` (1.20.5+, permission 3) with `accepts-transfers=true` on the destination: a datapack button can move a kid between games with no proxy, the client reconnects to the new address ([Commands/transfer](https://minecraft.wiki/w/Commands/transfer), [24w03a](https://minecraft.wiki/w/Java_Edition_24w03a)); the address baked into the function must be reachable from where the kid sits, the same hairpin caveat as above, so this is a studio-only hub trick unless you run split DNS.

The child-account block is independent of all of this and is the item most likely to eat the first class. Microsoft treats under-16 accounts in the US and EU as child accounts whose multiplayer is parent-gated ([help.minecraft.net: parental controls](https://help.minecraft.net/en-us/article/parental-controls)); a blocked account sees the Java Multiplayer button greyed out with "Multiplayer is disabled. Please check your Microsoft account settings", the parent flips "You can join multiplayer games" (plus "play with people outside Xbox Live" and "join cross-network play" per the fullest third-party checklist) from the parent account, and the child must sign out and back in, with reports of a day's propagation delay ([Microsoft Q&A 4220013](https://learn.microsoft.com/en-us/answers/questions/4220013/minecraft-java-edition-multiplayer-option-disabled), [Mud Club checklist](https://mudclub.helpjuice.com/en_US/online-safety-and-privacy/minecraft-access-checklist)). Because LAN worlds and Direct Connect live inside that same Multiplayer screen, a LAN-only studio server doesn't sidestep it (that's an inference from the menu structure; no official text says so). Send families the toggles a week early and keep two adult-owned spare accounts.

## Nothing is public except the game ports

The security posture has one organising idea: the only inbound ports on the studio IP are TCP 25565–25570, and everything administrative rides Tailscale. SSH first. Two drop-ins, `/etc/ssh/sshd_config.d/20-force_publickey_auth.conf` (`PasswordAuthentication no`, `AuthenticationMethods publickey`) and `20-deny_root.conf` (`PermitRootLogin no`), plus `AllowUsers dave`, are the Arch wiki's recipe; put your key in `authorized_keys` first, and note custom snippets should sort after `99-archlinux.conf` ([Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Force_public_key_authentication)). With passwords off, brute force is already blunted: OpenSSH 9.8's `PerSourcePenalties` is "a basic protection similar to fail2ban", pam_faillock locks password auth after three failures but never key auth, and fail2ban's own page says it "usually does not make sense" with key-only sshd ([Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Protecting_against_brute_force_attacks), [Arch wiki: Security](https://wiki.archlinux.org/title/Security#Lock_out_user_after_three_failed_login_attempts), [Arch wiki: fail2ban](https://wiki.archlinux.org/title/Fail2ban)). If you want a banner anyway, sshguard with the nftables backend is the lighter Arch choice ([Arch wiki: sshguard](https://wiki.archlinux.org/title/Sshguard)). Moving the port only reduces log noise ([Arch wiki: OpenSSH](https://wiki.archlinux.org/title/OpenSSH#Configuration)). Better than any of that: don't expose 22 at all. Tailscale SSH "takes over port 22 for traffic arriving via the Tailscale IP", leaves `sshd_config` untouched, and can force periodic re-auth with `action: "check"` ([Tailscale KB: Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)); keep plain key-based sshd reachable on `tailscale0` as the fallback for the moment `tailscaled` is mid-upgrade. Mosh adds nothing once SSH rides WireGuard and would need UDP 60001–60999 ([Arch wiki: Mosh](https://wiki.archlinux.org/title/Mosh)). A panel, if you ever add Crafty or Uptime Kuma, binds to `127.0.0.1` and is published with `tailscale serve`, which only tailnet devices can reach ([Tailscale KB: Serve](https://tailscale.com/kb/1312/serve)).

Use nftables directly: the package ships a secure default `/etc/nftables.conf`, ufw only works through the `iptables-nft` layer, and firewalld is a heavier front-end ([Arch wiki: nftables](https://wiki.archlinux.org/title/Nftables)). This ruleset is assembled from the wiki's server example and its rate-limit and dynamic-set idioms; the rate numbers are placeholders to tune (a class joining at once is about 20 new connections in a minute):

```
flush ruleset
table inet filter {
  set mc_abusers { type ipv4_addr; flags dynamic, timeout; timeout 10m; }
  chain input {
    type filter hook input priority filter; policy drop;
    iif lo accept
    ct state invalid drop
    ct state { established, related } accept
    meta l4proto { icmp, ipv6-icmp } accept
    iifname "tailscale0" tcp dport ssh accept
    # tcp dport ssh ct state new limit rate 15/minute accept   # only if public SSH must stay
    tcp dport 25565-25570 ct state new add @mc_abusers { ip saddr limit rate over 10/minute } drop
    tcp dport 25565-25570 ct state new limit rate 30/minute burst 20 packets accept
    # nothing for 25575-25580 (RCON) or udp 25565 (Query): policy drop covers them
  }
  chain forward { type filter hook forward priority filter; policy drop; }
  chain output  { type filter hook output  priority filter; policy accept; }
}
```

Reload atomically with `nft -f /etc/nftables.conf` and keep it enabled as `nftables.service` ([Arch wiki: nftables](https://wiki.archlinux.org/title/Nftables#Atomic_reloading)). Tailscale's own UDP 41641 is outbound-initiated and works through the established/related rule. Two Docker notes even though the recommendation avoids it: the `forward` drop policy breaks container networking (the Arch wiki says nftables "may block docker connections by default"), and if containers ever appear, their published ports are not covered by this `input` chain, so publish them to `127.0.0.1` or restrict them in `DOCKER-USER` ([Arch wiki: Docker](https://wiki.archlinux.org/title/Docker#Troubleshooting), [Docker docs: iptables](https://docs.docker.com/engine/network/firewall-iptables/)).

On RCON, the right phrasing is "off to the network", not "off". The native design needs a command channel for the graceful `ExecStop`, the backup `save-off`/`save-on`, deploys (`reload`), and whitelist syncs, and RCON is unencrypted, so the wiki says localhost only ([Server.properties](https://minecraft.wiki/w/Server.properties)). Enabling it with a random per-server password while the firewall never opens 2557N gives exactly that; `server-ip` can't bind RCON separately (it moves the game port too). The cautionary tale is the Docker image's default password, which a scanner author found accepted by "a few hundred" exposed servers ([matdoes.dev](https://matdoes.dev/minecraft-scanning)). If you'd rather keep RCON off entirely, the alternative is a stdin FIFO or tmux for commands; whether the 26.3 server saves cleanly on a bare SIGTERM isn't sourced in this research, so test a `systemctl stop` and read `latest.log` before relying on it.

The Minecraft-level settings do the heavy lifting against the internet. Full-IPv4 scans take "several hours" from one VPS, known servers are re-checked hourly, and griefing groups run their own scanners ([matdoes.dev](https://matdoes.dev/minecraft-scanning), [matscan FAQ](https://matdoes.dev/matscan.md)), so an open port is found within hours to days; `online-mode=true` plus a whitelist is what stops joins, and offline mode makes the whitelist useless because bots try previously seen usernames until they hit an op ([Java server tutorial](https://minecraft.wiki/w/Tutorial:Setting_up_a_Java_Edition_server), [matscan FAQ](https://matdoes.dev/matscan.md)). Op levels are cumulative and per-command: level 2 covers `function`, `reload`, `datapack`, `execute`, `give`, `gamemode`, `tp`, `fill`, `summon`, `dialog`, `gamerule`, and command blocks; level 3 adds `op`, `ban`, `kick`, `whitelist`, `transfer`; level 4 adds `stop`, `save-all`, `perf` ([Permission level](https://minecraft.wiki/w/Permission_level), [Commands](https://minecraft.wiki/w/Commands)). Since the npc-game forms run `/function` as the player and need op, kids get op at level 2: `op-permission-level=2` makes every `/op` grant level 2, and because `/op` itself is level 3, a kid can't op a friend. The teacher's entry in `ops.json` is edited to `"level": 4` by hand (the per-op level lives there and existing entries keep their stored level) ([Permission level](https://minecraft.wiki/w/Permission_level)). The blast radius of a level-2 kid is one world: `/fill` and `/clone` up to `max_block_modifications` 32768 per command, `/kill @e`, `/gamerule`, `/reload`, lag machines, but never `/stop`, `/ban`, or the host ([Game rule](https://minecraft.wiki/w/Game_rule)). Mitigations are the per-server sandbox, hourly backups during class, lower `max_command_forks`/`max_command_sequence_length` on servers that don't need them, and `log_admin_commands` left on so `latest.log` says who ran what. Keep `enforce-secure-profile=true`: unsigned chat is tagged `[Not Secure]` in the log and can't be reported to Mojang ([Java Edition 1.19.1](https://minecraft.wiki/w/Java_Edition_1.19.1)). Treat usernames, UUIDs, IPs, and chat logs as children's personal data: the FTC's COPPA FAQ counts screen names and IP addresses as personal information, applies to commercial operators, and the amended rule (compliance date 22 April 2026) requires a written retention policy inside the privacy notice ([FTC COPPA FAQ](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions), [Fenwick summary](https://www.fenwick.com/insights/publications/what-the-amended-coppa-rule-means-for-data-retention-practices)); a one-page notice, parent email consent, a fixed log-retention window on the encrypted disk, and no public status page showing names is the proportionate posture. Not legal advice.

The LUKS root is the one problem that changes how you operate the box remotely. After every kernel update or power cut, someone has to type the passphrase at the console before anything starts, and Arch has no unattended-upgrades: the wiki's position is read the news, then `pacman -Syu`, with `checkupdates` for safe checking and a reboot as "always the most secure" option after a kernel update ([Arch wiki: System maintenance](https://wiki.archlinux.org/title/System_maintenance)). Two supported remote routes exist. TPM2 auto-unlock: `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/<luks-partition>` plus `--recovery-key`, the `systemd` + `sd-encrypt` mkinitcpio hooks, and `rd.luks.options=<UUID>=tpm2-device=auto` on the kernel line; PCR 7 binding assumes Secure Boot is active and in user mode, can be invalidated by firmware certificate changes, and the wiki describes PCR 15 or signed-UKI policies as mitigations against a rogue root partition ([Arch wiki: systemd-cryptenroll](https://wiki.archlinux.org/title/Systemd-cryptenroll), [Arch wiki: dm-crypt/System configuration](https://wiki.archlinux.org/title/Dm-crypt/System_configuration#Trusted_Platform_Module_and_FIDO2_keys)). SSH in the initramfs: for a systemd initramfs the AUR `mkinitcpio-systemd-extras` with `sd-network sd-tinyssh sd-encrypt` hooks, `tinyssh` installed, and the **critical** `rootflags=x-systemd.device-timeout=0` kernel flag, without which systemd gives up after 90 s and "You are then effectively locked out"; the older `mkinitcpio-dropbear`/`-tinyssh`/`-netconf` packages are unmaintained, and the busybox path is now `mkinitcpio-extras` + `mkinitcpio-utils` listening on port 222 with `ip=` on the kernel line ([Arch wiki: dm-crypt/Specialties](https://wiki.archlinux.org/title/Dm-crypt/Specialties#Remote_unlocking_of_root_(or_other)_partition)). For a studio machine that needs reboots while the admin is away, TPM2 with a recovery key kept off-box is the usual pick; initramfs SSH keeps the passphrase a human secret at the cost of wired Ethernet and an extra boot-time service. One GRUB-specific check that isn't in the sources but matters: if GRUB itself prompts for the passphrase before the kernel loads (that is, `/boot` is inside the LUKS container and GRUB uses `cryptodisk`), neither initramfs route gets a chance to run; confirm which stage asks before choosing. Until one of these is in place, every remote `pacman -Syu` that includes a kernel is a trip to the studio, which is a reason to run `linux-lts` and batch kernel reboots into class days. On sudo, keep `%wheel ALL=(ALL:ALL) ALL` with a password; the wiki's warning is that blanket NOPASSWD lets any process under your user escalate, and the alternative is per-command `NOPASSWD:` lines (reboot, `pacman -Syu`, the deploy script) after the `%wheel` line ([Arch wiki: Sudo](https://wiki.archlinux.org/title/Sudo#Configuration)).

## Backups freeze saves, deploys are rsync plus reload

A live world can only be copied safely between `save-off` and `save-on`: `save-off` "stops the server from writing to level files, except player, advancement, and stat files, so they can be copied", `save-all flush` writes everything immediately, and `save-off` resets on restart, so a crash mid-backup self-heals ([Commands/save-all](https://minecraft.wiki/w/Commands/save-all)). Region files are rewritten in place, which is why Crafty's docs warn that copying "file system data" during play "can cause data loss or corruption" ([Crafty: Backup Manager](https://docs.craftycontrol.com/pages/user-guide/backup-manager/)). This is exactly the sequence itzg's sidecar automates over RCON, including a filesystem `sync` after `save-all` ([itzg/docker-mc-backup](https://github.com/itzg/docker-mc-backup)); natively it's a 20-line script with a `trap` so `save-on` always runs:

```bash
#!/bin/bash
# /usr/local/bin/mc-backup <name>   (run as root from mc-backup@.timer, hourly)
set -euo pipefail
n=$1; d=/srv/mc/$n; . "$d/.env"
export RESTIC_REPOSITORY=/srv/backups/restic RESTIC_PASSWORD_FILE=/root/.restic-pw
rcon() { mcrcon -H 127.0.0.1 -P "$RCON_PORT" -p "$RCON_PASSWORD" "$@"; }
if systemctl is-active -q "minecraft@$n"; then
  trap 'rcon save-on' EXIT
  rcon save-off "save-all flush"; sleep 2; sync
fi
restic backup "$d" --tag "$n" --exclude '*.jar' --exclude logs --exclude cache \
  --exclude libraries --exclude .fabric --exclude versions
restic forget --tag "$n" --keep-hourly 24 --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune
curl -fsS -m 10 --retry 3 "https://hc-ping.com/<uuid-for-$n>" >/dev/null
```

Back up the whole server directory, not just `world/`: `whitelist.json`, `ops.json`, `server.properties`, `mods/`, and `config/` live outside it, and `world/` already contains `datapacks/`, `players/`, `data/minecraft/` (scoreboards and command storage are world-level, which is what the tutorial's per-player progress depends on), and `dimensions/` ([Java Edition level format](https://minecraft.wiki/w/Java_Edition_level_format), [Commands/whitelist](https://minecraft.wiki/w/Commands/whitelist)). restic's retention is one `forget` line with `--prune`, and the docs say to run `restic check` after pruning ([restic: removing snapshots](https://restic.readthedocs.io/en/stable/060_forget.html)); deduplication across six similar small worlds keeps the repository tiny. Put the repository on a second disk or straight onto the laptop (`sftp:dave@laptop:/path` when it's on the tailnet), or keep it local and pull with `rsync -a --delete studio:/srv/backups/ ~/mc-backups/` from the laptop; the healthchecks.io ping turns a silently broken timer into an email, since a check goes Late when its period elapses and Down after the grace time ([healthchecks.io docs](https://healthchecks.io/docs/)). Take a tagged manual snapshot before each class (so griefing rolls back to "start of class") and before every upgrade, and test a restore once a term by unpacking into a scratch directory and starting a throwaway server on port 25599.

Upgrades are mechanical but one-way. 26.4 Snapshot 1 still lists Java 25 and sets data pack format **122.0** (26.3 is 121.0; the repo's packs declare `min_format: 107, max_format: 121`), with worldgen-side changes and three new `server.properties` keys but no removed commands ([Java Edition 26.4 Snapshot 1](https://minecraft.wiki/w/Java_Edition_26.4-snapshot-1), [Pack format](https://minecraft.wiki/w/Pack_format)). Paper's guide applies to any jar: back up, stop before replacing the jar, watch the startup log, avoid automatic updates ([PaperMC: updating](https://docs.papermc.io/paper/updating/)); worlds upgraded to 26.3 can't be downgraded ([space-node, third-party](https://space-node.net/blog/minecraft-26-3-server-update-guide-2026)), so rollback means restoring the pre-upgrade snapshot. The sequence: tagged backup; clone one server directory to a scratch port and run the 26.4 launcher there (`https://meta.fabricmc.net/v2/versions/loader/26.4/<stable loader>/1.1.2/server/jar`, choosing a loader with `stable: true` in Fabric meta); bump `max_format` to 122 in every `pack.mcmeta` and rezip; swap `fabric-api-*+26.4.jar` (each Fabric API build is single-version) and a spark build listing 26.4 (today's `spark-1.10.187-fabric.jar` covers 26.1–26.3 with no Fabric API dependency) ([Modrinth API: spark](https://api.modrinth.com/v2/project/spark/version?game_versions=%5B%2226.3%22%5D&loaders=%5B%22fabric%22%5D)); `/reload` and grep `latest.log` for "Failed to load function" and "Registry loading errors"; then upgrade the real servers one at a time on a non-class day. Java pinning on Arch needs no `IgnorePkg`: `jre25-openjdk-headless` stays at 25.x across `-Syu`, and the explicit path in the unit ignores whatever `archlinux-java fix` does to the default; `IgnorePkg` is only for freezing a specific 25.0.x build.

The laptop-to-server deploy has two shapes. A world ships once: stop the singleplayer world in Prism so `level.dat` is flushed and the OS file lock on `session.lock` is released ([Java Edition level format](https://minecraft.wiki/w/Java_Edition_level_format)), then with the server stopped run `rsync -a --delete --exclude session.lock --exclude level.dat_old --exclude 'players/' ~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/instances/<inst>/minecraft/saves/<world>/ studio:/srv/mc/<name>/world/` and `chown -R minecraft:minecraft`. Excluding `players/` drops your own position and inventory so kids spawn at world spawn; the `datapacks/` subfolder rides along with the zips already installed. A pack change ships often and never touches the world: `scp ~/minecraft/zips/<pack>.zip studio:/srv/mc/<name>/world/datapacks/` then `mcrcon … reload` and `grep -A3 "Failed to load function" logs/latest.log`. For `commands-tutorial`, which keeps per-player scoreboards and storage in the world, re-copying the world wipes progress; the zip is what you redeploy. `/reload` covers "registry tags, loot tables, recipes, advancements, item modifiers, predicates, functions, and structure templates", which is everything these packs change today; dimension and worldgen files need a restart, and an invalid pack leaves the previous data in use ([Commands/reload](https://minecraft.wiki/w/Commands/reload), [Data pack](https://minecraft.wiki/w/Data_pack)). Whitelist edits made outside the game need `whitelist reload`; `ops.json` is read at start ([Commands/whitelist](https://minecraft.wiki/w/Commands/whitelist)). Keep `server.properties`, `whitelist.json`, `ops.json`, the unit files, the nftables config, and the scripts in a `server-config/` git repo with the `.env` files untracked.

Running state needs little attention. With vanilla pause-when-empty and no plugin leaks, there's no evidence small servers need daily restarts; a weekly one at a dead hour, after the backup, is enough. The watchdog exit (code 1) under `Restart=on-failure` brings a server back in ten seconds and leaves a report in `crash-reports/`; JVM-level crashes write `hs_err_pid<pid>.log` in the working directory instead, relocatable with `-XX:ErrorFile=` ([Crash](https://minecraft.wiki/w/Crash), [Oracle troubleshooting guide](https://docs.oracle.com/en/java/javase/21/troubleshoot/fatal-error-log.html)). Logs go two places: the journal (cap it with `SystemMaxUse=500M` in `journald.conf` and set `Storage=persistent`) and Minecraft's own `logs/latest.log` plus dated `.log.gz` rotations; keep the gzipped logs for the term plus your retention window since chat, `[Not Secure]` tags, admin commands, and IPs (with `log-ips=true`) all land there, and clean them with a `find … -mtime` line in the backup script rather than `tmpfiles.d` so `crash-reports/` and `hs_err` files survive. Time sync (`timedatectl set-ntp true`) matters for the timers, healthchecks, and Mojang's session servers.

For monitoring, spark in every `mods/` is free and gives `/spark tps`, `/spark health`, `/spark tickmonitor --threshold-tick 100`, and `/spark profiler start --only-ticks-over 100`, which is how you find the datapack function behind a "Can't keep up!" line; look under `MinecraftServer.tickChildren` ([spark: command usage](https://spark.lucko.me/docs/Command-Usage)). Without mods, `/tick query` (1.20.3+, permission 3) reports average and percentile tick times ([Commands/tick](https://minecraft.wiki/w/Commands/tick)), and `/debug function <name>` writes a trace with every command a function ran, handy for counting what `tut:internal/tick` does per player ([Commands/debug](https://minecraft.wiki/w/Commands/debug)). Outside-in, Uptime Kuma (bound to `127.0.0.1:3001`, published with `tailscale serve`) has TCP and Push monitors and a `gamedig.js` type in its source tree that covers Minecraft ([Uptime Kuma](https://github.com/louislam/uptime-kuma), [monitor types](https://github.com/louislam/uptime-kuma/tree/master/server/monitor-types)); itzg's `mc-monitor status -host 127.0.0.1 -port 2556N` exits non-zero when a server is hung behind an open port and can export Prometheus metrics if you ever want Grafana ([itzg/mc-monitor](https://github.com/itzg/mc-monitor)). The `OnFailure=notify@%n.service` hook in the unit is systemd's answer to cron's `MAILTO`, which it lacks: a oneshot template that runs a script with the failed unit's name, either the wiki's sendmail recipe or a `curl` to a Discord or ntfy webhook with the URL in a root-only `EnvironmentFile` ([Arch wiki: systemd, notifying with e-mail](https://wiki.archlinux.org/title/Systemd#Notifying_with_e-mail), [quickvm/blazon](https://github.com/quickvm/blazon)). Add the same `OnFailure` to `nftables.service`.

Multi-server housekeeping is mostly naming. One directory per game (`one-block`, `one-block-2`, `command-forge`, `tile-game`, `npc-game`), ports 25565+N and 25575+N, a `README.md` in each saying which pack version it runs and how to reset it, a single `/srv/mc/_shared/whitelist.json` and `ops.json` in the config repo with a `sync-lists.sh` that copies them into each server and runs `whitelist reload` (symlinking one file into six running servers races the first `/whitelist add` that rewrites it), and a short `mc` wrapper: `mc start|stop|restart|status [name|all]` over `systemctl`, `mc rcon <name> <cmd>`, `mc deploy <name> <pack>`, `mc backup [name|all]`, `mc logs <name>` as `journalctl -fu minecraft@<name>`. The template unit's `WantedBy=minecraft.target` plus `PartOf=` gives the real start-all/stop-all.

## Conclusion

The decision that looks like a tooling choice is really a security and operations choice. Running the JVMs directly under systemd means the firewall you write is the firewall you get, the sandbox that stops one op kid from touching another class's world is five lines in a unit, and Java 25 is a package rather than an image tag; every panel in the field adds a web surface and a daemon to defend in exchange for features built for strangers renting servers. The two things that will consume real time are not Minecraft at all: the LUKS passphrase at boot, which turns every kernel update into a studio visit until TPM2 or initramfs SSH is in place, and the child-account multiplayer gate, which no server setting can bypass and which applies on the LAN too.

What changes going forward is that the box becomes the development target as well as the host. The hosting report's one-server-per-game architecture and the dialog custom-click mod both assume a host that runs your jar; this box does, with the same `mods/` and `world/datapacks/` paths the packs already expect, so the laptop's existing zip-and-copy loop extends to `scp` plus `reload` with no new tooling. When 26.4 lands, the whole fleet moves with a URL change, a `max_format` bump, and a scratch-port test, which is cheap enough to do the week it ships rather than the week before class.
